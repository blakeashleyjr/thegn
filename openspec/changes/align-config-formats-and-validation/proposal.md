# Settle the config format contract and close the validation blind spots

Linear: THE-38

## Why

THE-38 ("Configuration audit") asks two questions: are JSON, YAML and TOML all
supported, and are the examples autogenerated from code? The audit answers both
— and found real drift while doing so.

**Formats.** The trusted layers (the main `config.toml`, `--config`, the
profile overlay `profiles/<name>/config.toml`) are TOML-only
(`Config::try_load_layered` → `toml::from_str`). The repo-root overlay is
tri-format: `.thegn.{toml,yaml,yml,json}`, first existing file wins
(`load_repo_overlay`). That split is the right shape — the trusted layers are
one hand-edited file backed by an entirely TOML-native gate chain, while the
repo overlay is a checked-in file that meets other ecosystems' conventions —
but it is documented nowhere and misdocumented in two places. This change
specs the split as deliberate rather than widening it (see Non-goals for why
JSON/YAML at the trusted layers loses).

**Examples.** `config/config.toml.example` is **not** autogenerated, and should
not be: it is hand-written prose that cannot drift, because it is gated in both
directions — `config_example.rs` walks the `schemars` schema and fails on any
undocumented section/key, the example must parse as a `Config`, and
`example_config_validates_clean` strict-validates it. Downstream, the in-app
config-reference help page is _generated from the example at runtime_
(`help/config_ref.rs`), and `hm_module_drift` checks the home-manager module
against the same schema. Autogeneration would trade curated prose for
mechanical dumps and gain nothing the gates don't already guarantee. The
answer to THE-38's second question is "no, and by design" — recorded here, no
delta needed.

**Drift and blind spots found by the audit** (the actual work):

1. The config spec's layer requirement omits the profile overlay from the
   fixed order, and claims the repo overlay carries "`[sandbox]` only" — the
   real `RepoConfigFile` carries `[sandbox]` (trust-clamped), `[keybinds]`,
   `[notifications]`, `[issues]`, and the `env` selector.
   `docs/help/configuration.md` contradicts _itself_: one paragraph lists
   sandbox/keybinds/env, another says "`[sandbox]` only".
2. The spec and the help page both reference `thegn config validate --strict`.
   No such flag exists — `Action::Validate` takes none; validation is
   unconditionally strict. The docs describe a CLI that isn't there.
3. `thegn config validate` reads only the main file. The profile overlay and
   the repo `.thegn.*` are never strict-checked anywhere: a typo'd key in
   either is silently dropped by tolerant deserialization, with no command
   that would ever report it.
4. When more than one `.thegn.*` file exists in a repo root, all but the
   first (TOML > YAML > yml > JSON) are silently ignored — editing
   `.thegn.yaml` while a stale `.thegn.toml` sits beside it does nothing,
   wordlessly.
5. `thegn doctor` — the diagnosis hub that reports every provider probe,
   sandbox capability and reserved kind — says nothing about whether the
   config file it just loaded has problems.

## What Changes

- **Spec the format contract**: TOML is the only format at the trusted layers;
  the repo overlay accepts `.thegn.{toml,yaml,yml,json}` with the existing
  precedence. (ADDED requirement; behaviour unchanged except the warning
  below.)
- **Warn on shadowed repo overlays**: when multiple `.thegn.*` files exist,
  the load warns naming the file used and the file(s) ignored.
- **`thegn config validate` covers every layer it can locate**: the main file,
  the active profile overlay, and — when run inside a repo or given
  `--repo` — the repo `.thegn.*`, strict-checked against the
  `RepoConfigFile` schema in whichever of its three formats it is written,
  each problem prefixed with the file that carries it.
- **`thegn doctor` gains a config-health line**: the config path plus its
  strict-validation problem count (and the same for a repo overlay when run
  inside one), pointing at `thegn config validate` for the detail.
- **Fix the drift**: the spec's layer requirement gains the profile overlay
  and the repo overlay's real table set; `--strict` disappears from spec and
  help-page prose (validation is strict, full stop);
  `docs/help/configuration.md`'s two contradictory paragraphs are reconciled.

## Non-goals

- **JSON/YAML at the trusted layers.** Every consumer of the user config is
  TOML-native: `config set` edits via `toml_edit` preserving comments, the
  example-coverage gate scans TOML, the config-reference page renders from
  TOML, the home-manager module emits TOML, live-reload watches
  `config.toml`. Multi-format would multiply the write path, the gates and
  the docs for no demonstrated demand — and `thegn config schema` already
  gives any editor JSON-Schema-driven validation of the TOML. The repo
  overlay is where format tolerance earns its keep, and it already has it.
- **Autogenerating `config.toml.example`** — see Why; the gates make
  hand-written prose drift-proof, which beats generated text.
- **A defaults-accuracy gate for commented `# key = value` lines** (do the
  commented values match code defaults?). Plausible but noisy — many
  commented values are deliberately illustrative, not defaults. Recorded as
  an open question in design.md, not scoped.
- **Trust-clamp semantics.** The repo overlay's constraint clamping,
  trust-on-first-use and `config explain` traces are owned by
  `add-config-trust-resolution` (implemented, unarchived) and untouched here;
  this change only describes the overlay's _table set and formats_ correctly.

## Impact

- Roadmap: **O 188** (validation + error surfacing), **O 189** (config
  layering), **O 192** (schema docs) — this is the audit-and-tighten pass over
  work those items landed.
- Specs: `config` — 2 MODIFIED ("Configuration layers in a fixed order",
  "Unknown keys are reported by strict validation"), 2 ADDED ("One
  configuration format per trust tier", "Doctor reports configuration
  health").
- Code: `thegn-core` `config_validate.rs` (overlay validation walk — pure,
  unit-tested under the 95% line gate), `config.rs` (`load_repo_overlay`
  shadow warning); `thegn-host` `cmd/config.rs` (multi-layer validate),
  `cmd/doctor.rs` (config-health line); `docs/help/configuration.md`.
- In-flight reconciliation: `add-config-trust-resolution` (its `sandbox` and
  `state-db` deltas are untouched; the layer-requirement rewrite here
  describes the repo `[sandbox]` table as trust-clamped, consistent with it).
  No overlap with `add-workspace-zones` (reserved trust slot unaffected).
- No new capability-catalog row: `config validate`/`doctor` are local CLI
  verbs that never drive a running instance; the catalog's surfaces are
  unaffected.
