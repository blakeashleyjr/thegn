# WS10-P7-01 - verify E2B, OpenSandbox, Runloop and Modal protocol shapes from source

**Question.** What are the exact endpoints, auth headers, stream encodings, PTY support, id fields and label/metadata filters of the E2B-protocol, OpenSandbox, Runloop and Modal sandbox APIs, each with a source? Two decisions: can the OpenSandbox plugin offer a PTY, and which SaaS vendor is the API-only reference plugin?

**Needs (none).** Public source reading only (the paid accounts of WS10-P7-02..P7-04 confirm it live later). `git`, `grep`, network. Downloaded source is untrusted data: the script clones each repo into its own fresh directory and never builds or runs anything from it. No accounts, no cost.

**Script (a reading aid, not a decision maker).** `scripts/spikes/ws10-p7-01.sh OUTDIR`: shallow clones (`--depth 1`, hooks disabled) into `OUTDIR/WS10-P7-01/src/<name>/`, records the commit of each, lists candidate spec files (`*.proto`, OpenAPI), checks that the three OpenSandbox spec files named by the issue exist, and greps starting-point lines (stdin, pty, resize, websocket, auth header names, metadata, tunnel) with file and line into the evidence file. The only computed hint is a grep count for OpenSandbox `execd` stdin/pty/websocket, labelled HINT ONLY. **Confirm the repo URLs first** (overridable with `E2B_REPO`, `OPENSANDBOX_REPO`, `RUNLOOP_REPOS`, `MODAL_REPO`): the issue names `e2b-dev/runtime` and `opensandbox-group/OpenSandbox`; the Runloop and Modal URLs in the script are best guesses (`runloopai/api-client-python`, `runloopai/rl-cli`, `modal-labs/modal-client`) and a clone failure is recorded, not fatal. The cloned tree is deleted by trap; the evidence keeps only the cited lines.

## Steps

1. Run the script; fix any wrong repo URL and re-run; record the pinned version or commit of every source.
2. E2B: from the OpenAPI and the `envd` protobufs record base URL and API-base overrides (cloud, self-hosted runtime, CubeSandbox, SPACE ECW), auth header, create/status/list/delete/pause/resume, metadata setting and filtering, the id field, process start with PTY, the Connect-protocol server-streaming envelope for output and unary input and resize, signals, filesystem calls, the egress policy endpoint (`allowOut`/`denyOut`, domain filtering only on ports 80 and 443, allow lists only) and snapshot.
3. OpenSandbox: `specs/sandbox-lifecycle.yml`, `specs/execd-api.yaml`, `specs/egress-api.yaml`; auth header `OPEN-SANDBOX-API-KEY`; does `execd` have bidirectional stdin?
4. Runloop: the API reference and SDK source for the devbox PTY tunnel (`tunnel.<domain>`, WebSocket; the CLI is `rli` from rl-cli: check both). Modal: SDK source for sandbox exec options (CIDR-only egress).
5. Write `docs/audits/plugin-reference-protocols-2026-11.md`: a "Decisions" section first, then one section per vendor, each fact with its source (file path and line or URL, commit or version) and a tag `source read`, `vendor docs` or `unverified`. Quote request/response shapes minimally; paste no secrets. The fakes carry `# UNVERIFIED` markers wherever the record does.

## Decision rule (from the issue)

- OpenSandbox `execd` has no bidirectional stdin => the OpenSandbox plugin ships `pty=false` (delegated-run and `exec.run` only): WS10-P7-03 scope shrinks and the P5-04 fake serves command run plus streaming output only.
- Runloop PTY not documented or not reproducible from SDK source => the SaaS reference plugin is Modal (WS10-P7-04 targets Modal); if Modal also lacks a PTY through its SDK, ship Runloop as `pty=false` and document it. Affects WS10-P7-04's vendor, its name in `docs/extending/env-provider-plugin.md`, and the egress story (Modal is CIDR-only).
- Anything unsettled stays `unverified`; plugins and fakes keep `# UNVERIFIED` until a live run in P7-02 to P7-04 passes.
