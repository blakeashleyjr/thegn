# WS10-P2-04 - plugin stream framing: base64 in NDJSON versus an fd side channel

**Question.** Can Plugin API 0.7 carry terminal and exec bytes as base64 inside NDJSON `stream.data` frames (decoded at most 32 KiB per frame, 1 MiB line cap), or must `stream:fd` (a second transport) be built? Targets: Rust echo child at least 100 MB/s, Python child at least 20 MB/s, added 1-byte echo p99 at most 2 ms.

**Needs (none).** Linux dev host (macOS numbers are advisory and only if the W0 Mac is available: run the same script there), Rust toolchain, network to crates.io for `serde_json` and `base64` (the probe is standalone, not the workspace), `python3` (stdlib only). Quiet machine. No accounts, no cost.

**Script and probe.** `scripts/spikes/ws10-p2-04.sh OUTDIR`, building `scripts/spikes/probes/plugin-framing/` (standalone crate with its own `[workspace]`, built from a COPY under OUTDIR; also `bench_echo.py`, the stdlib Python echo child). Same machine, same harness for three children: `raw` (`cat`, no JSON or base64: the baseline), `rust` (decode+re-encode echo, serde_json + base64), `python`. Sizes 1 B, 1 KiB, 32 KiB (one maximum chunk) and 1 MiB (32 frames of 32 KiB, burst completion), p50/p99 latency, pipelined MB/s, and child cold start (spawn to first echo, p50 of 10). Every child is waited on. The real bench the item lands is `crates/thegn-svc/benches/plugin_framing.rs` (criterion, `[[bench]] harness = false`) and `examples/plugins/python/bench_echo.py`; this probe is the equivalent one-run spike and does not depend on P1/P2 code.

## Steps

1. `scripts/spikes/ws10-p2-04.sh $HOME/spike-evidence/WS10-P2-04-$(date +%F)` (about a minute of load after the build).
2. The script records machine description (CPU, cores, governor, rustc, python) and computes: added 1-byte p99 = framed p99 minus raw-pipe p99 (the issue does not define it more exactly, so both absolute numbers and the difference are recorded), Rust and Python MB/s at 32 KiB frames, cold start.
3. Optionally repeat on macOS (advisory).
4. Write `docs/audits/plugin-stream-framing-2026-11.md`: the table for both children at all four burst sizes, the raw-pipe baseline, cold start, the machine description, the decision and the rule that produced it. When the real bench lands run it with `cargo bench -p thegn-svc --bench plugin_framing` (not `just bench-micro`).

## Decision rule (from the issue)

If Python is below 20 MB/s, or the added p99 is above 2 ms for a 1-byte echo, open a 0.8 item for `stream:fd` (Unix socketpair; Windows named pipe). Otherwise record "base64 only" and close.

## Downstream

"Base64 only": WS10-P2-03 builds the stream table as specified and `stream:fd` stays a reserved unused manifest capability. "Open stream:fd": WS10-P2-03 still ships base64 first and files the 0.8 item; the side channel is added later. Either way the measured numbers go into the P2-03 acceptance and plugin docs. Expected cold start (plan): Python about 30-60 ms, Node about 40-80 ms, Rust about 2 ms.

**Time.** 45 min plus the record.
