# WS06-P6-03 - nested-virtualisation spike: does WSL2 boot inside the Win11 KVM guest?

**Question.** Does WSL2 boot and run a Linux command inside the Windows 11 KVM guest on the owner's Linux machine? The answer decides where the WSL and container device checks run (the VM or the owner's Windows machine). Five W0 items wait on this one.

**Needs (kvm + windows-device).** Linux host with KVM (`kvm_amd`/`kvm_intel` `nested` on), `quickemu` from the repo flake (the VM is the existing `scripts/windows-vm.sh`), 40-60 GiB disk and 16 GiB RAM for the guest, 30-60 minutes of first boot plus a Windows Update pass, and the licence gate `THEGN_WINVM_ACCEPT_LICENSES=1` (Microsoft consumer ISO, unattended Build Tools; unchanged by this item). The guest must be at 24H2 26100.9278+ or 25H2 26200.9278+ (an older build must fail provisioning). No accounts, no paid runners.

**Script (the spike only).** `scripts/spikes/ws06-p6-03.sh OUTDIR [DISTRO=Ubuntu]`: read-only. HOST part always: CPU vendor, kernel, KVM `nested` flag, `/dev/kvm`, the running QEMU command line. GUEST part only if the VM is up (it ssh-es with the VM's own `ssh_config`, host alias `thegn-winvm`): build/UBR, `HypervisorPresent`, processor virtualisation fields, `wsl --version`, `wsl -l -v`, `wsl -d <distro> -e uname -r`, uptime and memory. It never starts, provisions or destroys the VM. The item's implementation work (provision.ps1 build/UBR check and update step, nested CPU flag, `wsl-check` subcommand, `just test-windows-sandbox`, CONTRIBUTING ladder, optional WSL/engine installs) is NOT a spike and is not in the script; the spike needs a VM prepared with the nested CPU flag (`-cpu host,+vmx` Intel or `+svm` AMD; work out how quickemu passes extra QEMU arguments or document the direct-QEMU alternative) and the WSL install (`wsl --install --no-distribution`, then a distro; reboot).

## Steps

1. Host: record kernel, CPU vendor, and the KVM `nested` parameter (`/sys/module/kvm_amd/parameters/nested` or `kvm_intel`; `Y` or `1`).
2. Provision/boot the VM with the nested CPU flag and WSL installed (`THEGN_WINVM_ACCEPT_LICENSES=1 scripts/windows-vm.sh setup` then `up`, per the implementing item), reboot after the WSL install.
3. `scripts/spikes/ws06-p6-03.sh $HOME/spike-evidence/WS06-P6-03-$(date +%F) Ubuntu`.
4. Record boot time, memory use and any failure text. Paste the QEMU command line or quickemu config, guest build/UBR, the hypervisor output and the WSL output into the issue and the CONTRIBUTING note.

## Decision rule (from the issue)

- WSL2 boots and runs `uname -r` => WS06-P2-00 (WSL capture), WS06-P2-10 (seal evidence) and WS06-P3-04 (engine spike) run in the VM, with the owner's device as a second confirmation where the plan asks for physical-console checks.
- It does not boot => those three items run on the owner's Windows device; the VM still serves WS06-P0-05 and the job-limit and MXC checks. Never mark WSL checks done from a Linux-only substitute.
