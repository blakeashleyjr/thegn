# WS06-P4-00 - direct PSEC exports vs pinned `mxc-sdk`, and the proxy peer identity

**Question.** (1) Does the helper talk to Windows' process security environment (PSEC) through direct `processmodel.dll` exports or Microsoft's `mxc-sdk`? (2) Does a console (ConPTY) child work under PSEC? (3) Which string identifies the egress proxy as an allowed AppContainer peer (profile name or SID)? (4) May a proxy URL carry the lease token as userinfo?

**Needs (windows-device + kvm).** Windows 11 at 26200.9278+ (the WS06-P6-03 VM) AND a 26100.9278+ install (or the owner's device); run EVERYTHING on both builds and state the exact UBR (a build below the minimum is not evidence). Rust toolchain; the MXC and Codex MXC-wrapper source at a pinned revision for reading `secenv.rs`, `base_container_runner.rs`, `availability.rs`, `policy.rs` and `ProcessSecurityEnvironment.fbs` (MIT). A VM or device you can reset; synthetic canary files and invented tokens only. If only one build exists, record the other "blocked" and keep the strategy decision open (the rule needs both). Timebox for the direct path: 5 days. No accounts, no cost.

**Script (partial, by design).** `pwsh -File scripts\spikes\ws06-p4-00.ps1 -OutDir C:\spike-out [-MxcRevision <sha>]` (parse-checked only; read-only; starts nothing under PSEC): records build/UBR against the supported-build table, loads `processmodel.dll` from System32 and records which of the four exports exist, plus toolchain and MXC revision. **Not scripted and not guessed:** X1.2-X1.5, X2, X3, X4, X5 call undocumented exports and the FlatBuffer policy, whose exact signatures must be taken from MXC's own source at the pinned revision; code written from memory would produce misleading evidence about an undocumented ABI. Write that code under `tools\spikes\psec\` on an UNMERGED branch (and `mxc-sdk` in an excluded workspace `tools\thegn-sandbox-win-mxcsdk\` for X4). The spike must add nothing to the main `Cargo.lock`.

## Steps (each on both builds; record argv, output, pass/fail/blocked)

1. Run the script on each build. Stop if the build is unsupported or an export is absent (record it; the helper fails closed).
2. **X1 direct path (subset F1-F4, N1-N4, P1-P3).** Resolve the four exports; `IsProcessSecurityEnvironmentVersionSupported(1,0)` and `(1,1)`; `QueryProcessSecurityEnvironmentSupport` (record the flags, especially FS_DENY); `CreateProcessSecurityEnvironment` with an empty deny-all spec then `CloseProcessSecurityEnvironment` (HRESULTs); launch `cmd /c whoami /all` under PSEC (read-write temp dir, deny `%USERPROFILE%\.ssh` with a canary) inheriting a test ConPTY in console mode (no handle list, `bInheritHandles = FALSE`, `CREATE_SUSPENDED | EXTENDED_STARTUPINFO_PRESENT | CREATE_UNICODE_ENVIRONMENT`, assign to a job, resume). Then F1 grant write ok, F2 write outside denied, F3 `.ssh` and browser-profile canaries denied, F4 deny inside a granted parent enforced; N1 network `none`: TCP to 1.1.1.1:443 and DNS fail; N2 proxy-only: direct fails, a throwaway loopback proxy requiring a token succeeds with it and gets 407 without (WS04-P4-02's `thegn-egress.exe` does not exist yet: use a throwaway proxy and say so); N3 `nat` denies 169.254.0.0/16; P1 `pwsh`, `cmd`, `git` interactive through the ConPTY; P2 Ctrl+C once; P3 resize reaches the child.
3. **X2 peer identity.** A listener inside a PSEC container created with a profile name (plays the egress service); derive its SID (`DeriveAppContainerSidFromAppContainerName`); a client container with `allowed_appcontainer_peer` set to the profile name, host loopback deny; repeat with the SID string. Record for each form: accepted by PSEC, client reaches the proxy port, and a second host loopback listener outside any container is UNREACHABLE (the N4 pre-check). Also identity-less mode (peer none, host loopback allow): is the second listener reachable?
4. **X3 userinfo.** Does `ProxyInfo.url` accept `http://user:pass@127.0.0.1:PORT` (throwaway token)? Per-container WinHTTP setting and env-based clients.
5. **X4** repeat X1.3-X1.5 and X2 via `mxc_sdk::v1::spawn_with_extended_options(req, SpawnStdio::Inherit)`; note differences. **X5** release binary size, launch latency (p50/p95 over at least 20 runs of `cmd /c exit 0`, advisory), ETW events listed from a trace session and whether `MXC_TELEMETRY_COMPONENT_PATH=""` stops them, for both paths.
6. Write `openspec/changes/add-windows-mxc-backend/spike-psec.md` (that folder is authored by later WS06 items; add only this file; coordinate with the lead if `just openspec-validate` rejects a folder with no proposal) with logs for both builds, source and toolchain versions, the spike branch and commit, and one sentence each for strategy, peer string, userinfo, ConPTY.

## Decision rule (from the issue)

- Strategy: direct path passes the F1-F4, N1-N4, P1-P3 subset on BOTH 26100 and 26200 within the 5-day timebox => direct PSEC exports (WS06-P4-03 builds, vendored sha256-pinned schema). Otherwise `mxc-sdk` in the excluded workspace with telemetry routing disabled; WS06-P4-03 is not built and the privacy page gains the MXC telemetry statement.
- Peer: record the working string (profile name or SID); WS06-P4-06 passes exactly that. No peer form works, or the client cannot reach the proxy with host loopback denied, or the second host listener is reachable => peer mode does not exist: allowlist stays `PortPinned` plus opt-in (`accept_loopback_open = true`) permanently (E10) and WS06-P6-05 cannot graduate `WinIsolation` on allowlist enforcement. If it works, `PeerProof::OsVerified` only after device check N4 in WS06-P4-08.
- Userinfo accepted => token in `ProxyInfo.url` as well as the proxy env; rejected => env userinfo only (tools reading only the WinHTTP setting get 407 and fail closed, documented).
- ConPTY child fails on either build => record the symptom; WS06-P4-04's console-mode design cannot merge; escalate to the lead.

## Downstream

Unblocks WS06-P4-01, P4-02, P4-03 (only if direct), P4-04, P4-06, P6-05 (through the evidence register). No refusal is lifted; MXC satisfies secure policies only after WS06-P4-08.
