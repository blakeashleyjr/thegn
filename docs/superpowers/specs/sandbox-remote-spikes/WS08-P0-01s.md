# WS08-P0-01s - how the Daytona ssh gateway mints tokens and runs commands

**Question.** Can thegn reach a Daytona sandbox through the token gateway (`ssh <token>@ssh.app.daytona.io`) for both non-PTY commands and PTY panes, with the token held in a private file and never in argv? (The CLI handle `daytona ssh <id> --` is at risk: `daytona-v0 ssh` takes no command after `--`.)

**Needs (paid-account).** A Daytona account (free or paid) with an API key in `DAYTONA_API_KEY`; optional `DAYTONA_API_BASE` (default `https://app.daytona.io/api`) and `DAYTONA_SNAPSHOT`. Tools: `curl`, `jq`, `ssh`, `ssh-keyscan`; `daytona` and `daytona-v0` CLIs optional (versions recorded if present). Cost: ONE throwaway sandbox for a few minutes (a few cents at most; deleted by trap).

**Script.** `DAYTONA_API_KEY=... scripts/spikes/ws08-p0-01s.sh OUTDIR`. The API key and the minted token never appear on argv: curl reads the Authorization header and token-bearing URLs from a 0600 config file; ssh reads the token from a 0600 `ssh_config` `User` line (check 8's file-only route). Tries the candidate mint paths `POST /sandbox/{id}/ssh-access` (with and without an expiry body) and `POST /ssh-access` and records path, body, status and the (redacted) response shape for each; extracts the token field defensively; records the expiry fields; non-PTY `ssh -F cfg host -- echo ok` (check 5); `ssh -tt ... -- tty` (check 6); host key fingerprints from two `ssh-keyscan`s (check 7); checks `ps` for the token while a command runs (check 8); tries candidate revoke calls and confirms a revoked token is rejected (check 4). Deletes the sandbox and removes the secrets directory by trap. The redacted mint response is saved as `OUTDIR/WS08-P0-01s/daytona_ssh_access.json`.

## Steps

1. `export DAYTONA_API_KEY=...` (from your secret store; never paste on a command line), then `scripts/spikes/ws08-p0-01s.sh $HOME/spike-evidence/WS08-P0-01s-$(date +%F)`.
2. Read the mint tries: which path worked, the request body, status, the field holding the token, the expiry field name/format and default (verify/05 says 60 minutes).
3. Revocation: record the call, or that none exists, and whether the revoked token is rejected. Host key: compare the fingerprint with the Daytona docs.
4. If no mint succeeded (or the field names differ), read the saved responses and adapt the candidates in the script's `for try in` list; do not guess a decision.
5. Write `docs/audits/provider-live-2026-11/daytona-gateway.md` (new directory): date, API base, account type, `ssh -V`, CLI versions, a transcript for checks 2 to 8 (redacted: `<TOKEN>`, `<KEY>`), and one decision. Copy the redacted response to `crates/thegn-svc/tests/fixtures/daytona_ssh_access.json` after review (shape must match the real response, only redacted).
6. Confirm the sandbox is deleted and tokens revoked; no token or key may appear in any committed file.

## Decision rule (from the issue)

- Checks 5 and 8 pass => "gateway accepts commands": WS08-P0-01a as planned (hidden `thegn daytona-ssh <id> -- cmd` mints or reads a cached 0600 token, writes a private ssh_config, runs `ssh -F <cfg> tg-daytona-<id> -- cmd` for control and panes).
- Check 6 passes, 5 fails => "PTY only": `daytona-v0 exec {id} --` for non-PTY control, gateway for interactive panes only (descriptor `reach` stays SelfBridge).
- No REST path mints (check 2) => "no API mint": WS08-P0-01a reduced to the `daytona-v0` path; the token-file design is removed.
- Check 3 sets the refresh margin (mint when missing or under 5 minutes left) and token cache lifetime; check 4 whether the bridge revokes on exit or lets tokens expire; check 7: a stable published key => pinned `HostKeyPolicy` entry (WS09-P1-03), else `accept-new` with a per-sandbox known_hosts file; check 8 failing => stop and report before WS08-P0-01a starts (the no-secret-in-argv guarantee needs another mechanism).
