# BTOP comparison and performance priorities

September 13, 2026. This is a source review and a maintenance plan, not a measured speed comparison. Thegn was inspected at private integration candidate `283550d8` and the in-progress `audit/process-refresh` worktree. BTOP sources were read from upstream `main`; that source identifies itself as 1.4.7, but no immutable upstream SHA was obtained. Recheck the reference revision before implementation.

The strongest near-term match is a stable, responsive process table with low sampling overhead. Thegn already covers the principal resource families. Fix its current refresh defects and unnecessary work before adding a new dashboard or collectors. Missing capabilities below are planning information; this audit does not authorize new feature implementation.

## What to preserve and what differs

BTOP advertises CPU, memory, disk, network and process monitoring, filtering, sorting, tree mode, process details and signals, pausing, mouse interaction, themes and presets. Its official reference images are [normal](https://github.com/aristocratos/btop/blob/main/Img/normal.png), [TTY](https://github.com/aristocratos/btop/blob/main/Img/tty.png), and [help](https://github.com/aristocratos/btop/blob/main/Img/help-menu.png). Upstream screenshot pixels could not be retrieved through the browser, but the installed BTOP 1.4.7 was subsequently captured and inspected at 140×42 using a private Muse PTY/config. It confirms the simultaneous CPU, memory/disk, network and process boxes, dense fixed columns, inline filter/sort controls and persistent action footer. The capture font lacks some box/graph glyphs, and its initial sample has no populated history; it is layout evidence rather than a smoothness benchmark. ## Verified performance mechanisms

BTOP defaults to a 2,000 ms sample interval; configuration recommends that spacing for graph samples and rejects intervals below 100 ms. Faster input response therefore need not mean faster OS collection. [Configuration](https://github.com/aristocratos/btop/blob/main/src/btop_config.cpp#L109)

Its worker blocks on a binary semaphore between requests, collects requested boxes, and can receive a redraw request with `no_update`. It measures collection and drawing separately in debug mode and wraps output in terminal synchronization sequences when configured. GPU collection can still serve the CPU panel when GPU boxes are hidden; visibility is dependency-aware. This is not evidence of zero total idle CPU. [Worker and output](https://github.com/aristocratos/btop/blob/main/src/btop.cpp#L330)

On Linux, process collection keeps prior process data for `no_update`, while applying filter/sort changes. Detailed process reads are conditional. Sorting is suppressed during ordinary paused refreshes. Some input operations, including tree changes, explicitly request collection, so it would be incorrect to claim all key handling is collection-free. [Linux collector](https://github.com/aristocratos/btop/blob/main/src/linux/btop_collect.cpp#L2971), [input handling](https://github.com/aristocratos/btop/blob/main/src/btop_input.cpp#L299)

BTOP distinguishes ordinary selection from an explicit followed PID. Thegn's maintenance fix preserves the selected process on passive updates while retaining deliberate sort/filter navigation semantics; copying BTOP's extra follow UI is unnecessary for THE-628. [Follow and pause controls](https://github.com/aristocratos/btop/blob/main/src/btop_input.cpp#L340)

Thegn already has a separate process sampler, two-second minimum scan interval, narrow CPU/memory refresh, reused scratch storage, bounded retained rows, pure row construction and no command-line reads. These are verified source properties. Comments claiming particular millisecond scan costs were not independently benchmarked in this audit.

## Prioritized maintenance work

1. **Finish THE-628 first.** `run.rs` replaces a hydrated model independently of process sampling and loses `model.procs`, creating intermittent empty/warming views. The process agent's candidate preserves that snapshot, uses deterministic PID ties in top-N selection and flat/tree order, and preserves `(pid, start_time)` selection on passive refresh. Pending signal confirmation and escalation use the sampled identity too. The combined host checkpoint passed 79 monitor and 3 model-equality tests, with independent source review. Native live smoothness benchmarking and canonical-main landing remain pending. Sample identity alone must not be described as eliminating the final OS-level PID-reuse race.
2. **Remove hidden process-worker wakeups and own shutdown.** `hydrate.rs:467-517` unconditionally sleeps 500 ms before checking `live`; hidden or paused state takes `continue`. Receiver closure is detected only by `tx.send` after an enabled scan. The join handle is discarded. Consequently hidden state avoids enumeration but still schedules two wakeups per second and can retain a detached worker indefinitely within a surviving process. The gate is only an atomic store at `run.rs:12060`; nothing wakes a parked worker. Replace this with an owned, fallible worker, an interruptible gate/deadline wait, cancellation and acknowledgement. Retain the two-second scan spacing and reset the CPU baseline on gate close. Use a coalescing latest-snapshot slot or bounded publication, with lifecycle generation fencing. This needs a separate reviewed plan, including a truthful shutdown outcome if an OS sampler itself cannot be interrupted.
3. **Avoid rebuilds unrelated to the active tab.** `MonitorOverlay::rebuild` rebuilds both process and worktree-disk rows for every tab; `refresh` returns true for any unpaused status refresh. Cache by relevant snapshot/view/geometry generation; keep table invalidation separate from graph time progression. Do not cache merely by PID list: CPU/RSS, identity, attribution, filter, tree and sort changes all matter. Benchmark before widening this change.
4. **Stabilize process-column geometry.** `sections.rs:544` recomputes maximum cell widths for every table draw. Changes in names, ownership labels or formatted numbers can shift following columns. Add monitor-specific width constraints based on viewport and explicit clipping; avoid changing all shared tables casually. Also avoid formatting offscreen rows once a measured cost justifies that refinement. Test narrow screens and Unicode display-cell widths.

Linear duplicate check: team-scoped searches for process sampler, process sampling and monitor idle found no exact open issue for item 2. THE-412 concerns a different `gtui-query::HostSource` worker; THE-291 concerns GPU helpers. THE-44 and THE-75 are completed broader audits. THE-628 covers the reported view refresh, so geometry and invalidation evidence should remain related to it without expanding its current approved checkpoint. Items 2–4 can feed a later batch; they do not replace the selected ten issues.

## Acceptance and benchmark protocol

Use the same machine, release profile, terminal, window size and process fixture for before/after comparisons. Warm up 30 seconds, record at least 120 seconds for each state, repeat three times, and publish medians plus p95/p99 input-to-writer-completion latency. Writer completion is not proof of physical display latency. Record process count, scan duration, thread CPU, RSS, scheduled wakeups, rebuild count, output bytes and dropped/coalesced publications.

| State                                                   | Proposed measurable acceptance                                                                                                                                                                                          |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Monitor closed, then another tab selected               | Zero process scans and zero scheduled process-worker timer wakeups after gate acknowledgement. No snapshot publication after shutdown acknowledgement.                                                                  |
| Processes visible, no input                             | Never scan faster than two seconds; retain a continuous valid snapshot between scans and unrelated hydration completions. Record fresh-sample age and CPU delta warmup explicitly.                                      |
| Processes paused                                        | Zero process scans after pause acknowledgement; stable displayed rows; navigation remains responsive. Resuming establishes a fresh CPU baseline instead of reporting an across-pause average.                           |
| 100/1,000/10,000 synthetic processes with equal CPU/RSS | Identical top-N membership and display ordering regardless of source-map order; selected identity survives passive reorder. No false replacement selection on PID reuse.                                                |
| Bursty hydration plus keyboard/mouse input              | No empty process frame after a valid snapshot; no unwanted scroll reset. Proposed target: p95 input-to-writer completion below 50 ms and no regression above 10% versus the same fixture baseline.                      |
| Slow consumer and repeated open/close                   | At most one unpublished latest snapshot, bounded worker count, deterministic gate/close acknowledgement; injected spawn/poison/panic failures visible. Idle-worker shutdown target below 100 ms in deterministic tests. |
| Narrow and wide terminals                               | Column starts remain stable across changing values at fixed width; selected-row target matches the rendered identity. Resize and Unicode fixtures remain clipped.                                                       |

The numeric latency targets are proposed gates, not achieved results or claims about BTOP. Whole-machine CPU percentages and screenshot smoothness remain unmeasured. No live Thegn application was restarted or signalled. A private BTOP process was launched solely for a Muse layout capture; no process actions or before/after performance benchmark were run.
