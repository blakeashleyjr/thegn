# Launcher, trust, and fallback evidence

Audit date: 2026-10-13. Source baseline: `38e09ded78652c6cf56b0e3a7b6a7c16d18dcd95`.

This is an audit/design artifact, with no production or API changes. All source reads and this artifact were made in the isolated launcher audit worktree. Findings below distinguish source-confirmed behavior from runtime-confirmed behavior. Runtime canary/backend tests belong to the accompanying runtime evidence; this file does not claim real-platform validation for macOS, Windows, providers, or unavailable backends.

## Severity-ranked launcher findings

### L1 — High: repository environment selection can undo the sandbox clamp

**Affected paths:** worktree shells, configured interactive agents/tools, daemon agent/tool opens, native provider panes, and any consumer of `Config::resolve_env` without a stronger explicit selection.

**Evidence:** `config.rs:7194` reads checked-in top-level `env` directly; `config_resolve.rs:1283` chooses that name ahead of the trusted default; `config_resolve.rs:1317` then applies the globally defined named environment's sandbox overlay without clamping, after resolving/clamping the repository sandbox. The function documentation at `config_resolve.rs:1185` explicitly describes this order. The repo trust engine forbids a repo `sandbox.backend`/`backend_chain` and can only tighten profile/network/floor (`config_resolve.rs:448`, `:531`, `:540`, `:570`), but the separate name-selection route bypasses those restrictions. No trust request is emitted for selecting the named environment.

**Controlled reproduction recipe:** create a synthetic repository containing `.thegn.toml` with `env = "hostdev"` and `[sandbox] profile = "sealed"; network = "none"`. In a synthetic user `Config`, use a sealed global profile, network none, isolation floor shared-kernel/fail, and define `[env.hostdev.sandbox] backend = "none"; profile = "open"; network = "host"; isolation_floor = "off"`. Call `resolve_environment` with `selected = None` and `Approvals::deny_all()`. The clamped base is sealed/none, but the resulting environment is hostdev/none/open/host/off. This is a policy-resolution reproduction; it requires no execution of untrusted code or external traffic. Runtime agent was asked to execute the core-only reproduction using its offline build.

**Impact and limits:** an untrusted checkout can select an existing user-owned weaker environment, run on the host, widen egress, or select a remote environment carrying credentials. The repository cannot invent an environment; the weaker named environment must already exist and an explicit DB/workspace selection must not override it. Global ownership of a definition does not establish authorization for every repository to select it.

**Design requirement:** distinguish user-owned environment selection from repository hints. Gate any repo selection that changes placement or broadens the effective global policy; apply repository narrowing after the selected user environment. Retain a monotonic global security ceiling and an explicit user-owned per-repo grant.

### L2 — High: local test/build/gate execution remains outside pane sandbox policy

**Affected paths:** Tests panel runs; command-based discovery; pipeline validation through the same task runner; merge gate commands and artifact regeneration. This applies even when the worktree's agent pane is sealed and network-disabled.

**Evidence:** `task.rs:712` forwards the task command to `run_capped`; `task.rs:173` composes host shell `-c`; `task.rs:219` routes local locations to `build_capped_command` over a resource-cap wrapper. `task.rs:196` builds a host `Command` with inherited environment, removes only Git routing variables, and optionally sets an isolated cargo target. No sandbox configuration/spec, trust approvals, home gate, isolation admission, or network control participates. `task.rs:928` uses that same route for command-based discovery at `:996`; cargo discovery is manifest-only metadata (`:979`), and source-scan ecosystems use an in-process scan (`:943`), so those cases should not be misdescribed as compiling test code. Test runs do execute repository tests and build scripts. Entry points include `run.rs:5227`, `:5252`, `:19710`, `:20241`.

Merge gate `integrate_gate.rs:874` wraps a host shell only in CPU/resource limits, inherits the launcher environment, and removes Git routing variables at `:887`. `integrate.rs:651` similarly runs regeneration through host `sh -c` with no environment clearing. The private scratch checkout and identity/inode protections surrounding these commands protect integration correctness; they do not confine arbitrary commands or build scripts.

**Impact and limits:** project scripts, tests, dependency build scripts, or prompt-induced edits can read/write host files, inherit host credentials, and access host network when run through these UI/background paths. User ownership of the task/gate command does not make the code it executes trusted. These runners visibly document host execution (`config.rs:2088`, `task.rs:212`), but cannot fulfill a cross-launcher sandbox security policy.

**Safe reproduction:** use a synthetic user-configured task/gate invoking a script in a synthetic repo that reads a sibling/home canary and writes a sibling output. Do not pass real environment credentials. Source evidence establishes the route; no host task/gate execution was performed in this sub-audit.

**Design requirement:** all code-executing test/build/gate/validation work must resolve and enter the same durable workspace and policy as the corresponding untrusted agent. Resource caps, process groups, and scratch Git identity must remain additional controls.

### L3 — High: queue agents default to credentialed host execution and opt-in resolution drops per-repo policy

**Affected paths:** merge fixing agents, PR CI/conflict/review agents, CI autofix, review handoff and review-task handoff. Unix platforms implement the shared runner; non-Unix dispatch is held (`agent_run.rs:31`, `:1020`).

**Evidence:** PR queue defaults are `agent_sandbox = false`, floor off, miss degrade (`config_pr_queue.rs:152`); merge queue has the same posture (`config.rs:1077`). `agent_run.rs:193` immediately returns `Run(None)` when the queue switch is off. The runner then uses the host login shell (`agent_run.rs:286`) and only clears environment when `credential_free` is true (`:309`). Queue call sites set it false: `pr_driver.rs:648`, `merge_driver.rs:751`, `ci_autofix.rs:382`, `review_handoff_headless.rs:164`, `review_task_handoff.rs:190`. They consume untrusted branch/CI/review content.

When enabled, `agent_floor_gate` constructs a local Git location and resolves **`full.sandbox` directly** (`agent_run.rs:196`, `:203`), instead of effective repo/profile/named-env policy with approvals. This drops repo `network = "none"`, strengthened repo floors, trusted workspace mounts, profile overlays, devcontainer policy, and selected execution environment. The separate queue floor is passed to `agent_task_gate` at `:221`; the global sandbox floor itself is not admitted there. A demanded queue floor with `agent_sandbox = false` is also ignored by the early return. This is distinct from the interactive launcher's final admission.

**Impact and limits:** enabling an unattended workflow can give repository code or prompt-controlled shell actions ambient host authority despite strong global pane or repo settings. Opt-in agents can execute with wider egress or wrong placement than the same worktree's interactive pane. Queue enablement/agent command itself is user-owned, so this is a dangerous default and cross-launcher contract inconsistency rather than a repo-only way to enable the queue.

**Positive controls:** the opt-in resolver refuses unavailable sealed confinement (`agent_run.rs:207`), checks the home gate (`:216`), provisions and preflights before dispatch (`:226`), and holds requested VPN because attachment is unsupported (`:160`). Entry errors refuse the run (`:287`). Bounded execution owns groups/jobs, timeout, drain and reap (`:330`). Those controls do not cure the default host path or resolution inconsistency.

**Design requirement:** make unattended tasks follow the same resolved execution policy with deny-by-default credentials and fail-closed admission. Keep an explicit user-owned host mode for trusted jobs; do not infer host authorization from an unrelated queue enable flag.

### L4 — High: secure terminal requests can fall back to a host without final floor admission

**Affected paths:** standalone/local terminal tabs using an optional sandbox backend; separate from worktree panes.

**Evidence:** `panes.rs:195` builds terminal specs separately. An unknown backend, absent HOME, or resolver returning none produces `Ok(None)` for profiles that do not hide home (`panes.rs:329`, `:336`, `:346`). `terminal_launch_spec` converts that result immediately to a host shell with no warning and `degraded = false` (`panes.rs:215`). Neither this branch nor the bottom host branch at `:269` calls `sandbox_admission::admit`. Core `resolve_placed_with` checks enabled, picks a backend, and returns none on a local host backend (`sandbox.rs:1025`); it does not enforce isolation floors. A requested hardened terminal with a shared-kernel/fail global floor can therefore become a host shell if resolution fails. A resolved weaker backend likewise receives only the home gate before entry (`panes.rs:366`).

**Impact and limits:** terminal tabs do not honor the same fail-closed isolation-floor contract as worktree panes. Sealed terminals have explicit refusal paths (`panes.rs:322`, `:353`, `:366`) and a HOME-anchored sealed terminal generally refuses wholesale home exposure. Remote ssh/mosh terminals intentionally run the remote client on the host and need a distinct user-trusted transport contract. Selecting host/none intentionally is not the missing-runtime case.

**Design requirement:** require final effective-policy admission on every terminal outcome and preserve explicit-backend intent. Unsupported controls must be surfaced/refused before spawning; label reconciliation alone is insufficient.

### L5 — High: provider-native execution forwards credentials without proving configured egress/containment controls

**Affected paths:** native API agent/shell provider panes (`native_shell_exec`/`native_agent_exec`) and remote-managed placement floor handling.

**Evidence:** `agent.rs:1638` resolves environment with deny-all repo approvals (`:1651`), obtains a provider (`:1671`), and returns `NativeShell` (`:1720`). It never creates/admit/preflights a `SandboxSpec`; it does not enforce `network`, hostname allow/block lists, home secrecy, nested runtime choice or requested floor. It sends configured passthrough token values into the provider (`:1688`), derives `NIX_CONFIG` from a GitHub token (`:1698`), and prefixes uploaded account credentials (`:1682`). `sandbox_floor.rs:94` explicitly treats ProviderManaged isolation as outside the ordering and returns `BypassProvider` regardless of requested floor. The API pane may therefore be stronger than the host in some dimensions, but Thegn cannot claim its policy controls were honored without a provider capability contract.

**Impact and limits:** a `network = "none"`/sealed/floor request can be represented in effective config while provider-native code executes under provider defaults with forwarded secrets. No provider runtime canary was performed; provider policies outside this source tree may impose independent limits. This is a source-confirmed lack of Thegn enforcement, not an asserted provider escape.

**Design requirement:** adapters must report their enforced capability set and immutable effective-policy identity. Admit only backends capable of honoring the request. Provider-native routes must use the same policy decision as CLI/OCI routes or explicitly refuse unsupported constraints.

## Interactive launcher trace and existing protections

The worktree command path is shared: interactive launch, daemon agent/tool open (`daemon/agent_open.rs:83`, `:217`), and the off-loop worktree launcher (`handlers/worktree_launch.rs:271`) reach `launch_spec_full` (`agent.rs:3489`). It derives canonical repo root and DB-selected environment (`:3526`), honors a deliberate saved backend override (`:3542`), then calls `prepare_sandbox_env` (`:3549`). Configured tools and agents resolve through the same command function (`agent.rs:52`, `:3211`); a tool drawer does not overwrite the remembered agent (`:3510`).

`prepare_sandbox_env` resolves persisted trust approvals and devcontainer input (`agent.rs:305`; `handlers/repo_trust.rs:85`), admits configured volume sources before provider/resolver effects (`agent.rs:441`), walks exact candidates (`:636`), prevents explicit-backend drift (`:683`), performs final source admission (`:723`), floor comparison (`:728`), home gate (`:758`), Compose policy refusal (`:766`), and ensure/preflight with VPN rollback (`:793`). Explicit runtime failures return errors (`:826`). It refuses exhausted sealed launches (`:885`) and missing explicit containment except for a local auto chain which actually names host (`:903`). Final host fallback is compared to the isolation floor (`:981`) and `on_missing = fail` refuses (`:997`). Unsupported hardening only warns (`:780`) rather than being a blanket capability refusal.

This materially narrows the initial plan's claim that all fallback silently reaches host: interactive explicit backend requests now refuse; sealed requests refuse; non-local placement/provider failures refuse unless an explicit allowed host policy exists (`agent.rs:1823`). The default local auto chain still includes `host` (`config_defaults.rs:40`), default floor is off/miss-degrade, and missing behavior is warn (`config.rs:4425`). A runtime-less default installation can intentionally reach host under its default configuration. `compose_spec` labels actual local argv using `sandbox_truth::reconcile` (`agent.rs:3343`); errors entering a sandbox propagate (`:3327`).

**Post-admission additions:** after sandbox ensure/preflight, `launch_spec_full` folds environment bundles and profile credentials (`agent.rs:3642`), build-cache mounts (`:3686`), toolchain activation (`:3720`), provider configuration homes RW (`:3758`) and compiler cache (`:3769`). `bundle.rs:66` appends mounts/overrides without checking the sealed deny list. Agent provider-auth directories are explicitly allowed even on sealed launches (`agent.rs:3648`). These are user-owned grants, but final effective filesystem authority must include them; treating only the pre-ensure spec as final misses this expansion. The core resolver's configured mount deny list (`sandbox.rs:1204`) does not automatically cover every later contributor. Mount changes after persistent OCI creation also warrant runtime verification for actual application/recreation. No late-mount escape is claimed here without backend-specific reproduction.

## Filesystem and credential defaults relevant to launch

Default config is enabled/auto/hardened/NAT, auto caches enabled, credentials including GH_TOKEN/GITHUB_TOKEN/ANTHROPIC_API_KEY forwarded if present, and mounts `~/.gitconfig:ro`, `~/.gnupg:rw` (`config.rs:4366`). With same-ABI OCI or bwrap and auto caches, resolver injects host toolchain and home substrate (`sandbox.rs:1112`). Hardened home is read-only (`:1115`), protecting integrity but permitting reads; linked-worktree Git common directory is writable (`:1045`), with only shared config pinned read-only (`:1068`). Writable hooks/refs/objects/per-worktree config are still host-shared. Secret-manager SSH key targets are explicitly mounted for non-sealed toolchain injection (`:1235`).

Sealed creates a home-hiding marker and drops configured credential paths (`sandbox.rs:1123`, `:1204`), suppresses SSH agent passthrough (`:1249`), but is not an unconditional credential-free mode: other configured token names remain in passthrough (`:1255`) and interactive provider-auth homes are intentionally carved later. The durable private-copy design must define explicit credential delegation, prohibit mutable shared Git metadata, and enumerate caches as shared untrusted data.

## Repo/global policy and trusted host exceptions

The repository sandbox engine exhaustively classifies every overlay field (`config_resolve.rs:393`). It forbids backend, chain, Compose, env passthrough, remote routing, VPN and personal HOME; only allows stronger profile/network/on-missing/floor/on-miss/warm-direnv/file-access; only allows disabling auto caches; intersects hostname allow patterns and unions block lists; gates image/mounts/volumes/scripts/ports/GPU and other additive authority (`config_resolve.rs:434` onward). Empty repo allow or an empty allowed intersection is encoded as `network_block += "*"` (`:663`, `:692`). This is a DNS universal block, not packet-level network none. Global empty allow means universe (`:348`); repository empty allow means deny-all DNS, so configuration semantics differ.

`resolve_repo_sandbox` folds global, active-profile overlay, clamped repo overlay, trusted workspace mounts and tilde expansion (`config_resolve.rs:1136`). DB failure denies approvals (`handlers/repo_trust.rs:48`). Trusted environment selection and zone application also matter; native/provider and queue bypasses above need separate coverage.

Lifecycle hooks run host `sh -lc` under resource caps and process-group/job ownership (`hook_run.rs:174`). They clear the environment to a safe base/context (`:191`) and filter credential-shaped names (`:204`), but retain filesystem/network host authority. Repo hooks and legacy prepare are omitted until their exact event request is approved (`hooks.rs:358`); changed commands require a new canonical approval. Global/workspace hooks are user-owned and ungated (`hooks.rs:309`). Lifecycle resolves DB trust fail-closed (`worktree_lifecycle.rs:281`) and loads repo hooks separately (`:300`). This meets the audit assumption only if approval explicitly conveys **host authority**, including mutable repo script dependencies. Approval of a shell string cannot freeze the script it calls.

Devcontainer's single lifecycle category gates initialize/onCreate/updateContent/postCreate/postStart/postAttach (`devcontainer_overlay.rs:717`) and prominently names initialize execution ON HOST (`:730`). Initialize maps to host prepare (`:596`), while postStart/postAttach become pane init scripts (`:562`) and one-time steps become provisioner steps (`:216`). The optional raw CLI provider is eligible only when no pending/unapplied/unknown execution-affecting fields remain (`handlers/repo_trust.rs:214`) and only for auto/Open/NAT/no-filter/no-audit/no-VPN/floor-off with no OCI endpoint/runtime override or CPU/memory ceiling (`devcontainer_provider.rs:116`). The CLI receives an immutable trusted config snapshot and cleared host environment (`devcontainer_provider.rs:542`), and stale sessions refuse entry instead of falling to host (`agent.rs:3192`, `:3314`). Image/build/Compose references, mutable local build contexts and referenced scripts still need trust and backend-native confinement; trust of JSON bytes does not freeze all their dependencies.

Mise tool install requires explicit current config-set approval (`mise_provider.rs:668`) and clears env (`:705`) but is a trusted host execution exception. Cold ordinary launch reads cached activation and does not automatically install (`agent.rs:3689`). Keep these exception semantics explicit rather than silently equating every toolchain operation to the pane sandbox.

## Autopilot is materially stricter, with a shared-Git residual limit

Autopilot always calls `sealed_autopilot_sandbox` before worker dispatch (`autopilot_driver.rs:289`), ensures/preflights (`:296`), and uses `credential_free = true` (`:322`). The helper derives deny-all-approved repo policy, forces Sealed/Worktree, clears mounts/volumes/pass-env/caches/devshell/Nix/prepare/init/ports/GPU/Compose/hostname rules/VPN (`:652`), applies the home gate (`:691`), rejects systemd, WSL and both Windows native entries (`:722`), clears overrides and blocks credential names (`:703`), and sets network none (`:718`). The generic runner clears inherited credentials (`agent_run.rs:309`, `:991`) and refuses entry errors (`:287`). These are source-confirmed improvements over ordinary queue defaults.

The generated worktree and writable common Git mounts remain (`sandbox.rs:1053`), so an issue worker can change shared refs/objects/hooks rather than just returned files. Image/build source may still be user configured. Backend network-none enforcement must be validated in each platform runtime; a Sealed label is not proof. Adopt the independent private repository for autopilot first and keep sandbox refs/commits private.

## Verification status and scope limits

Source searches covered the principal pane, daemon, terminal, native provider, queue, autopilot, hook, devcontainer, test/discovery, gate and toolchain routes. No real credentials were inspected or test traffic sent externally. An offline `thegn-core --lib` focused test build was started, then stopped to avoid duplicating the runtime agent's core compilation. No passed-test claim is based on that incomplete build. The runtime agent owns executable policy/canary probes and records unavailable backend reasons separately. Future security acceptance should exercise every listed route with synthetic home/sibling/common-Git/cache/credential/system canaries and controlled loopback egress, and require identical effective policy or an explicit refusal.
