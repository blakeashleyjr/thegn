## Runtime failure diagnosis and platform basis

The first actual service run exposed an exit-notice timeout even though non-consuming waitid subsequently confirmed exit. An independent Python SIGCHLD handler received its owned fixture's exit normally. Socket `send`, however, returned `EPERM`, while a direct descriptor write succeeded. `/tmp/thegn-resident-socket-wake-diagnostic.rs` reproduces `PermissionDenied` from Rust `UnixStream::write`. Locally cached Tokio's signal handler uses this primitive for its wake byte and discards its error. This explains the direct Tokio Signal::recv timeout here; it is not a general upstream Tokio defect claim.

The [Linux pidfd_open manual](https://man7.org/linux/man-pages/man2/pidfd_open.2.html) documents poll/epoll exit readiness, close-on-exec descriptors, and the preconditions for opening an exited child safely: no ignored SIGCHLD, no SA_NOCLDWAIT, and no competing reaper. The implementation checks disposition before spawn and retains the unreaped child. No periodic idle timer or unrelated-process scan is introduced.

Windows uses dedicated synchronous-I/O workers retained until confirmed completion. ERROR_NOT_FOUND from CancelSynchronousIo is inconclusive, so closing retries against the exact thread handle. Microsoft documents cancellation races and the need to observe completion: [cancellation guidance](https://learn.microsoft.com/en-us/windows/win32/fileio/canceling-pending-i-o-operations), [CancelSynchronousIo contract](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelsynchronousio). A pre-syscall barrier fixture exists; it has not run natively here.
