**Confirmed telemetry defects and limitations**

1. **Render/flush/input metrics normally stop before terminal output completes.** In [run.rs:13322](../../crates/thegn-host/src/run.rs#L13322), the normal renderer encodes bytes and calls `writer.submit_frame`; `loop_perf.flush` immediately follows, and `loop_perf.render` consumes the input stamp at [run.rs:13390](../../crates/thegn-host/src/run.rs#L13390). [frame_writer.rs:1](../../crates/thegn-host/src/frame_writer.rs#L1) explicitly sends blocking output to another thread. These metrics measure composition/encoding/submission and dispatch-to-submission, not physical flush or end-to-end keypress-to-display. The synchronous writer/debug renderer exceptions exist; the captured startup does not independently attest their environment overrides. Rename the metrics or record writer queue wait and completed-write time with frame IDs. Even write completion is not terminal paint acknowledgement.

2. **The reported idle ratio omits synchronous input dispatch.** [run.rs:7952](../../crates/thegn-host/src/run.rs#L7952) resets `iter_t0` at the start of an iteration; [run.rs:13457](../../crates/thegn-host/src/run.rs#L13457) accumulates busy time before polling and the large key/mouse/paste handlers. Their work then executes, and the next iteration resets the timer again. Thus `idle_ratio` omits more than off-thread producer CPU: handler work itself is excluded. It is also wall-time accounting, not CPU utilization. Instrument dispatch separately and subtract only the actual blocking wait from loop wall time. Validate with an isolated synthetic handler that consumes a known duration before the next frame.

3. **Input latency is a single dispatch stamp consumed by the next frame.** Key, mouse, and paste events assign `input_at` after event retrieval ([run.rs:13476](../../crates/thegn-host/src/run.rs#L13476), [run.rs:14754](../../crates/thegn-host/src/run.rs#L14754), [run.rs:23176](../../crates/thegn-host/src/run.rs#L23176)); any later event can overwrite an unconsumed stamp. [perf.rs:727](../../crates/thegn-host/src/perf.rs#L727) clears it on the next render. Reader/queue delay is excluded, and no causal check guarantees that frame contains the pane application's response. An input that does not require redraw can instead wait for unrelated damage. The 16:35:16 bucket is a valid long dispatch-to-next-submission observation, but it cannot identify a specific restored pane or prove its displayed response took that duration. Add event-receipt timestamps, earliest-pending/coalescing semantics, sample counts, and distinct application-action versus pane-response measurements.

4. **Hydration CPU is an incomplete ledger.** [perf.rs:201](../../crates/thegn-host/src/perf.rs#L201) uses the calling thread's CPU clock. [hydrate.rs:3585](../../crates/thegn-host/src/hydrate.rs#L3585) wraps only the initial `build_model`, after database open/heal waiting; the later commit-refresh rebuild is outside that guard. `build_panel` fans out to scoped child threads ([hydrate.rs:2793](../../crates/thegn-host/src/hydrate.rs#L2793)), whose CPU is excluded by a parent thread clock, as are Git child processes. Aggregate CPU at guard completion can cross a rollup boundary. Treat the reported CPU as attributed work, not total hydration/process CPU; add child-thread/subprocess measurements and publish elapsed interval and invocation counts.

All of `perf.rs`, `frame_writer.rs`, `hydrate_tuning.rs`, and `probe.rs` are unchanged between the two audited build commits. These coverage limitations are pre-existing in this range.

**Where to investigate performance next**

Repeated hydration is a concrete candidate. The primary capture contains **1,249 `model hydrated` records, median 1,062 ms wall time, maximum 2,185 ms**. These are model-build calls, not necessarily distinct periodic refreshes. The nominal safety ticker is five seconds ([hydrate_tuning.rs:14](../../crates/thegn-host/src/hydrate_tuning.rs#L14)), while each complete build loads layered configuration, enumerates workspace/worktree/sidebar state, collects status, and builds the active panel ([hydrate.rs:2493](../../crates/thegn-host/src/hydrate.rs#L2493)). Suppressing an unchanged result does not avoid constructing it. Instrument config parsing, environment resolution, sidebar DB work, Git fan-out, semantic summary, and panel composition independently; then cache unchanged inputs or split lightweight background-glyph refresh from complete model construction. Do not simply lengthen the timer without preserving freshness requirements.

The relevant changed hydration hot path is [hydrate.rs:1699](../../crates/thegn-host/src/hydrate.rs#L1699): commit `fbc1dc96` switched devcontainer status from base repository sandbox resolution to each worktree's effective environment. [handlers/repo_trust.rs:62](../../crates/thegn-host/src/handlers/repo_trust.rs#L62) adds effective-environment DB lookup and complete environment resolution per eligible worktree. This is a correctness fix with plausible added cost, not an established root cause. Compare it using the same copied DB/config and workspace inventory; cache by worktree/environment/config generation if measured material. The remaining hydration changes in the range mainly preserve typed DB failures.

The warning text “render path is recomposing too much” is a hypothesis emitted whenever p50 exceeds a threshold, not a diagnosis supported by a full-frame count. Instrument incremental compose, surface diff, allocation/copy, emulator lock time, and writer submission separately. Also tag periodic resync: every three seconds by default, an otherwise incremental frame can run a whole-screen `full_repaint_changes` path ([run.rs:13157](../../crates/thegn-host/src/run.rs#L13157), [run.rs:13185](../../crates/thegn-host/src/run.rs#L13185)) and still be counted as incremental. This makes resync a testable candidate for sparse tails without claiming it caused these particular events. Pane layout/zoom changes in `bfb1a471` and `27a995ff` merit workload-matched review, but the captured geometry does not isolate their effect.

Background logging also has measurable architecture costs. The host always starts the file tailer ([run.rs:7925](../../crates/thegn-host/src/run.rs#L7925)); it polls once per second and wakes on batches even when Logs is hidden. The hidden panel correctly avoids setting `dirty` ([run.rs:12164](../../crates/thegn-host/src/run.rs#L12164)), so claiming an unconditional hidden-panel render feedback loop would be wrong. When Logs is visible, debug frame records can themselves provoke its next repaint. Consider subscribing/waking only when visible while retaining bounded history.

A separate **confirmed source defect** in that tailer can undermine diagnostics: [provider.rs:47](../../crates/thegn-svc/src/log/provider.rs#L47) opens one file descriptor, seeks to end, and never reopens or checks file identity/truncation. The actual log sink rotates by renaming the active file ([log_trace.rs:679](../../crates/thegn-core/src/log_trace.rs#L679)); the tailer can keep polling the old file and miss the new `thegn.log`. After truncation, its old offset can skip replacement content. This is unchanged across the build range. Add an isolated rotate/recreate/truncate fixture requiring delivery of each appended record exactly once, then reopen on file identity change and reset safely on truncation. No live panel freeze was reproduced in this review.

**Keyboard and channel claims**

The startup capture reports Ghostty 1.3.1, `modify_other_keys=None`, `kitty_keyboard=Some(0)`, and `ctrl_digits=Some(false)`. [termcaps.rs:940](../../crates/thegn-core/src/termcaps.rs#L940) deliberately maps that response to false, and [run.rs:520](../../crates/thegn-host/src/run.rs#L520) deliberately avoids enabling kitty protocol because the pinned parser cannot handle some forms. This confirms the application's negotiation result and supports hiding unsupported quick-jump hints. It is not an independent experiment pressing every Ctrl-digit, nor evidence all keys are broken. Verification should use an isolated parser/probe fixture and terminal matrix, followed by an explicitly arranged interactive test; this review sent no keys.

Stable channel is confirmed by the startup log and [channel_state.rs:38](../../crates/thegn-host/src/channel_state.rs#L38): the compiled default depends on the `dev` feature, while `profiling` alone does not change it; `THEGN_CHANNEL` can override resolution. The captured clamp names providers and trackers. This validates the observed startup policy; it is not a full proof every downstream feature path enforces the clamp. No request to enable experimental features is implied.

Recommended verification order: correct telemetry semantics and coverage; benchmark hydration phases against a copied, fixed workload; replay sustained PTY output at captured geometry with resync tags; add log-rotation coverage; then compare build commits under identical conditions. Preserve the original audit's distinction between observed latency and causal attribution.
