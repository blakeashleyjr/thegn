# THE-429 investigation — native dispatch row 484

## Verdict

**Plan-ready for primary review; implementation not performed.** The bug remains
on the exact branch `blake/the-429-stop-checkout-hooks-from-executing-branch-controlled-code-or`
at `46f8587a` (parent/base `0be575ce`). No production source files were changed.

The smallest complete source repair is to remove the automatic `post-checkout`
installer and its branch-resolved invocation. Keep the existing generated
pre-commit/pre-merge/pre-push developer gates supplied by `preCommit.shellHook`,
but make linked-worktree config seeding an explicit, documented developer action
if it is still desired. Do not replace this with a generic hook trust framework.

There is one deployment caveat: this checkout's shared Git hooks directory
currently contains an old installed copy of the vulnerable hook. It is an exact
byte match for the tracked payload. I did not remove it. A primary-approved
implementation must either provide a narrowly scoped, no-follow migration for
that exact legacy artifact or document an explicit external cleanup procedure;
it must never clean unknown hooks, global/shared `core.hooksPath` targets, or
non-regular path types.

## Evidence that the bug remains

- `flake.nix:456-466` runs `hookExtras` for every non-CI dev-shell entry and
  exports `PREK_ALLOW_NO_CONFIG`.
- `flake.nix:468-480` reads `core.hooksPath`, falls back to
  `$(git rev-parse --git-common-dir)/hooks`, and unconditionally runs
  `install -m 0755 test/git-hooks/post-checkout.sh "$hooks_dir/post-checkout"`
  whenever the directory and tracked source exist. There is no ownership,
  collision, symlink/no-follow, repository-identity, or atomic-generation
  check.
- `flake.nix:773-776` deliberately runs this block after
  `preCommit.shellHook`, because the latter rewrites `core.hooksPath`. Thus the
  installer targets the effective shared path rather than only the current
  checkout.
- `test/git-hooks/post-checkout.sh:21-31` executes
  `sh test/git-hooks/heal-worktree.sh` from the checkout's current working
  directory. The `test -f` path is resolved after checkout, so a branch can
  replace that script and control the executed bytes.
- `test/git-hooks/post-checkout.sh:33-48` operates in the newly checked-out
  worktree. It only early-returns for a live symlink, then uses `ln -sf` on
  `.pre-commit-config.yaml`; a regular file, directory, valid foreign symlink,
  or dangling symlink can be replaced. Failures are mostly silent.
- `test/git-hooks/heal-worktree.sh:73-112` rewrites the shared
  `.git/config` with a predictable temporary name and `cat > "$cfg"`; this is
  not the generation-fenced/no-follow repair required by THE-371.
- Read-only environment evidence: `git config --local --get core.hooksPath`
  resolves to `/home/blake/code/thegn/.git/hooks`, and its
  `post-checkout` is a regular mode-0755 file, uid/gid 1000/1000, 2614 bytes,
  SHA-256
  `90b85945a3c30c3a9aa806f87fe9585e9ce660e450672e3e5e24b40dca140365`.
  The tracked `test/git-hooks/post-checkout.sh` has the same digest. This
  confirms a live legacy installation; no external file was changed.

## Production call paths and prerequisites

### Installation

1. A developer enters the default Nix dev shell with `CI` unset.
2. `preCommit.shellHook` runs first and establishes the generated hook setup
   and effective `core.hooksPath`.
3. `hookExtras` then resolves that effective path and copies the current
   checkout's `test/git-hooks/post-checkout.sh` into its `post-checkout` slot.
   A global/shared path is accepted by the same code.

### Invocation on checkout/worktree creation

- `thegn wt new` reaches `crates/thegn-host/src/cmd/wt.rs:252-287`, then
  `thegn_core::worktree::add_checked_with_state`.
- The core add path at `crates/thegn-core/src/worktree.rs:238-268` runs ordinary
  `git worktree add --quiet -b ...`; `thegn_core::util::git_cmd` only scrubs
  inherited Git environment variables and does not disable hooks.
- The service seam's CLI implementation at
  `crates/thegn-svc/src/git/mod.rs:1343-1346` likewise runs ordinary
  `git worktree add`; its `run_root` wrapper at `:1232-1239` does not set
  `core.hooksPath=/dev/null`.
- The control/daemon path at
  `crates/thegn-host/src/daemon/service.rs:1781-1855` resolves the repo,
  calls `add_checked_with_state`, and therefore has the same Git hook behavior.
  Session forking enters this path through
  `crates/thegn-host/src/cmd/session_fork.rs:47-55`.
- Git invokes `post-checkout` after `git worktree add` and ordinary branch
  checkout with the new worktree as cwd. The hook consequently resolves
  `test/git-hooks/heal-worktree.sh` and `.pre-commit-config.yaml` from the
  selected branch/worktree.

### Conditions needed for exploitation

The attacker needs a developer to have entered a non-CI dev shell that installed
the hook into the effective path, followed by checkout or worktree creation of a
branch containing hostile replacements. No sandbox admission, Thegn process,
pre-commit approval, or agent launch is required. The hook is a Git checkout
hook, so `--no-verify` for commit hooks is not a mitigation.

## Failure cases to preserve in the implementation plan

1. A hostile branch replaces `test/git-hooks/post-checkout.sh` and/or
   `heal-worktree.sh`; checkout/worktree creation must not execute its bytes or
   write a sentinel.
2. Dev-shell entry must not overwrite an existing executable/regular foreign
   `post-checkout` hook.
3. It must not touch a repository with a global/shared `core.hooksPath` merely
   because that path is effective.
4. A regular file, directory, valid symlink, dangling symlink, and FIFO at the
   candidate hook or `.pre-commit-config.yaml` path must be preserved unless a
   positively owned, exact legacy artifact is being migrated.
5. A concurrent shell entry/checkout or replacement between inspection and
   cleanup must fail closed; no path-following `install`, `ln -sf`, or blind
   unlink is acceptable.
6. An interrupted update must not leave a half-written hook or config target.
7. Multiple linked worktrees must not share branch-controlled hook execution or
   destroy per-worktree user configuration.
8. Existing generated pre-commit/pre-merge/pre-push developer hooks must remain
   available where their config is present. Documentation must say these are
   optional local gates, not CI/merge security authority; CI and explicit merge
   gates remain authoritative.
9. The existing `just heal-git` path at `justfile:682-692` is an explicit
   developer repair path but still calls the shell healer. It must not be
   confused with a safe checkout-hook boundary; shared config repair belongs to
   THE-371's generation-fenced primitive.

## Smallest complete fix proposed for primary greenlight

1. Remove the `hookExtras` block that installs `post-checkout`; retain only the
   environment behavior needed by existing optional generated gates, with
   comments/docs explaining that no checkout hook is installed or trusted.
2. Remove the automatic `post-checkout` payload and its branch-controlled
   healer invocation from the supported workflow. Do not add a multiplexer,
   trust database, or new implicit setup path.
3. Preserve the explicit `preCommit` configuration and pre-push commands. Make
   the linked-worktree config-seeding limitation explicit: users who want local
   prek hooks in another worktree must perform a repository-scoped setup after
   reviewing that worktree, or use the documented explicit `just`/CI gates.
4. Handle legacy installations narrowly. Preferred implementation: a trusted,
   no-follow, repository-scoped check may remove only the exact known legacy
   digest from a verified local hooks directory owned by the user/repository.
   It must refuse custom/global/shared paths, symlinks, directories, FIFOs,
   foreign bytes, ownership mismatches, and races, and report every refusal.
   If that primitive is not available without pulling in THE-371, do not guess:
   provide a clear explicit cleanup command/procedure and state that external
   cleanup is required. Never overwrite or delete an unknown hook.
5. Keep shared Git-config self-healing on THE-371's scope; do not make the
   branch-resolved shell healer a replacement repair mechanism.
6. Update relevant comments/documentation and `just heal-git` wording so the
   distinction between explicit developer repair, optional local hooks, and
   trusted CI/merge enforcement is unambiguous.
