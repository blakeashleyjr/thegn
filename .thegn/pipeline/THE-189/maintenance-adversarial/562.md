## Findings

### R-001 — high: generation fences still have a check-then-commit race

Acceptance criteria affected: old ticker tasks cannot deliver stale-generation
results; disable during in-flight work. Primary revision F-002 explicitly
requires the check-then-publish window to be closed at the publication/cache
boundary.

`generation_is_current` is an independent atomic load, not a commit boundary.
The configuration reload can increment the generation after the load and
before the side effect. Concrete paths include:

- weather checks at `crates/thegn-host/src/hydrate_weather.rs:139-144`, then
  writes the cache and delivers;
- CI checks at `crates/thegn-host/src/ci_refresh.rs:259-268`, while log writes
  continue at `:373-376` and the error path at `:274-282` updates fetch health
  without any generation check;
- calendar checks at `crates/thegn-host/src/hydrate_calendar.rs:477-497`, but
  `put_calendar_events` / `replace_calendar_account` can commit after a reload
  (and the incremental path can leave a partial stale write);
- LOC checks at `crates/thegn-host/src/measure/loc.rs:139-143` before the DB
  commit;
- usage writes/prunes at `crates/thegn-host/src/actions.rs:714-719`, and can
  raise proxy budget notifications at `:574-580` after the earlier check;
- PR cache/review-cache writes at
  `crates/thegn-host/src/hydrate.rs:3515-3563`.

The same interleaving exists at reminder notification raising:
`crates/thegn-host/src/hydrate_calendar.rs:717-722` checks and then calls the
notifier while the event-loop thread can reload concurrently. A stale provider
result can therefore mutate cache, fetch-health/connectivity state, or notify
after the schedule has been replaced even though its eventual envelope is
dropped.

Required correction: make the generation check and the publication/cache
commit one serialized boundary (or use an equivalent commit token/version
guard understood by the cache writer); a second standalone load after the
write is not sufficient. Add deterministic blocked-commit tests for each
cache-writing class and reminder notification.

### R-002 — high: scheduled child refreshes bypass the schedule fence

Acceptance criteria affected: old ticker tasks cannot deliver stale-generation
results; CI/PR in-flight work. The outer `RefreshKind::Scheduled` envelope
only fences admission to the event loop; it does not automatically fence work
spawned from an admitted request.

The scheduled CI path passes its generation only to the run-history refresh at
`crates/thegn-host/src/ci_refresh.rs:116-122`. If a live CI drill is open,
`on_ci_tick` immediately starts `spawn_ci_detail` without that generation at
`:123-124`. `spawn_ci_detail` has no fence, writes CI log cache entries at
`crates/thegn-host/src/actions.rs:393-398`, and sends an untagged
`CiDetail` result at `:411-418`. A slow detail request from the old schedule
can consequently write and render after a successful reload.

The scheduled PR path has the same secondary path: after the fenced PR cache
refresh, `run.rs:12197-12205` calls `refetch_pr_view` without the schedule
generation. Its fetch writes the review cache and emits an untagged model wake
at `crates/thegn-host/src/actions.rs:957-973`. The view-local generation
protects one overlay instance, but does not protect that cache write from an
old scheduled request.

Required correction: carry an optional schedule fence through these scheduled
child jobs and check it at both cache commit and delivery, while leaving
manual/user-forced detail and view refreshes untagged as required by F-003.
Add a reload-mid-detail regression for CI and the PR review cache path.

### R-003 — medium: the effective projection compares raw LOC TTLs

Acceptance criterion affected: unchanged schedules are not restarted
unnecessarily.

`ScheduleConfig` stores raw `cfg.loc.scan_interval_secs` at
`crates/thegn-host/src/hydrate_schedule.rs:55,79`, but the worker actually
uses `scan_sched::pump_slots`, which divides by four and floors at the LOC
pump floor (`hydrate_refresh_ticker.rs:297-298`,
`crates/thegn-core/src/scan_sched.rs:117-130`). For example, LOC TTLs `1` and
`2` both select the same effective 60-second pump, yet
`ScheduleConfig::from_config` differs, so `ScheduleOwner::reconfigure` bumps
the generation and re-arms the slot unnecessarily.

The test-only regression added at
`crates/thegn-host/src/hydrate_schedule.rs:372-389` asserts the required
equality. It was not executed because Cargo/test execution is owned by the
primary; as written against the current projection it should fail until the
effective cadence is stored/compared.

The same raw-versus-effective shape should be audited for disk and auto-fetch
fields in `ScheduleConfig` (`:51-55,72-75`) because their worker helpers also
floor cadence values.

### R-004 — medium: required live-owner/event-loop coverage remains missing

Acceptance criterion affected: fake-time coverage for all ticker classes,
rapid reloads, disable during in-flight work, stale result arrival, and
shutdown.

The tests that claim this coverage are mostly model tests:

- `hydrate_schedule.rs:294-314` drives a local `FakeSlot`, not the production
  worker;
- `:317-347` only stores/loads an `AtomicU64` and tests the pure fence helper;
- the production-thread live replacement test in
  `hydrate_refresh_ticker_tests.rs:348-413` exercises only CI and does not
  drive the event-loop envelope or a provider/cache publisher;
- the all-class fixture at `:244-328` tests startup cadence and disabled
  startup state, not live replacement of all seven classes.

Missing regressions include all-seven-class live reconfigure through the real
owner, disable while each class is in flight, stale publication at the commit
boundary, invalid reload retention, scheduled-vs-untagged work after reload,
and stale CI/PR child deliveries. The shutdown join assertion exists in the
CI fixture, but not as part of a full owner/event-loop replacement scenario.
