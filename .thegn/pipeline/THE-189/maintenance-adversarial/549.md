## Findings

### F-001 — stale reminder work both raises and permanently strands a window

Severity: high. Acceptance criteria affected: old ticker work cannot deliver
stale results; disable during in-flight work; shutdown/cancellation semantics.

The reminder worker raises every due reminder at
`crates/thegn-host/src/hydrate_calendar.rs:640-666`, specifically
`:650-656`, before it emits its generation-tagged acknowledgment. On a reload
during that evaluation, `run.rs:11745-11747` drops the old
`RefreshKind::Scheduled` envelope before reaching the
`CalendarReminderResult` arm at `run.rs:11782-11783`. The old reminder can
therefore notify the user after its schedule was replaced, while its
`ReminderCursor.inflight` window is never cleared. Every later
`ReminderCursor::begin` returns `None` (`hydrate_calendar.rs:540-553`), so
reminders stop for the rest of the process.

The existing `abandon` primitive (`hydrate_calendar.rs:556-562`) is not called
when a scheduled result is discarded. The stale-result test required by the
primary plan would expose this immediately.

### F-002 — generation checks do not cancel in-flight work or fence cache publication atomically

Severity: high. Acceptance criteria affected: old ticker tasks are canceled and
cannot deliver stale-generation results; disable during in-flight work; bounded
resource behavior.

`ScheduleOwner::reconfigure` only increments the shared generation and sends a
replacement command (`hydrate_schedule.rs:124-132`); it does not cancel or join
the background operations already launched by the old schedule. The workers
then use check-then-publish races rather than a cancellation-aware publication
boundary:

- Weather checks no generation at all between the provider response and the
  cache write/delivery at `hydrate_weather.rs:136-143`.
- CI checks at `ci_refresh.rs:257-263`, then writes the cache at `:267-269`;
  failed-log fetching similarly checks only before the provider call
  (`ci_refresh.rs:327-330`) and writes logs after a reload can race it
  (`ci_refresh.rs:358-377`).
- PR writes `pr_cache` after the check at `hydrate.rs:3495-3517`, and writes
  review cache after a second check that can become stale during the following
  provider calls (`hydrate.rs:3522-3560`).
- Calendar applies provider pages to the DB without any generation or
  cancellation check in `hydrate_calendar.rs:311-343` and `:390-436`.
- LOC checks before `loc_scan`, but can publish the completed scan after a
  reload at `measure/loc.rs:91-101` and `:115-127`.

Even where the immediate loop message is wrapped and dropped, a stale cache
write can be consumed by a later current-generation hydration and become a
visible stale result. A reload storm also leaves all old provider/network/scan
work running until completion.

### F-003 — coalescing loses scheduled-vs-manual origin

Severity: medium. Acceptance criterion affected: user-forced/event-driven work
must remain untagged and immediate after reload.

The loop records one optional generation per class while draining
`refresh_rx` (`run.rs:11745-11758`) but coalesces scheduled and untagged requests
into the same booleans. If a scheduled `Pr` and an untagged user/filesystem
`Pr` arrive in one drain, the untagged request inherits
`scheduled_pr_generation` when the combined job is launched at
`run.rs:12159-12175`. The same shape affects CI at `:12221-12230`, calendar and
reminders at `:12177-12193`, LOC at `:12248-12255`, and usage/weather at
`:11885-11893` and `:11956-11964`.

If the generation changes while that combined job is in flight, the legitimate
manual result is fenced out with the old scheduled result. This contradicts the
primary plan's explicit user-forced-refresh guard.

### F-004 — replacement commands can grow without a bound during reload storms

Severity: medium. Acceptance criterion affected: rapid reloads and resource
growth.

`RefreshTicker` stores an ordinary `std::sync::mpsc::Sender` and creates an
unbounded `mpsc::channel()` (`hydrate_refresh_ticker.rs:24-42` and
`:75-103). Every reload enqueues a full `Replace` command, while the worker
drains only after its next 500ms wait (`hydrate_refresh_ticker.rs:309-327`).
The drain keeps the last command semantically, but does not bound the queued
allocations. A sustained rapid-reload/config-watcher storm can therefore grow
this queue until the worker catches up. A bounded latest-value command slot or
equivalent coalescing primitive is needed.

### F-005 — required live/in-flight regression coverage is not present

Severity: medium. This is a gate weakness independent of the functional
findings.

The original schedule tests in `hydrate_schedule.rs:190-251` test a local
`FakeSlot`, an `AtomicU64`, and field presence; they do not drive
`ScheduleOwner`, the replacement command, the event-loop envelope, or any
provider/cache publisher. The existing ticker fixture exercises the production
worker arithmetic but not live replacement. This review added one real command
boundary test for CI (`hydrate_refresh_ticker_tests.rs:347-404`) and one
projection-diff test covering every projected slot (`hydrate_schedule.rs:202-231`).

Still missing are the primary-plan cases for all seven classes under live
replacement, A→B→C rapid reloads, disable while in flight, stale result
arrival, invalid reload retention, shutdown/post-shutdown reconfigure,
unchanged worker identity, and the mixed manual/scheduled request guard.
