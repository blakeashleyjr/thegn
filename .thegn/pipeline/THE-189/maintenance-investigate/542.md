## Failure cases and stale-result surfaces

- **Cadence change:** old slot remains active indefinitely; the new interval
  never governs the worker.
- **Disable:** old optional slot continues to wake and dispatch work. Weather,
  usage, and LOC jobs also retain old config snapshots when they are started.
- **Enable:** `current_config` and UI change, but the old `None` slot remains
  absent until restart.
- **Rapid reloads:** there is no single scheduler generation or replacement
  owner. Multiple valid config messages are processed in the loop, but no
  schedule command coalesces them and no stale scheduled result can be rejected.
- **In-flight old work:** usage sends an untagged `RefreshKind::Usage` payload
  from `actions.rs:505-566`; weather sends untagged snapshots from
  `hydrate_weather.rs:47-53,215-231`; calendar periodic sync captures its old
  `CalendarConfig` at `hydrate_calendar.rs:131-153`; CI captures `full.ci` at
  `ci_refresh.rs:129-146`; and LOC captures `LocConfig` at
  `measure/loc.rs:29-68`. Cancellation alone would race these deliveries.
- **Existing model generation is not config generation:** model hydration tags
  results with a worktree/hydration generation at `hydrate.rs:3252-3360` and
  the loop rejects stale worktree generations at `run.rs:9970-9991`, but the
  config reload path does not advance that generation for schedule changes.
- **Invalid reload:** `try_load_layered` returns an error for read/parse/type
  failures (`config.rs:5966-6050`); the watcher sends the error and the loop
  leaves `current_config` untouched while reporting the status. This must remain
  true for the scheduler. Parseable values that are normalized/floored by
  existing config post-processing should continue to use the normalized
  effective projection, not invent a new config key or fallback schedule.
- **Duplicate workers and shutdown:** `spawn_refresh_ticker` discards its
  handle, so there is no explicit join/cancel boundary. A replacement must
  retain one owner, cancel the prior schedule before accepting the next one, and
  stop/join it during host shutdown without creating a second 500ms worker.
- **Immediate thundering refresh:** rebuilding by sending a synthetic refresh
  immediately would make every save fan out to seven providers/scanners. The
  replacement must reset each changed slot to its next future tick and not emit
  an immediate refresh.
- **Idle/waker regression:** a schedule command must not become a periodic
  terminal wake. The worker may keep its existing internal 500ms clock, but only
  a due scheduled event sends on the refresh channel and pulses the waker.

## Smallest complete fix proposal

1. Add a sibling scheduler module, preferably
   `crates/thegn-host/src/hydrate_schedule.rs`, and register it in
   `crates/thegn-host/src/main.rs`. Keep cadence projection, diffing,
   cancellation, generation, fake-clock state, and worker ownership there; do
   not add scheduling logic to `run.rs`.
2. Define a compact effective `ScheduleConfig`/`ScheduleSnapshot` containing
   the existing normalized projections above. Derive it from the loaded config
   using current helpers (`calendar.poll_secs`, `weather.poll_secs`, usage
   effective floor, existing cadence slot helpers). Compare per class. Equal
   projections keep the same worker/schedule; changed projections replace the
   affected logical schedule only. Keep the one shared worker and one owned
   handle rather than spawning one timer per feature.
3. Give the owner a replaceable command boundary (`Replace(snapshot)` and
   `Shutdown`) and a monotonic config generation. A replacement cancels the
   prior schedule state, records the new generation, and re-arms only changed
   slots at their next normal boundary. The worker remains off-loop and pulses
   the waker only for actual refresh messages. Retain and join the handle on
   shutdown; use the THE-193 `StatusScheduler` ownership/shutdown pattern as
   the reviewed reference.
4. Carry the schedule generation with scheduler-originated refresh requests and
   result deliveries. At the loop boundary, discard a request/result whose
   generation is older than the active schedule. Capture the generation when a
   scheduled CI/PR/usage/weather/calendar/LOC operation starts; preserve
   untagged event-driven/user-forced refreshes so this change does not disable
   legitimate on-demand work. For cache-writing workers, check cancellation
   before publishing/re-delivering and fence the loop-facing result; do not
   change provider behavior or cache authority.
5. In `run.rs`, make only the wiring changes needed to create/pass the owner,
   call `reconfigure` after a successful `current_config` replacement, retain
   the scheduler handle, and shut it down. The reload path must process the
   latest effective config without issuing an immediate refresh. The `Err` path
   must not call `reconfigure`, preserving the last effective schedule and its
   existing status message.
6. Keep the existing `hydrate_refresh_ticker.rs` production I/O adapter and
   cadence helpers where practical; move only schedule ownership/state into the
   sibling module. This preserves the reviewed THE-483 worker arithmetic and
   its no-provider test adapter rather than duplicating that implementation.

   `Err(String)` reports the error and leaves the prior schedule/generation
