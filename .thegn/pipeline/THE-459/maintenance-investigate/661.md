## Finding and production call path

The bug is present exactly as captured:

1. `spawn_month_fetch` gets the configured home zone (`hydrate_calendar.rs:58`), derives a home-local horizon (`:72-74`), and calls `sync_accounts` with local `NaiveDate`s. The view path then calls `expand_month(db, wide_from, wide_to, home)` (`:109-114`, `:169`). `expand_month` invokes `load_cached` without the zone (`:113`), then expands events in `home`.
2. `sync_accounts_with_generation` builds `CalendarRouter::from_config(&scoped)` (`hydrate_calendar.rs:316-320`) and sends only `from`/`to` dates through `list_events_each` (`:334`). `apply_page_with_generation` also converts these dates with `day_ms` before writing `calendar_sync` horizon metadata (`:444-459`).
3. `day_ms` is explicitly midnight UTC (`hydrate_calendar.rs:853-858`). `load_cached` queries `[day_ms(from), day_ms(to)+86_400_000)` (`:539-542`). The SQL overlap predicate is `start_ms < ?1 AND end_ms > ?2` with binds `(to_ms, from_ms)` (`db_calendar.rs:65-87`), so bad bounds omit valid first/last-day events. The fixed duration also cannot represent a local next midnight over DST.
4. CalDAV receives the same naive dates through `CalendarBackend::list_events` (`calendar/mod.rs:317-331`, `:603-612`). `calendar_query_body` formats `from` and `to` as UTC-labeled strings (`caldav.rs:98-114`); both initial full fetch and token-recovery fetch call it (`:419-424`, `:536-545`). The CalDAV `zone` field is used for event parsing, but its factory construction leaves it empty: `raw_backend_from_account` calls `CalDavBackend::new` without `with_zone` (`calendar/mod.rs:358-368`), and router construction only supplies account/admission (`:500-520`). Passing an explicit canonical instant window is needed so CalDAV request filtering matches cache filtering; merely adding a zone-aware conversion in one host call site would leave the seam able to drift.
5. Reminder candidate loading also calls `load_cached` (`hydrate_calendar.rs:799-810`), so it inherits the same bad date-to-instant interpretation even though the actual reminder evaluation bounds are already instant milliseconds (`:813-818`).

Examples of failure: for `America/Los_Angeles`, UTC-midnight bounds start later than local midnight and end before local final-day midnight, missing early first-day and late final-day events; `Asia/Kolkata` has the opposite edge direction; either DST transition makes a fixed 24-hour end wrong. UTC currently masks the offset issue. The wrong cached overlap selection and wrong CalDAV filter can independently omit rows; a full replacement can persist provider omissions.

Existing cache tests (`hydrate_calendar_tests.rs:141-228`) cover incremental application, full replacement, and preserving recurrence masters, but use date-only helpers and do not assert zone-aware range edges. The malformed-row test uses UTC (`:230-265`). CalDAV request tests live in `crates/thegn-svc/src/calendar/tests.rs`; they should be extended for exact XML range bounds.

## Scope and proposed smallest complete fix

Follow the coordination brief: define a pure, testable conversion in `thegn-core` from inclusive local `NaiveDate` bounds plus explicit `chrono_tz::Tz` to one canonical range `[start_ms, end_exclusive_ms)`. Convert midnight at `from` and midnight of `to + 1 local calendar day`, resolve each boundary through `calendar::tz::resolve_local` using the existing `GapPolicy::ShiftForward` behavior (ambiguous time selects the resolver's earlier instant), and return an error for an invalid/unrepresentable window rather than substituting UTC or adding a fixed duration.

Carry that canonical range with the local date bounds through the calendar service/router seam. Existing date-oriented providers can continue using the date endpoints; CalDAV must format the canonical UTC instants as its `time-range` `start` and exclusive `end` (including in token-recovery full fetch). Use the same range for cache overlap queries and `calendar_sync` horizon metadata. Preserve the current SQL strict inequalities, recurring-master inclusion, and all-day/recurrence expansion behavior. A concrete API detail remains for the primary to approve: whether the public seam takes one core `CalendarWindow` value (preferred to avoid parallel date/instant arguments) or adds a narrower window-aware method while retaining the date method for compatibility. Do not construct a CalDAV range from the backend's currently empty `zone` field.

## Failure cases and regression coverage to require

- UTC control case unchanged; negative and positive offsets with events in the first and last hour of the requested local dates.
- `Asia/Kolkata` (+05:30), and preferably a +05:45 zone, to catch rounding assumptions.
- New York spring-forward (23-hour local date) and fall-back (25-hour local date), asserting exact UTC start/end and full-day interval.
- Event overlap semantics at exact boundaries: an event starting at `start` is included, an event ending at `start` is excluded, an event ending at `end_exclusive` is included, and an event starting at `end_exclusive` is excluded. Keep SQL's half-open predicate aligned.
- CalDAV XML emits those same UTC instants and labels the end-exclusive endpoint correctly; both initial full query and token-recovery full query use it. No naive date is appended with `Z`.
- Cache/provider agreement: for each table case, assert the cache and CalDAV consume identical canonical endpoints.
- Existing all-day events, recurrence masters, incremental tokens/tombstones, and month widening continue to behave as before. Recurring masters remain included regardless of their own start/end span.
- Tests explicitly construct every zone and do not sleep, inspect machine `TZ`, or depend on the system zone.
