## Finding: defect remains on this exact branch

1. `crates/thegn-host/src/theme_store.rs:56-59` stores only the public `mpsc::Sender<Work>` and an unbounded Tokio result receiver; it has no cancellation state or `JoinHandle`.
2. `theme_store.rs:62-81` creates an unbounded std request channel and unbounded Tokio result channel, clones the request sender for the watcher callback, detaches the worker, and panics on thread creation failure with `.expect("theme store worker thread")`.
3. `theme_store.rs:137-164` passes the watcher sender into `worker`, captures it in the notify callback (`:148-157`), owns the watcher in that worker, and blocks on `request_rx.recv()` (`:164`). Dropping the store drops only its sender. The callback's sender clone keeps `recv()` connected, so the worker never exits and retains the watcher and result sender.
4. The only production construction is `crates/thegn-host/src/run.rs:663`. The worker starts before remaining startup setup; `run.rs:796-802` awaits its initial catalog before first-frame theme selection. In the loop, `theme_store` is owned by `event_loop` (`run.rs:6163`) and results are drained by the theme-builder paths (`run.rs:8269-8283`, `handlers/theme_builder.rs:106-159`). Normal event-loop returns drop the store, but do not currently stop the worker.
5. Worker writes are synchronous and occur on that background thread: `theme_store.rs:222-234` dispatches Save/Apply, and `:375-381`, `:384-479`, `:493-...` perform filesystem reads/atomic writes. No Save/Apply completion acknowledgment is issued to the caller at enqueue time; completion is represented by worker results.
6. Existing tests at `theme_store.rs:589-648` establish that Save/Import/Apply queued during watcher debounce are processed and their results published. `:762-773` checks a disconnected request receiver returns an error. No current test exercises ThemeStore drop, watcher teardown, worker join, thread-spawn failure, or shutdown with writes pending.

## Smallest complete scoped fix

Give `ThemeStore` ownership of the worker `JoinHandle` and an explicit shutdown path. On drop, signal the worker independently of the watcher-held request sender, have the worker exit its receive loop and drop its watcher, then join the worker. The signal must not depend on dropping the public sender alone; that is the defective cycle. Keep the existing Background QoS assignment.

Replace `.expect` on thread creation with a degraded/unavailable store path and a warning. On failure, ensure the request receiver and result sender are dropped so `scan/import/save/apply` return the existing unavailable error and `initial_catalog()` takes its existing closed-results path rather than hanging. If changing `spawn` to return a typed result, adapt `run.rs:663` to preserve first-frame startup and emit a warning. Primary should choose the minimal representation that makes failure observable without adding new theme behavior.

The shutdown signal and channel interaction needs careful review against the existing unbounded watcher/request queue: a stop queued behind an arbitrarily growing notification backlog cannot itself guarantee bounded join time. A minimal in-scope solution should ensure watcher notifications cannot indefinitely starve shutdown (for example, use a distinct/coalesced control path or another prioritized cancellation mechanism) while retaining accepted user mutation ordering. Do not claim a hard bounded join across a filesystem operation that can itself stall; define what bound the tests actually establish. This is a design point for primary review before implementation.

## Failure cases the fix/tests must cover

1. Drop the last ThemeStore while the watcher is registered: worker exits, watcher is dropped, join completes within the explicitly tested bound; no self-retaining callback sender remains.
2. Repeated create/drop: each iteration joins; worker/watcher count does not accumulate.
3. Shutdown requested with queued Change notifications: cancellation is not starved behind notification churn.
4. Shutdown while Save/Apply is queued or in progress: accepted user mutations obey the documented drain policy and preserve order; failures are surfaced through the existing result/status path when possible.
5. Thread spawn failure: app construction does not panic; startup does not hang; theme operations report unavailable/degraded state.
6. Worker panic: join observes the panic or channel closure and does not hang; user-visible status follows a defined path.
7. Existing debounce case: Save/Import/Apply remain processed once and in order while catalog refresh is debounced.
