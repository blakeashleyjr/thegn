## Exact-branch evidence

The cited audit line numbers are stale, but the same failure is present at this
HEAD:

1. The public fields are accepted and documented in
   `crates/thegn-core/src/config_calendar.rs:230-257`:
   `WorldClock.format` is a per-row strftime override whose empty value is
   documented to inherit `[calendar] time_format`, and `WorldClock.show_date`
   is documented as an always-date switch.
2. `CalendarConfig::active_clocks` at
   `crates/thegn-core/src/config_calendar.rs:147-167` resolves enabled known
   zones and copies `label`, `zone`, and `format`, but drops `show_date`.
   Unknown zones are intentionally warned and omitted. Thus a configured
   `show_date = true` row cannot reach production rendering.
3. `ResolvedClock` at `crates/thegn-core/src/calendar/tz.rs:253-274` has only
   `label`, `zone`, `format`, and `is_home`; there is no show-date policy and
   `format` may still be empty. `ClockReading` at `:276-295` carries neither
   policy. `read_clocks` at `:297-332` copies local time, offset, abbreviation,
   delta, and the compressed `-1/0/+1` `day_delta`, but never reads or carries
   `ResolvedClock.format`.
4. `CalendarDocs::from_config` at
   `crates/thegn-host/src/calendar_docs.rs:164-202` resolves the global
   `time_format` to `CalUiCfg.twelve_hour` at `:183-195`, but creates the home
   row with an empty format and calls `cfg.active_clocks()` without resolving
   row inheritance. This is the last typed config snapshot before UI state.
5. The synthesized fallback home row in
   `crates/thegn-host/src/detail/calendar/mod.rs:224-237` also uses an empty
   format. It must retain explicit default policy when the fallback is used.
6. `clocks_table` at
   `crates/thegn-host/src/detail/calendar/render.rs:420-475` calls
   `read_clocks` and then hard-codes the global `st.ui.twelve_hour` branch at
   `:429-439`, so every row uses the same 12/24-hour format. It unconditionally
   emits `r.local.format("%a")` at `:449`; the only date indication is the
   amber `+1d`/`-1d` cell at `:460-464`. No row-local format or show-date policy
   affects this code.
7. The safe projection from THE-471 is already on this branch:
   `crates/thegn-core/src/calendar/display.rs:1-157` defines bounded
   `DisplayText`, including the 64-scalar/64-cell `Field::ClockLabel` budget and
   control/whitespace filtering. Existing clock labels and abbreviations use it
   in `render.rs:441-453`; formatted row time/date text does not.
8. `validate_calendar` at
   `crates/thegn-core/src/config_calendar.rs:475-504` validates non-empty row
   formats with `validate_strftime`, so valid values pass admission while the
   runtime ignores them. It does not currently reject second-bearing formats.
   `validate_strftime` at `crates/thegn-core/src/config.rs:39-52` only rejects
   parser errors. The parsed `strftime_needs_seconds` helper at `:54-78` and
   its tests at `crates/thegn-core/src/config_tests.rs:3582-3596` already
   recognize `%S`, `%T`, `%r`, `%X`, `%s`, nanoseconds, timestamps, and escaped
   `%%S` behavior for the bar cadence, but only returns a boolean and is not
   applied to calendar rows.
9. Normal config loading calls `Config::post_process` (for example
   `crates/thegn-core/src/config.rs:6044` and `:6068`), which normalizes invalid
   bar formats at `:6341-6362` but has no calendar-format normalization. The
   implementation must either make the resolved clock policy safely fall back
   for lenient runtime loads or add the equivalent calendar normalization; a
   strict `config validate` error alone must not turn a user-supplied bad format
   into a render-path panic.


An open popup is refreshed by `RefreshKind::ClockTick` at
`crates/thegn-host/src/run.rs:11791-11797`; `retick_open` updates `CalState.now`
at `crates/thegn-host/src/detail/calendar/mod.rs:373-402`. The shared ticker
uses the existing bar-only `clock_period_secs` in
`crates/thegn-host/src/hydrate_refresh_ticker.rs:121-141` and `:372-385`.
Calendar account polling is separately floored at 60 seconds. There is no
calendar-row seconds cadence, and the primary decision is to keep it that way:
second-bearing per-clock formats must be rejected, not wired into the ticker.

The relevant production prerequisites are therefore:

- Resolve locale/global 12/24 inheritance once before constructing row state.
- Preserve the synthesized home row and unknown-zone warn-and-skip behavior.
- Keep `read_clocks` a pure instant-based calculation; it must carry policy, not
  consult config or environment.
- Keep draw-site output bounded through THE-471’s existing sanitizer and the
  existing table clipping/degradation path.
- Do not change account hydration, refresh ownership, or the shared ticker.

## Current failure cases

| Input / state                                                 | Current result                                                                                   | Required result                                                                                               |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| Known row, `show_date = true`, same local date as home        | `show_date` is dropped; compact weekday only                                                     | Typed policy reaches the row and deterministically shows the full local date in the date cell                 |
| Known row, `show_date = true`, local date differs             | Only `+1d`/`-1d` is shown                                                                        | Full local date is shown; the relative delta remains a separate, truthful indicator if it fits the contract   |
| Mixed rows, one `format = "%H:%M"`, one `format = "%I:%M %p"` | Both use global `st.ui.twelve_hour`                                                              | Each row uses its validated effective policy                                                                  |
| Empty row format with global 12-hour or 24-hour setting       | Renderer happens to use global setting, but inheritance is implicit and not carried with the row | Resolved row policy explicitly contains the inherited 12/24 format                                            |
| `%n`, `%t`, or another control-producing supported directive  | No row format is rendered today; future direct formatting could inject controls                  | Format output passes `DisplayText::new(..., Field::ClockLabel)` and is bounded before a cell is built         |
| `%S`, `%T`, `%r`, `%X`, `%s`, `%f`/nanosecond equivalent      | Current validation accepts it and the row would have only minute-driven updates                  | Strict validation rejects it with the directive and cadence reason; lenient runtime loading falls back safely |
| Unknown zone                                                  | `active_clocks` warns and skips it                                                               | Same explicit behavior; no malformed row is synthesized                                                       |
| No configured clocks / synthesized home row                   | Home row is created with empty format and `is_home = true`                                       | Home row receives the resolved global default and retains tested home/date behavior                           |

The exact full-date spelling is not prescribed by the captured issue. The
implementation plan proposes a compact, locale-independent calendar date in the
date cell (for example `YYYY-MM-DD`) when `show_date` is true, while retaining
the existing weekday-only cell and conditional relative delta when it is false.
Primary review must greenlight that deterministic spelling and whether the
`+1d`/`-1d` cell remains alongside the full date; this is a contract choice,
not a dependency on another branch.

## Smallest complete fix

1. **Core typed policy and resolution.** In
   `crates/thegn-core/src/calendar/tz.rs`, introduce the smallest typed
   effective-format representation that distinguishes the inherited 12-hour,
   inherited 24-hour, and validated custom strftime cases. Add `show_date` to
   `ResolvedClock`; make `CalendarConfig::active_clocks` copy it and resolve an
   empty format against the already-resolved global default. Add the effective
   format and `show_date` to `ClockReading` so the renderer receives one
   self-contained row contract. Keep zone resolution, DST offset calculation,
   fractional-minute deltas, and `day_delta` unchanged.
2. **Validation/lenient-load safety.** In
   `crates/thegn-core/src/config_calendar.rs`, retain existing strftime
   validation and add parsed-item detection for formats whose output varies
   within a minute. Reuse/extend the existing parsed helper in `config.rs` (do
   not substring-match and do not mistake `%%S` for seconds). Report
   `calendar.clocks[i].format` plus the offending directive and “seconds are
   not supported at the configured cadence.” Make normal `Config::post_process`
   apply the same safe fallback for invalid or second-bearing calendar formats,
   analogous to the existing bars fallback, so a lenient load cannot panic or
   promise stale seconds. No refresh knob and no ticker change.
3. **Host snapshot.** In `crates/thegn-host/src/calendar_docs.rs`, resolve the
   global time format once, pass it to active-clock resolution, and give the
   synthesized home row that same explicit default. Update the fallback home
   constructor in `detail/calendar/mod.rs` to preserve the effective policy.
   The startup/reload call sites stay unchanged; they already rebuild this
   snapshot when config changes.
4. **Pure row rendering.** In
   `crates/thegn-host/src/detail/calendar/render.rs`, format each reading from
   the carried row policy rather than `st.ui.twelve_hour`. Keep the current
   compact inherited output byte-compatible (`h:mmam` / `HH:MM`) unless a
   custom format is selected. Build the date cell from `show_date` using the
   primary-approved compact date spelling; keep same-day/cross-day behavior
   deterministic and do not recompute config at draw time. Pass both formatted
   time and date text through `DisplayText::new(..., Field::ClockLabel)` before
   constructing `Cell::Text`. Preserve the existing table clipping and avoid
   new glyph/color literals.
5. **Contract documentation.** Update the Rust field/type docs (which feed the
   generated schema), `config/config.toml.example`, `docs/help/calendar.md`,
   and the calendar OpenSpec requirement/scenarios so they state: empty format
   inheritance, supported minute-safe formats, rejection of seconds-bearing
   directives, the `show_date` same-day/cross-day output, and bounded terminal
   text. No new keys.
