# THE-686 adversarial source review — dispatch 604

Verdict: **revisions-needed**

The implementation preserves the primary issue's main admission rule: an
ignored-only status is admissible, tracked and non-ignored untracked status is
refused, and the TTL/`--force` selection logic is unchanged. The source review
also found two cleanup races/classification gaps that prevent this from being
source-review-clear.

## Findings

### 1. High — ignored files can still be deleted after the final status check

`crates/thegn-host/src/merge_cleanup.rs:621-639` performs
`self.revalidate()` at line 626, runs the caller-supplied `final_guard` at line
627, and then invokes `git worktree remove` at lines 628-638. The status
snapshot is therefore not protected across the final guard/removal boundary.
The mutation lock used by `mutation_lock()` is a repository bookkeeping lock;
it does not prevent a compiler, test process, or other external writer from
creating an ignored entry in the worktree.

This is exploitable against the issue's safety regression: a new ignored file
can appear after the last status observation and be silently removed. Plain
`git worktree remove -- <path>` does not save us here; a focused temporary Git
fixture showed it exits 0 and deletes a worktree containing a newly-created
ignored file.

The added regression `ignored_work_appearing_after_the_last_guard_is_not_removed`
at `crates/thegn-host/src/merge_cleanup_tests.rs:401-417` writes the ignored
file from the final guard and requires `Refusal::Changed`. It is intentionally
not run in this dispatch because Rust execution is centrally owned; by source
inspection it currently reaches `git worktree remove` and is expected to fail.

Required correction: close the status-to-removal interposition window with a
removal protocol that actually protects the worktree contents (a second check
alone only narrows, but does not eliminate, the race), and retain this
deterministic regression.

### 2. Medium — tracked/untracked status changes are not typed as

`Changed` and miss the changed-during-cleanup report path

At `crates/thegn-host/src/merge_cleanup.rs:581-591`, `revalidate()` calls
`Self::probe()` with `?` before comparing the raw status bytes. If a new
tracked or non-ignored untracked entry appears after admission, `probe()`
returns `Refusal::Dirty` at the parser and the comparison is never reached.

That error is caught only as a generic error in
`crates/thegn-host/src/merge_lifecycle.rs:480-497`: the special
`Refusal::Changed` arm is skipped, `changed_during_cleanup` stays false, and
the outcome becomes `CleanupOutcome::Refused`, not `KeptChanged`. The sweep
then puts it in `SweepReport::kept` at
`crates/thegn-host/src/merge_sweep.rs:241-246`, so the UI/CLI receives the
generic refused form instead of the dedicated `kept … — changed during
cleanup` category.

Physical safety is retained (the worktree is not removed), but this violates
the primary instruction that a changed final snapshot use the typed changed
outcome and makes the report counts inaccurate. The added regression
`final_validation_classifies_new_tracked_work_as_changed_during_cleanup` at
`crates/thegn-host/src/merge_cleanup_tests.rs:390-399` captures the expected
behavior and is not run here.

Required correction: preserve the fresh raw status observation even when its
classification is dirty, compare it with the admission observation first, and
return `Refusal::Changed` for any changed admissible/dirty status snapshot;
then keep the existing admission-time `Refusal::Dirty` behavior.
