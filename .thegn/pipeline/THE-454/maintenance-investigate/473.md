## Finding: the bug remains

### URL validation and credential surface

- `crates/thegn-core/src/config_calendar.rs:266-275` defines the remote URL,
  username, and token fields. `CalendarProviderKind::IcsUrl` accepts
  `ics_url`, `webcal`, and `url` aliases at lines 363-371.
- `validate_calendar` at lines 425-464 checks account names, required fields,
  and plugin capability syntax. At lines 440-451 it only requires a non-empty
  URL for `ics_url`/CalDAV; it does not parse the URL, restrict schemes,
  reject URL userinfo, bind an origin, or constrain address classes.
- `crates/thegn-svc/src/calendar/ics_url.rs:31-46` only trims the string and
  replaces a lowercase `webcal://` prefix with `https://`. Unsupported schemes,
  malformed authorities, URL credentials, and redirect destinations reach the
  transport layer unchecked. CalDAV stores the similarly unparsed string at
  `caldav.rs:35-44`.

### Redirects and secret/body replay

- `ics_url.rs:83-101` creates a default `reqwest::Client` and attaches
  Bearer or Basic authorization to the request before `.send()`. No redirect
  policy is set, so reqwest's default redirect handling remains active.
- `caldav.rs:57-66` attaches Basic/Bearer authorization, and
  `caldav.rs:90-99` interpolates the opaque `sync_token` into the REPORT XML
  body. The request is sent at lines 249-263 using the default redirect policy.
  A 307/308 can therefore replay that body at a redirect destination; same-host
  redirects also leave the authorization retention question to the default
  client policy. Cross-origin header scrubbing would not remove the token from
  the body.
- CalDAV's 409/507 recovery at `caldav.rs:270-285` recursively calls
  `list_events` with a fresh client and a full-fetch body. This is legitimate
  protocol recovery but currently has no shared operation deadline or policy
  state.
- Neither backend explicitly forbids HTTPS-to-HTTP downgrade, loops, relative
  versus absolute locations, or a redirect to a private/special address. The
  default proxy environment is also not made part of an explicit destination
  policy.

### Response/resource bounds

- ICS success handling at `ics_url.rs:127-139` treats Content-Length as an
  advisory precheck, then calls `.text().await` at line 134 and checks the
  decoded string length only after the full body has been allocated and
  decoded. Chunked/no-length and compressed responses bypass the precheck; a
  compressed body can be small on the wire and oversized after decoding.
- CalDAV has no Content-Length precheck and calls `.text().await` at
  `caldav.rs:290-295`, applying the same post-buffer 32 MiB check.
- Non-success responses return a status-only `CalendarError` before a bounded
  diagnostic-body policy or content-type check. The code does not currently
  allocate the error body, but there is no shared bounded error-body/stream
  contract to protect future diagnostics or a never-ending error stream.
- `CalendarError` at `calendar/mod.rs:27-51` permits arbitrary strings, and
  network errors are constructed from `reqwest::Error::to_string()` at
  `ics_url.rs:101,137` and `caldav.rs:263,293`. Unlike `IssueError`, the
  calendar Display/Debug path does not guarantee that request URLs, query
  secrets, redirect locations, or provider text are redacted. The host logs
  `%e` and persists `e.to_string()` at
  `crates/thegn-host/src/hydrate_calendar.rs:191-205`.

### Client/pool lifecycle

- Both backends construct a new client inside every `list_events` call
  (`ics_url.rs:83-86`, `caldav.rs:236-239`), discarding connection pools on
  every poll.
- `CalendarRouter::from_config` builds new backend objects at
  `crates/thegn-svc/src/calendar/mod.rs:180-193`. The host deliberately scopes
  a router to stale accounts each pass at
  `crates/thegn-host/src/hydrate_calendar.rs:168-183`, so a backend-local
  client would still not survive periodic refreshes. A process-shared policy
  client/pool with no default authorization, or a genuinely persistent router,
  is required for the reuse acceptance criterion.

## Smallest complete fix proposal

1. Extract the generic, reviewed portions of `thegn_svc::issue::http` into a
   service-level safe HTTP module (likely `crates/thegn-svc/src/http.rs`), or
   make that module generic while keeping issue-specific error adapters. It
   should own a process-reused reqwest client/pool with no default auth or
   cookies, account-local parsed destination/origin state, and a per-operation
   deadline. Preserve the already-reviewed tracker behavior rather than
   duplicating it.
2. Parse and normalize remote calendar URLs at config validation and again at
   backend construction/startup. Accept only the documented HTTP/HTTPS forms
   plus `webcal` for ICS URL accounts, normalize `webcal` to HTTPS, reject
   malformed/unsupported schemes and URL userinfo, and never include raw URLs
   in errors. Preserve query-bearing subscription URLs only if their redacted
   representation remains safe; this is important because signed ICS URLs are
   commonly query-based credentials.
3. Use `Policy::none` and reject every 3xx response (301/302/303/307/308)
   before reading a body. This is the smallest complete redirect state machine:
   there is no hop to authenticate, no Location-following, no downgrade, no
   loop, and no CalDAV REPORT body replay. Do not log or return the Location
   value. Enforce the configured destination/address policy on the initial
   connection and make proxy behavior explicit; the implementation must not
   claim DNS/address protection while an ambient proxy can bypass it.
4. Stream decoded success and bounded diagnostic/error bodies with a
   `bytes_stream` reader that stops at `MAX_BODY` before vector growth beyond
   the cap. Do not trust Content-Length. Apply the same hard limit when
   content encoding is present, and reject or explicitly support only documented
   ICS/DAV media types and parameters. Use distinct connect, read/idle, and
   total operation deadlines, including for never-ending bodies and CalDAV's
   token-recovery follow-up within one operation budget.
5. Make Ics URL and CalDAV backends use the shared client/pool, attach
   Authorization and conditional headers per request only, and keep the
   CalDAV REPORT token in the request body only for the configured origin. Do
   not install account credentials as client defaults. A process-shared client
   may pool connections across accounts only because auth/cookies/state remain
   request-local.
6. Keep the existing host router/scoping and cache rules unless implementation
   review proves a persistent router is necessary. A process-shared transport
   is the smaller change that survives router recreation across polling passes.
   Sanitize `CalendarError` Debug/Display and host-persisted diagnostics so no
   subscription URL, username/token, sync token, body, or redirect location can
   appear.

### Design dependency requiring primary review

The issue requires address-class checks and mentions an explicitly configured
destination policy, but the current `CalendarAccount` has no such field and
the current URL feature has no proxy setting. Before implementation, the
primary agent must greenlight the compatibility rule. Recommended smallest
choice: redirects are never followed, the configured authority is the only
approved destination, every DNS result used for that authority is checked for
the allowed address class (including rebinding), and no ambient proxy is
allowed to bypass the check. If explicitly configured private/LAN calendars
must remain supported, that must be expressed as a trusted destination policy
and tested; do not silently infer it from a redirect or proxy response.

Other dependencies are coordination, not blockers: reuse THE-321's reviewed
transport extraction; keep THE-453's structural CalDAV parser work separate;
land before THE-456's bounded calendar concurrency; and avoid overlapping
THE-450 identity, THE-486 typed credential broker, THE-465 max-events,
THE-462 calendar filtering, and THE-457 recurrence work. THE-486 is especially
relevant to secret sourcing, but the transport must remain safe with the
current direct `expand_env_ref` path until that issue lands.

## Failure cases and regression matrix

The implementation should prove, with local deterministic fixtures:

- malformed URL; `ftp://`, `file://`, and other unsupported schemes; accepted
  HTTP/HTTPS/webcal; URL userinfo; IPv4 and IPv6 literals; private, loopback,
  link-local, multicast, and unspecified address classes; DNS rebinding; and
  ambient/explicit proxy behavior;
- 301, 302, 303, 307, and 308 with relative and absolute Locations, same-host
  and cross-host targets, HTTPS→HTTP downgrade, and loops. Assert one source
  request, zero target requests, no Authorization/cookie replay, no REPORT
  sync-token replay, and no Location/secret in errors;
- exact-at-cap, cap-plus-one, omitted Content-Length, chunked, and compressed
  decoded success bodies for ICS and DAV; oversized and never-ending error
  bodies; correct compatibility media types and rejection of unexpected types;
- connect timeout, idle/read timeout, total deadline, and CalDAV 409/507
  recovery staying within one operation deadline;
- two accounts and repeated router/poll construction sharing the transport
  pool without sharing auth, cookies, URL credentials, ETags, or sync tokens;
- sanitized `CalendarError` Debug/Display plus host log/DB error projection,
  while existing cache-preservation and per-account failure behavior remains
  intact.
