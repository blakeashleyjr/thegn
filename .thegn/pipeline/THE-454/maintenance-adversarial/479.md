## Findings

### 1. High — public IPv6 admission is not a complete global-unicast policy

Location: `crates/thegn-svc/src/http.rs:211-220`, especially the
`public_ipv6` predicate.

The predicate rejects loopback, unspecified, multicast, ULA, link-local, and
`2001:db8::/32`, but otherwise admits special-purpose non-global IPv6 space.
For example, `2001:2::1` (benchmarking), `2001:10::1` (ORCHID), and
`3fff::1` (documentation) all satisfy the current predicate. A configured
calendar hostname resolving to one of those addresses therefore passes the
public destination policy and can be used as an unintended special-network
destination. This violates the issue's default rejection of “other non-global
IPv4/IPv6 destinations,” even though the resolver does correctly fail closed
for mixed allowed/forbidden answers.

Practical fix: replace the hand-written partial IPv6 allowlist with an
authoritative global-unicast check or a complete, reviewed IANA special-purpose
denylist, applied to both literals and every resolver answer. Keep mapped forms
normalized before the check. Add tests for all special-purpose IPv6 classes,
including the three cases above and DNS answers rather than only pure helper
inputs.

The added test
`public_destination_policy_rejects_non_global_ipv6_special_prefixes` at
`crates/thegn-svc/src/http.rs:374-382` captures this requirement. It was not
executed here; source inspection shows the current predicate would fail it.

### 2. Medium — the streaming cap can grow the retained Vec beyond the hard cap

Location: `crates/thegn-svc/src/http.rs:283-299`.

The length check at line 295 prevents `body.len()` from exceeding `limit`, but
`extend_from_slice` may geometrically grow the Vec capacity past the requested
length and past the configured limit. A large valid chunk followed by a small
chunk can therefore make the retained allocation exceed the advertised 32 MiB
success cap (and the same shared reader is used for the 1 MiB tracker cap).
The check also happens only after reqwest has materialized the current stream
chunk, so a large transport chunk is not itself bounded by the application
limit. This weakens the issue's “before allocation growth” and resource-bound
requirements.

Practical fix: reserve only the exact remaining capacity before extending, or
use a bounded/chunked accumulator whose logical and physical retained capacity
cannot exceed the limit; reject a chunk before any retained-buffer growth.
Add a deterministic capacity/resource regression fixture for a false or absent
Content-Length with a boundary-crossing chunk, plus the chunked and compressed
oversize cases. Keep compressed responses rejected before body reads as the
approved plan specifies.

### 3. Medium — valid MIME tokens are compared case-sensitively

Location: `crates/thegn-svc/src/http.rs:233-256`.

Media type tokens are case-insensitive, but `validate_media` compares the raw
token against lower-case literals. A valid `TEXT/CALENDAR` or `Application/XML`
response is rejected, despite the documented compatibility policy. This is a
real-world compatibility failure in the new validation layer.

Practical fix: normalize the media token with ASCII case folding before the
match, preserve parameter handling, and test every documented ICS/DAV variant
with mixed case and parameters. The current calendar tests do not exercise any
successful MIME response; their oversized fixture only checks that the error is
one of several broad classes (`calendar/tests.rs:306-370`).

## Acceptance observations

- URL parsing/normalization is present in core and repeated at backend
  construction (`crates/thegn-core/src/config_calendar.rs:528-559`,
  `calendar/ics_url.rs:34-46`, `calendar/caldav.rs:38-50`). Unsupported schemes,
  userinfo, and fragments fail closed without echoing the raw URL.
- Redirect handling uses `Policy::none()` and refuses 3xx before inspecting
  `Location`; the ICS 304 cache compatibility exception is explicit and does
  not read a redirect location.
- Request credentials are attached per request, clients have no cookie store or
  default auth, public/private pools are split, and ambient proxies and
  decompression are disabled. These claims still need the integration tests
  listed above.
- Success bodies and diagnostic/error bodies are streamed through bounded
  readers, and CalDAV token recovery reuses one absolute deadline with one
  fallback request. Exact boundary and never-ending-body behavior remains
  unverified.
- Calendar errors constructed by these paths use static/generic transport
  messages and status-only API/Auth messages. `CalendarAccount` Debug redacts
  URL, username, and token. Host persistence/logging therefore appears safe by
  inspection, but the required host-level regression is absent.
