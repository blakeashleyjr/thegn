## Verdict

`blake/the-505-make-configuration-admission-bounded-validated-generation`);

## Bug still present: direct evidence

### 1. Error-to-default substitution is still the main runtime contract

`crates/thegn-core/src/config.rs:5925-6000` (`Config::try_load_layered`)
returns an error for an existing unreadable/invalid-UTF-8 base file, but it
also treats _any_ `NotFound` as an empty file. It parses and post-processes
without calling `config_validate::validate_diagnostics` or
`typed_semantic_errors`. The selected profile is guarded by
`if let Ok(ps) = read_to_string(...)` at `:5978-5986`; missing, unreadable,
invalid-UTF-8, and parse/apply failures do not prevent the base config from
continuing (parse/apply failures only warn).

`crates/thegn-core/src/config.rs:6004-6023` (`Config::load_layered`) catches
all `try_load_layered` errors, logs `parse error ... using defaults`, creates a
fresh `Config::default()`, reapplies environment and `--set` overrides, and
returns `Config`. Thus malformed, unreadable, invalid-UTF-8, and explicit
missing-path inputs can still become an apparently successful config. An
explicit `Some(path)` is not distinguished from the implicit default path for
the `NotFound` case.

The behavior is locked by an existing test rather than merely inferred:
`crates/thegn-core/src/config_tests_coverage.rs:1365-1377` asserts that a
malformed file recovers to defaults while retaining env and flags. The nearby
`config_tests.rs:2978-2999` only proves that `try_load_layered` reports the
read error; it does not stop callers using `load_layered` from continuing.

### 2. Strict validation is a separate, non-authoritative command path

`crates/thegn-core/src/config_validate.rs:34-99,101-280` has the schema walker,
compatibility normalization, and semantic validators (pipeline, templates,
sandbox/provider-related checks, calendar/weather/LSP/secret constraints, and
more). Runtime loading never makes this result an admission condition.

Serde-backed enum deserializers in `config.rs` are deliberately warning/default
based (`config.rs:126-130`), and unknown TOML keys are ignored by the tolerant
deserialization. `post_process` at `config.rs:6146-6314` also synthesizes
agents/tools, clamps values, drops unusable collectors, and substitutes invalid
strftime formats. These transformations can publish a different policy from
the written document before strict validation is consulted.

The CLI validator is independent: `crates/thegn-host/src/cmd/config.rs:385-408`
calls `config_health::collect`, while `config_health.rs:73-157` rereads the
main/profile files and runs `validate_diagnostics`. `run_subcommand` has
already loaded the config at `crates/thegn-host/src/main.rs:1139-1177`, and
the `open` path loads it at `:984-998`, before the command-specific validation
result can be used as an admission gate. `config set` does a local rollback
check (`cmd/config.rs:66-131`), not a shared admitted snapshot.

### 3. Hydration, daemon refresh, and reload have different failure policies

- Startup TUI: `crates/thegn-host/src/run.rs:617-655` uses
  `load_layered`, then installs DB migration policy, channel/automation/log
  state, and other runtime effects.
- CLI/open: `crates/thegn-host/src/main.rs:984-998` and `:1139-1177` use
  `load_layered`, merge DB hosts, clamp the channel, and continue.
- Hydration: `crates/thegn-host/src/hydrate.rs:4041-4050` invokes
  `try_load_layered(...).unwrap_or_default()`, merges DB hosts, and returns an
  empty/default `Config`. It is reached by model hydration at `:2114`, cold
  fill at `:3330`, and notification checks at `:3729`; handlers also call it
  (`handlers/repo_trust.rs:267,308`, `handlers/switch_cache.rs:170`).
- Hot reload: `run.rs:920-977` debounces a filesystem event and sends
  `Result<Config, String>` from `try_load_layered`, but the publication handler
  is not an admitted generation boundary. The old live config is retained on
  failure, without typed health or generation/digest parity.
- Daemon refresh: `crates/thegn-host/src/config_source.rs:37-50` maps a failed
  reload to `None`, and `daemon/service.rs:475-490` does
  `fresh.as_ref().unwrap_or(&snapshot)`. The explicit comment calls the boot
  config a fallback when the file no longer loads. This is unsafe for a new
  authority-bearing agent launch: it silently launches from an old generation.
- MCP proxy daemon reload: `crates/thegn-host/src/mcp_proxy/mod.rs:130-140`
  directly calls `load_layered`, so it gets the default fallback contract.
- Other direct, off-loop/config-derived paths include
  `agent.rs:1021-1034` (VPN teardown), `agent.rs:3029-3039` (provider sync
  teardown), `agent_teardown.rs:15-28` (checkpoint close),
  `merge_lifecycle.rs:301-312`, `worktree_lifecycle.rs:535-565`, and
  `complete.rs:351-371` (completion's cached tolerant load). They have no
  shared snapshot or typed failure surface.

### 4. Explain can lie about the effective runtime config

`crates/thegn-core/src/config_resolve.rs:1410-1476` rereads the raw base with
`read_to_string`, uses `toml::from_str(...).unwrap_or_default()` at `:1436`,
silently skips a readable-error profile at `:1439-1443`, and applies env/flags
without the same compatibility normalization and duration handling as runtime
loading. `cmd/config.rs:184-220` calls this replay, so it can report Builtin or
an old layer after runtime discarded/partially applied a source. The command
also overlays repo/workspace details onto that separately reconstructed trace.

### 5. No pre-parse bounded admission budget exists

The trusted loader uses unbounded `std::fs::read_to_string` for the base
(`config.rs:5936`) and profile (`:5979`). Before/while parsing it can normalize,
parse TOML, serialize to JSON, deep-merge, deserialize, clone, and
post-process. There are no source-byte, line-length/count, TOML depth/table,
array/map, string, profile, stage/agent/tool/plugin, normalized-size, or
deterministic-work limits on this path. `apply_toml_overlay` at
`config.rs:6044-6059` repeats the parse/JSON clone path without such a budget.

### 6. Provider side effects still precede complete local spec admission

The issue's provider evidence remains on this branch:

- `crates/thegn-svc/src/fly/machines.rs:87-102` maps every unknown size to

- Fly creation at `crates/thegn-svc/src/fly/mod.rs:242-270` and
  `:537-628` ensures an app and allocates a dedicated IPv4 before the machine

- VPS creation at `crates/thegn-svc/src/vps/mod.rs:719-762` calls

- Config provider fields are unconstrained strings/vectors in

## Production path and prerequisite map

The authoritative boundary must be established before these prerequisites and
consumers publish or use policy:

| Path                   | Current prerequisite/order                                                                                              | Failure today                                                                    |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Interactive startup    | profile reroot (`main.rs:952-959`) → `run.rs:617` load → DB migration policy → automation/log/metrics/session/hydration | malformed/unreadable input becomes defaults before authority-bearing setup       |
| CLI/open               | subcommand dispatch → `main.rs:984` or `:1139` load → DB policy/host merge/channel clamp → command                      | explicit missing and invalid config continue; validate is not the loader         |
| Hydration/UI           | `set_config_source` → repeated off-loop `load_hydration_config` → DB host merge → model/UI projections                  | failure becomes `Config::default()`/empty snapshot with no error                 |
| Hot reload             | watcher/debounce → `try_load_layered` → channel result → publication                                                    | no typed health, digest, or stale-generation CAS; old state is retained opaquely |
| Daemon agent launch    | daemon boot snapshot → per-request `config_source::fresh` → `unwrap_or(snapshot)` → recipe/sandbox/launch               | failed/new stale config can reuse an old authority snapshot                      |
| Explain/get/health     | command has an already-loaded cfg, then health or raw `config_resolve::explain` rereads                                 | health and explain can disagree with runtime layers                              |
| Standalone/teardown    | completion, MCP proxy, VPN/provider teardown, checkpoint, merge/worktree workers reread ad hoc                          | no common source identity, typed failure, or generation                          |
| Remote provider create | config → provider spec → Fly/VPS side effects                                                                           | unknown/malformed specs can reach app/IP/SSH-key mutations                       |

The source capture must happen after profile reroot but before the first DB
consumer/thread (the existing startup comments at `run.rs:612-632` and
`main.rs:990-996` make this ordering load-bearing). DB host definitions must be
captured strictly and composed into the same immutable candidate, rather than
added by a later `merge_db_hosts` call. Authority consumers then need a token
containing source identities, normalized-layer version, typed diagnostics,
last-known-good status, and a deterministic generation/digest.

## Smallest complete fix proposal

Keep the existing `Config` data model and compatibility policy, but put one
new core admission API beside it (rather than extending the already large
`config.rs`):

1. Add a bounded source reader and typed `ConfigAdmissionError`/reason enum
   covering absent implicit default, explicit missing, unreadable, invalid
   UTF-8, oversized, syntax, schema, semantic, profile, environment, and
   transient I/O failures. Read `limit + 1` bytes into a bounded buffer, reject
   before TOML allocation, scan line/depth/node/container/string/work budgets,
   then normalize once.
2. Compose defaults → base → selected profile → env → `--set` in one candidate;
   validate normalized schema/type/unknown-key/compatibility/template/semantic
   rules before any `Config` is published. A named profile is required when
   selected; only the absent implicit default path may intentionally produce a
   documented first-run defaults snapshot. No parse/read/profile error may
   invoke `Config::default()` as a replacement.
3. Finalize DB host definitions through the existing strict host-capture seam
   in the same candidate, validate again after merge, and return an immutable
   `AdmittedConfig` containing redacted bounded diagnostics, exact source
   identities, normalization version, last-good metadata, and a digest/generation.
   Do not expose raw credentials in diagnostics.
4. Replace production `load_layered`, hydration `unwrap_or_default`, daemon
   `unwrap_or(snapshot)`, and raw explain replay with the admission API. Startup
   must refuse before DB/provider/sandbox/agent authority starts on hard failure.
   Display-only reload may retain the prior admitted generation, but must mark
   degraded health; a new authority launch must refuse if admission failed or
   its generation no longer matches the current source/host capture.
5. Make `config explain`, `get`, schema/help health, daemon status, hydration,
   and reload consume the same admitted snapshot and trace. Keep repo overlays
   on their documented untrusted/tolerant path, but make any trusted profile
   failure fail closed and never let a profile identity survive without its
   policy.
6. Add pure provider-spec validators at the service boundary and invoke them
   before Fly app/IP allocation, VPS SSH-key registration, or other remote
   mutations. Unknown Fly presets and malformed image/snapshot/region/org/name
   values must return typed admission errors; optional authenticated provider
   preflight must be bound to the same generation and account.

This is the smallest complete boundary because changing only
`load_layered` would leave hydration, daemon, explain, standalone, DB-host,
and provider paths divergent; changing only `config_validate` would leave the
runtime fail-open behavior untouched.

## Ordered implementation and regression-test plan

1. **Core source/admission API:** add bounded reader, typed reasons, budgets,
   normalized layer trace, digest/generation, and redacted diagnostics. Unit
   test exact boundary values and one-over cases for bytes, lines, depth,
   nodes/containers, strings, profiles, stages/agents/tools/plugins, overrides,
   and total normalized size.
2. **Layer semantics:** test missing implicit default vs missing explicit path;
   unreadable/invalid UTF-8; malformed/truncated base; malformed, missing,
   unreadable, invalid UTF-8, oversized, and schema/semantic-invalid selected
   profile; unknown keys and warn-default enum values. Assert no default policy
   is returned and no secret/parser content is echoed.
3. **Composition parity:** test compatibility normalization, env duration
   errors, `--set`, strict host snapshot merge, profile precedence, and exact
   explain trace/digest. Mutate every input between capture and publication and
   assert the captured generation remains internally consistent.
4. **Host startup wiring:** test that hard admission failure occurs before DB
   migration policy, automation runtime, provider construction, sandbox launch,
   agent launch, or first authority-bearing side effect. Test documented
   first-run defaults separately.
5. **Reload/daemon/hydration:** test valid generation N, invalid reload retains
   N only for display and surfaces one bounded degraded diagnostic; no new
   launch uses N after failed/current generation mismatch. Test hydration and
   daemon use the same snapshot/digest rather than default/boot fallbacks.
6. **CLI/explain/status:** test `config validate`, `config explain`, `config
get`, schema/help health, and daemon status against the same typed snapshot;
   explicit missing and malformed config must exit nonzero before effectful
   setup. Add fault-injection cases for rename/truncate, symlink replacement,
   permission/EIO, and restart/reload.
7. **Provider side-effect gates:** use fake Fly/VPS transports and assert zero
   remote requests for one-unit-invalid size/region/image/org/name/snapshot;
   assert a stale preflight generation cannot create or reuse a resource after
   reload. Keep bounded transport tests at the service seam.
8. **Fuzz/property and focused gates:** fuzz bounded TOML structures and layer
   combinations for panic-free bounded work, then run only the affected core,
   host, and service test filters during implementation. Reserve the full
   workspace/push gate for the implementation owner after this handoff.
