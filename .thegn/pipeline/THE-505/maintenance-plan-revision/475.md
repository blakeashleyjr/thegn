# THE-505 implementation plan revision — native dispatch row 475

## Verdict

The investigation is revised into an ordered, serial implementation plan. The
complete fix is one admitted configuration snapshot with bounded source capture,
strict validation, one DB-host composition, and a real revision check at every
authority publication boundary. It is not a change to the default sandbox, a
provider network preflight, or a replacement for THE-268/THE-444.

This dispatch changes no production source and adds no executable regression
test yet. The regression tests below are part of the implementation chunks;
their exact names, scopes, and commands are recorded so implementation workers
can add them without widening the issue. No Cargo, build, Clippy, nextest,
smoke, or full-suite command was run for this revision.

Observed branch at planning time: ce986337 (review(the-505): record primary
implementation decisions). The existing investigation is
.thegn/pipeline/THE-505/maintenance-investigate/472.md.

## Non-goals and boundaries

- Do not change the default sandbox floor; THE-419 owns that policy.
- Do not add authenticated provider preflight or availability discovery. This
  issue adds local syntax/semantic provider admission only.
- Do not implement THE-268 pipeline leases or THE-444 credential firewalls.
  This plan supplies their admitted revision and profile-failure prerequisite.
- Do not make a repository overlay a trusted global authority. The existing
  repo-overlay boundary remains: it may affect only documented overlay fields
  after trusted global/profile/env/CLI/DB-host admission.
- Do not make teardown depend on a newly successful reload. Teardown may use
  its already-held admitted handle and must retain revocation/cleanup when new
  authority cannot be admitted.
- Do not do file or SQLite work from the input/render loop. Initial admission
  may run before the loop; reload and hydration capture run off-loop and publish
  through the existing channel/waker pattern.

## Contract to implement before wiring callers

The new core boundary should be a small module, not another policy hidden in
the existing Config loader. Names below are proposed API shapes; spelling may
change, but the semantics and ownership may not.

```rust
pub struct AdmissionInputs<'a> {
    pub defaults: Config,
    pub base: SourceInput<'a>,
    pub profile: Option<SourceInput<'a>>,
    pub env: &'a dyn EnvSource,       // already captured/frozen by the host
    pub overrides: &'a [String],
    pub hosts: HostDefinitionsSnapshot, // one strict DB read or explicit absence
}

pub fn admit(inputs: AdmissionInputs<'_>)
    -> Result<AdmittedConfig, ConfigAdmissionError>;

pub struct AdmittedConfig {
    // private; callers receive projections, never a mutable Config
    pub fn config(&self) -> &Config;
    pub fn trace(&self) -> &LayerTrace;
    pub fn revision(&self) -> ConfigRevision;
    pub fn health(&self) -> AdmissionHealth;
}

pub struct ConfigRevision {
    pub generation: u64,
    pub digest: [u8; 32],
    pub sources: SourceIdentities,
    pub normalization_version: u32,
    pub host_schema: i64,
}

pub fn require_current(
    expected: &ConfigRevision,
    current: &AdmissionStore,
) -> Result<RevisionGuard, StaleConfigError>;
```

SourceInput carries the selected path, whether it is implicit or explicit, and
bounded bytes from the one capture. SourceIdentities contains a redacted path
identity plus byte digest/length for base and profile, the frozen-environment
digest, canonical override digest, and host snapshot schema/digest. It contains
no secret values. Generation is allocated only on successful complete
admission; a failed reload cannot publish a new authority generation.

Composition is exactly:

captured defaults -> base -> selected profile -> frozen env -> --set overrides
-> strict DB host definitions -> final schema/semantic/provider validation.

The returned AdmittedConfig owns the normalized config, redacted bounded
diagnostics, exact layer trace, and revision. LayerTrace is the sole source
for explain/get provenance. Config::default() is permitted only when the
implicit default path is genuinely absent; it is not a recovery value for an
explicit path, existing path, selected profile, env/CLI failure, or host
capture failure.

require_current must be real, not a digest field that is never consulted:

1. The reload worker captures all sources and host definitions into a candidate.
2. Publication compares candidate source identities and host digest with the
   current store and atomically installs a new Arc<AdmittedConfig> only if the
   expected generation still matches.
3. An authority operation carries the exact ConfigRevision it observed and
   calls require_current immediately before its first authority side effect:
   provider request, sandbox launch, agent spawn, credential export, or
   pipeline claim. A mismatch returns StaleConfigError with no new side effect.
4. Async provider adapters receive the RevisionGuard; they check before the
   first remote request and again at their local publication/ledger boundary.
   The guard does not make an in-flight remote request cancellable.
5. A failed reload retains generation N for display only and records one
   bounded/coalesced degraded diagnostic. It never authorizes a new operation.

## Numeric admission budgets

These explicit constants are based on the checked-capture foundation and the
current example. The shipped example is 292,597 bytes with a 308-byte longest
line and 82 table headers.

| Input/work item                 |                                                                                  Accepted maximum | Basis and enforcement                                                                            |
| ------------------------------- | ------------------------------------------------------------------------------------------------: | ------------------------------------------------------------------------------------------------ |
| One base or profile source      |                                                                                             4 MiB | Retain parked config_checked MAX_SOURCE_BYTES; read limit + 1 and reject before TOML allocation. |
| Base plus selected profile      |                                                                                             8 MiB | Checked sum before normalization/merge.                                                          |
| One physical line               |                                                                                            16 KiB | Scanner count, outside TOML strings/comments.                                                    |
| Lines per source                |                                                                                            65,536 | Scanner counter.                                                                                 |
| TOML structural depth           |                                                                                                64 | Arrays/tables/dotted-key components only outside string bodies/comments.                         |
| Tables and arrays/maps          |                                              4,096 tables; 16,384 members/container; 65,536 nodes | Checked before child allocation.                                                                 |
| One decoded string              |                                                                                            64 KiB | Applies to keys and values.                                                                      |
| Normalized serialized candidate |                                                                                             8 MiB | Check after compatibility normalization and every merge, before clone/publication.               |
| Selected external profile       |                                                                                                 1 | One normalized selected name/path; implicit default has no file.                                 |
| CLI overrides                   |                                                       1,024 entries; 16 KiB each; 1 MiB aggregate | Matches parked checked foundation; reject before cloning.                                        |
| Captured environment            |                                                         1,024 keys; 16 KiB/value; 1 MiB aggregate | Freeze all mapper-requested keys and reject an uncaptured lookup.                                |
| DB hosts                        | Existing host snapshot limits: 1,024 definitions, 8,192 rows, 4 MiB/definition and 4 MiB snapshot | Reuse strict WAL/read-only capture and JSON decoder.                                             |
| Diagnostics                     |                                         256 source/diagnostic entries; 200 bytes/rendered message | Reuse bounded diagnostic storage; redact values and coalesce repeats.                            |
| Deterministic work              |                                                             Scanner plus decoded nodes <= 131,072 | Reject checked counter overflow and multiplication before normalization/clone.                   |

The scanner must recognize TOML basic, literal, multiline-basic, and
multiline-literal strings before applying line/depth/member counters. Brackets,
equals signs, comments, and apparent table headers inside strings do not affect
depth. A newline inside a multiline string counts toward line limit but is not
a table/array token. This avoids a lexical shortcut that rejects valid quoted
TOML or undercounts hostile structures.

Every budget gets an exactly-at-limit acceptance test and one-over rejection,
including quoted/multiline fixtures and checked-addition overflow. Existing
domain limits remain authoritative; these are preparse/postparse ceilings, not
clamps.

## Major risks and mitigations

- The config module is large and intentionally tolerant. Keep admission
  separate, migrate callers serially, and inspect normalized source/schema
  results before publication.
- A digest alone can be ceremonial. Require a store CAS and guard checks at
  first side-effect boundaries; test a mutation between capture and launch.
- File and DB capture are not globally atomic. Use one captured revision and
  reject identity changes; document remaining filesystem/WAL limits.
- Last-good reload can become launch authority accidentally. Split display
  projection from require_current and test failed reload launch.
- Teardown can be broken by over-strict reload handling. Pass prior handles and
  permit revocation/cleanup only.
- Provider grammars may reject valid vendor values or accept unavailable ones.
  Keep this chunk to documented local grammar/preset checks.
- Parked capture refs contain useful code with unsafe scope if copied wholesale.
  Their docs explicitly say startup, coalescing, reload holds, receiver policy,
  and launch admission are unwired.
- CPU pressure makes verification easy to overrun. Use the focused commands
  below; the primary schedules the full Rust gate once across the batch.
