## Findings

### High — an invalid process selector can silently select the default storage root

Evidence:

- `crates/thegn-core/src/profile.rs:49-55,96-109` passes a nonempty selector
  through `slugify` and then accepts an empty result as `"default"` via
  `normalize_name`.
- `crates/thegn-host/src/config_capture.rs:416-446` resolves the profile and
  only checks that `requested_name` and `resolved_profile.name` agree. For
  `--profile !!!` (or `THEGN_PROFILE=!!!`), both normalize to `"default"`, so
  the check succeeds and the seed uses the default `state_home`, DB, and
  `THEGN_DIR` root.
- The same selector normalization is used by the pre-reroot profile path
  contract, so a later caller cannot recover the fact that an explicit raw
  selector was invalid.

This violates the primary instruction to reject an empty normalized actual
process selector. A typo or malformed selector intended to isolate a process
can therefore run against the default profile's state and credentials instead
of refusing. Validate the trimmed raw process selector before the empty-slug
case is converted to the intentional default sentinel, and make reroot and
capture consume the same typed selector result. Do not apply this rule to the
independent `Config.profile` keybind setting or to `--set profile=...`.

Regression added at `crates/thegn-host/src/config_capture_tests.rs:207-232`:
`invalid_process_profile_slug_is_refused_instead_of_selecting_default`.
It is expected to fail against the current source until the production fix is
made; it was not run here.

### High — macOS and Windows reject ordinary final config symlinks without a

documented product boundary

Evidence:

- `crates/thegn-host/src/platform/config_file_capture_macos.rs:14-20,35-47`
  returns `Unsupported` for every final symlink and explicitly calls out that
  this includes Nix-managed config links.
- `crates/thegn-host/src/platform/config_file_capture_windows.rs:38-51` rejects
  every final reparse point and does not provide an equivalent safe dereference
  path.
- Repository documentation outside the maintenance notes does not describe
  this supported-platform refusal or give a remediation path. The only
  explanation is an implementation comment.

A normal Home Manager/Nix macOS installation commonly makes
`$XDG_CONFIG_HOME/thegn/config.toml` a final symlink into `/nix/store`. Once
this adapter is wired into startup, that valid installation will fail closed as
`configuration source capture is unsupported`, even though Linux deliberately
supports resolved regular-file symlinks. The primary plan permits a refusal
only when the compatibility boundary is explicitly justified in
docs/acceptance. Either implement bounded target opening/revalidation on the
affected platforms, or document and test the deliberate refusal before wiring
it into universal startup, including a typed user-facing remediation.
