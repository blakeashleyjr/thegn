## Does the bug remain?

Yes. In `crates/thegn-svc/src/revtunnel/mod.rs`, `run_sandbox` accepts indefinitely at lines 347–362, inserts each socket in `Conns`, and spawns a connection pump (which itself spawns a writer task in `pump_conn`, lines 145–180). There is no admission check before accepting/spawning. On the host, `run_host` handles every decoded `Frame::Open` at lines 302–324 by inserting its sender and spawning a task that awaits `dialer.dial()` and then pumps the target (lines 309–319). There is no cap or deadline; an Open flood or a dialer that never resolves can accumulate connection state/tasks/sockets.

Existing `CHANNEL_DEPTH = 32` (line 39), bounded inbound channels (lines 310, 353), and bounded shared sink (lines 129–139) only bound queued frames/bytes and create backpressure. They do not bound the number of active connections or spawned tasks. Existing tests `sink_is_bounded_under_a_stalled_writer` and `bounded_tunnel_round_trips_backpressured_payload` prove queue bounds and payload integrity, not admission bounds.

Lifecycle is not fully supervised. `run_sandbox` aborts only its accept task after `read_loop` exits (lines 347 and 368–370); accepted connection pumps and their writer subtasks are detached. `run_host` returns when its read loop ends while spawned dial/pump tasks are detached. `exec_stream` also spawns separate stdin/stdout relay tasks (lines 49–94) without handles or a cancellation token. A stream disconnect or host-side supervisor abort therefore does not by itself prove all child tasks and sockets have ended.

No handshake timeout exists around host `dialer.dial()`; no idle or total lifetime is applied to a logical connection; writes (`write_all` in `pump_conn`, lines 157–162, and outbound `sink.send` at lines 173 and 179) can wait indefinitely under a stalled peer/sink. No cap-rejection/backpressure signal exists; current reverse-tunnel warnings concern preamble skipping and decoder resync (lines 232–280), not admission.

## Smallest complete fix proposal

Keep transport mechanics and admission policy in the svc reverse-tunnel module. Introduce a small `TunnelLimits` value with safe defaults and a shared admission handle: a process/global semaphore shared across host tunnel invocations plus a per-tunnel semaphore. Acquire permits before registering an ID or creating per-connection tasks; hold an owned permit in a single connection owner so it releases on dial failure, timeout, normal close, task cancellation, and drop. Reject over-cap Opens/accepted sockets by closing them promptly and emitting rate-limited structured counters/logs. Handle duplicate IDs without overwriting a live owner.

Use supervised per-connection owners with child read/write tasks in a `JoinSet` or equivalent cancellation/receipt pattern. On stream end, protocol error, or outer task cancellation, stop accepting and drain/cancel child tasks, close sockets, remove routes, and release permits. Put bounded `timeout` wrappers around dial/handshake, socket reads/idle interval, each write/backpressured send, and total connection lifetime. Preserve the existing bounded channels and half-close behavior while ensuring timeout/cancellation wakes both directions. Keep warning volume bounded (for example, aggregate rejected count and log no more than once per interval per tunnel/global admission source).

The clean API seam is to pass `TunnelLimits` and a shared admission object into service functions, keeping existing default wrappers only if API compatibility requires them. To meet the issue’s user-configurable acceptance criteria, host supervisor/config wiring and config documentation/ratchets must also be approved for scope expansion. A svc-only implementation can offer configurable Rust parameters, but cannot make the live host setting configurable from user config because `run.rs`, `crates/thegn-host/src/revtunnel.rs`, core config/schema, and example/env validation are outside this lane. Do not silently claim full acceptance with defaults alone.

Likely files with scope expansion:

- `crates/thegn-svc/src/revtunnel/mod.rs` (admission, limits, supervision, timeout handling, regression tests) — within lane.
- `crates/thegn-host/src/revtunnel.rs` and likely `crates/thegn-host/src/run.rs` (construct/share configured global admission and pass per-tunnel policy) — currently out of lane.
- `crates/thegn-core/src/config.rs` plus split config module/defaults and `config/config.toml.example`; environment mapping/validation and config ratchets if values are `*_secs` — currently out of lane. Coordination explicitly notes four ratchets for new keys.

## Failure cases to cover

- Global quota exhausted across multiple simultaneous endpoint tunnels; per-tunnel quota exhausted while global capacity remains; rejected attempt does not leak a permit or create an unbounded task.
- Race at capacity admits no more than the cap; disconnect, dial error, dial timeout, protocol Close, client EOF, read/write timeout, cancellation, duplicate Open ID, and whole stream shutdown all release routes/permits exactly once.
- A never-resolving dial is bounded by handshake timeout; a connected but silent peer expires by idle timeout; active connection expires at lifetime limit; stalled local writer/shared sink does not pin tasks/permits indefinitely.
- Stream teardown cancels both directional pumps and their sockets; accept loop is stopped and no detached tunnel child remains.
- Repeated rejections produce bounded observability while retaining an exact/monotonic rejection count if exposed.
- Existing multiplexing, half-close semantics, preamble resync, and large backpressured payload continue to work.
