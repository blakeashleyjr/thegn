## Findings

### 1. High — batched inspect rejects the normal multi-container response

`crates/thegn-host/src/merge_cleanup.rs:10-11` makes the `end` marker part of
the per-object Docker/Podman template. `query_oci_runtime` passes every ID to
one batched inspect at `:198-203`, so two containers produce, for example,
`mount:/a\nend\nmount:/b\nend\n`. `parse_mount_sources` at `:290-315` sets
`ended` on the first marker and rejects the second container as “data followed
the end marker”. A normal machine with two or more containers therefore gets a
`could not be queried` refusal even when every mount is unrelated; the primary
acceptance case “installed runtime with unrelated containers is swept” remains
blocked in the common case. The focused regression test added at
`crates/thegn-host/src/merge_cleanup_tests.rs:95-101` demonstrates the required
multi-record shape and is expected to fail until the parser/format is corrected.

### 2. High — blank records are accepted as successful empty ownership data

`parse_container_ids` at `crates/thegn-host/src/merge_cleanup.rs:272-280` skips
all empty records, so `\n` or an ID followed by an extra blank record is treated
as a valid listing. `parse_mount_sources` at `:291-315` does the same, so
`\nend\n` is accepted as “no mounts”. These are malformed responses, not the
exact empty `ps` response or the exact `end\n` no-mount response emitted by the
declared template. A broken wrapper or runtime can consequently turn unknown
ownership into an allow-to-delete result, contrary to the explicit fail-closed
requirement to reject malformed output. The regression test at
`crates/thegn-host/src/merge_cleanup_tests.rs:103-109` covers these cases and is
expected to fail until the parsers become strict.

### 3. Medium — the required force/no-force acceptance matrix is not tested

The direct probe tests at `crates/thegn-host/src/merge_cleanup_tests.rs:139-196`
do not exercise the sweep or either `--force` mode. In `test/smoke.sh`, the
unrelated-runtime case at `:929-931` uses only `--force`, and every
unqueryable-runtime case at `:940-943` also uses only `--force`. There is no
end-to-end no-force test proving that an installed runtime with unrelated
mounts is collected, nor that nonzero/garbage/timeout refusals preserve the
worktree without `--force`. The no-runtime fixture is not swept in a due,
ordinary (non-force) case either. This does not satisfy the issue’s explicit
four-states-by-two-modes matrix and leaves the ordinary sweep path unprotected
by regression coverage.

### 4. Review risk — query-to-delete remains a TOCTOU window

The last ownership query is `resources.revalidate` passed as
`automatic_teardown` at `crates/thegn-host/src/merge_lifecycle.rs:490-498`; the
physical removal happens later in `destroy_one_checked` at
`crates/thegn-host/src/worktree_lifecycle.rs:818-853`. A container can be
created or a bind mount can be attached after the final probe and before
`verified.remove_checked` invokes `git worktree remove`. The new probe is
bounded and correctly rechecks at the teardown boundary, but it cannot make
the external Docker/Podman query and filesystem deletion atomic. This remains
an exploitable “never swept while mounted” race under a literal reading of the
acceptance criterion. No runtime transaction/lock is present in the reviewed
change; the primary’s explicit THE-689 scope exclusion does not document this
OCI race as resolved. At minimum, central validation/review should record this
residual limitation rather than claim an absolute race-free guarantee.
