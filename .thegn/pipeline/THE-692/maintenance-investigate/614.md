## Evidence

The cited paths are confirmed on this branch:

- `crates/thegn-host/src/cmd/land.rs:15-17` documents that `thegn land` does
  not touch queue rows. `:28-54` returns `(branch, target, AttemptOutcome)` from
  the fold without DB side effects. `:78-108` only prepares the existing
  sidebar lifecycle bookkeeping, and `:109-120` handles the successful
  `AttemptOutcome::Landed` by filing/reporting and printing the result. There is
  no queue-row writer. `:122-128` handles `UpToDate` similarly, while
  `:130-168` refuses conflict, gate, unreachable, and ready outcomes.
- `crates/thegn-host/src/integrate.rs:1593-1608` proves the outcome boundary:
  `Ready` returns before CAS; `Landed` is returned only after
  `update_ref_cas` succeeds and carries `folded_tip` as `commit`.
- `crates/thegn-host/src/merge_sweep.rs:68-77` selects candidates only from
  `merge_queue` rows with `status == "landed"` and the current target branch.
  `:206-216` feeds each row's `updated_at` to the TTL calculation, so a newly
  written row must receive its timestamp at the land.
- `crates/thegn-host/src/merge_lifecycle.rs:162-179` confirms the existing
  in-place guard: repo-root worktrees are a no-op, and a non-root lifecycle
  operation may file/unfile but must not remove the caller's worktree.
- `crates/thegn-core/src/db_aux.rs:85-126` validates observed registry/queue
  identity, status/OID consistency, and local-vs-remote context.
  `:343-388` is the validated atomic `persist_merge_outcome` writer: it can
  insert a final row when absent or replace the final projection when present,
  and sets `updated_at` with `util::now()`. The lower-level
  `update_merge_status` at `:430-480` is an existing-row updater and is not a
  suitable insert path.
- `crates/thegn-host/src/integrate_persistence.rs:34-47` and `:220-280` show
  the established pattern: observe before external fold work, persist the
  validated final outcome, then authorize lifecycle work only after `Written`.
- `crates/thegn-core/src/db.rs:328-375` shows that
  `SchemaOperation::LandLifecycleBookkeeping` is the declared read/write
  compatibility operation, whereas `LandRemoteTargetGuard` is read-only.
  Current `land.rs:61-70` selects the write operation only when the sidebar
  lifecycle is non-noop. A queue row is a new required bookkeeping write, so
  non-root manual land must retain the read/write operation even when
  `on_landed = "off"`; repo-root land can retain the read-only guard because it
  must write no row.

## Production call path and prerequisites

1. The CLI resolves the requested worktree and canonical main checkout in
   `cmd/land.rs:57-60`.
2. It resolves the per-repo merge-queue configuration and chooses a compatible
   DB handle in `:60-75`; the remote-target guard runs before git mutation.
3. `land_branch` resolves the branch and target, forces `auto_land`, and calls
   `integrate::attempt_land` in `:32-54`.
4. `attempt_land` folds, optionally gates, and CAS-advances the target. Only
   the successful `Landed { commit, resyncs }` branch is eligible for the new
   row. The commit is already the exact fold tip; no `derive_landed_commit`
   repair/backfill is appropriate.
5. The row must be persisted through `WorktreeAuxStore::persist_merge_outcome`
   using a `MergeFinalOutcome` with the worktree, branch, repo root, resolved
   target, local location (`""`), `Landed`, `Some(&commit)`, and null conflict
   and error fields. Capture `observe_merge_outcome` before calling
   `land_branch`, so registry/queue changes during the fold produce
   `RegistryChanged`/`QueueChanged` rather than an overwrite.
6. After a successful `Written`, retain the existing
   `apply_landed_in_place_checked` sidebar behavior. A lifecycle failure is
   post-land degraded bookkeeping, not a failed land. If row persistence fails
   after git has advanced, report a bounded degraded warning and return success;
   do not invite a destructive retry. The primary should confirm whether to
   skip row-dependent lifecycle filing when the row write itself fails; the
   safe ordering is row first, lifecycle second.

## Outcome/failure matrix

| Outcome or failure                                                      | Queue-row behavior                                                                 | Command behavior                                |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------- |
| Non-root `Landed` and validated write succeeds                          | Insert/update `status=landed`, exact fold OID, target branch, `updated_at` at land | Existing success output; then lifecycle filing  |
| Repo-root path                                                          | No observation write and no row                                                    | Existing root-safe behavior                     |
| `UpToDate`                                                              | No new landed outcome; leave existing row state untouched                          | Existing “already in target” behavior           |
| `Ready`, `Conflict`, `GateFailed`, `GateError`, `Unreachable`           | Do not invoke landed writer; no new landed row                                     | Existing non-success/refusal behavior           |
| `RegistryChanged`, `QueueChanged`, or SQLite write error after CAS land | No trusted new projection; report degraded state                                   | Exit zero because git/ref land already happened |
| Sidebar lifecycle error after row `Written`                             | Row remains sweep-eligible                                                         | Warn degraded, still exit zero                  |

The `UpToDate` choice is intentional for the smallest fix: the issue's
required new record is tied to `AttemptOutcome::Landed`, while `UpToDate` did
not advance the target. Primary review should explicitly preserve or change
this boundary before implementation.

## Smallest complete implementation plan

1. In `crates/thegn-host/src/cmd/land.rs`, keep the existing remote guard, but
   select the declared read/write compatibility operation for every non-root
   manual land because the new final row is required independently of sidebar
   `on_landed` policy. Keep root on the read-only/no-row path.
2. Before `land_branch`, capture the non-root `MergeOutcomeObservation` from
   the retained compatible DB handle. Do not observe only after git work has
   completed, and do not derive the OID from ancestry.
3. Add a small local helper (or tightly scoped function) that builds the
   `MergeFinalOutcome` and calls `persist_merge_outcome`. Match all three
   `MergeOutcomeWrite` results with explicit degraded diagnostics for the two
   compare/refusal cases. Do not hand-roll SQL and do not use
   `update_merge_status` for an absent row.
4. In the `AttemptOutcome::Landed` arm, persist the row with the exact `commit`
   before invoking in-place lifecycle filing. Convert the post-CAS DB error to
   the same warning/zero-exit discipline already used by `file_landed`; keep
   `report_resyncs` and the successful land output. Leave every other outcome
   arm without a landed writer.
5. Add focused host tests around the new dispatcher/helper: non-root success
   inserts the exact OID/target/status and starts `updated_at` at the write;
   an existing queue row is finalized through the validated writer; repo-root
   skips it; `Ready`, conflict, gate-red, gate-error, and unreachable paths
   leave no new landed row; and an injected DB failure is surfaced as degraded
   without converting a post-CAS success into a retryable command failure.
6. Add a hermetic smoke scenario beside the existing merge-drain scenario in
   `test/smoke.sh`: create a separate clean worktree/branch, invoke
   `thegn land --worktree`, assert the row's status, target, and exact fold OID,
   assert the worktree/branch survive the grace period, then set
   `merged_ttl_secs=1`, wait for real expiry (not zero), and assert
   `merge sweep` collects it. Keep the existing drain scenario as coverage for
   its separate path. Include a root-land/no-row assertion if the CLI fixture
   can do so without changing the target branch.
