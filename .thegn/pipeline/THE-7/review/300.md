# THE-7 security/test/bug review — row 300

## Verdict

FAIL — not ready for the merge queue.

The focused theme tests pass after review fixes, but the filesystem boundary
still violates the promised path confinement and bounded-I/O contract. There
are also unimplemented variant semantics and runtime paths that bypass the
loaded user-theme resolver.

## Blocking findings

1. **Theme/config atomic writes can follow a hostile temporary-file symlink.**
   `theme_store::write_theme` derives the predictable
   `<slug>.toml.tmp` name and calls `std::fs::write` before rename
   (`crates/thegn-host/src/theme_store.rs:299-307`). The CLI duplicates the
   same pattern (`crates/thegn-host/src/cmd/theme.rs:170-177`), and config
   persistence uses a predictable sibling temp path too
   (`crates/thegn-host/src/theme_store.rs:401-407`). `std::fs::write` follows
   an existing symlink, so a pre-positioned temp symlink can overwrite any
   user-writable target outside the themes directory before the rename. That
   directly violates the requirement that writes remain confined beneath the
   themes directory. Create a unique same-directory temporary file with
   exclusive/no-follow semantics, preserve config permissions, and add Unix
   tests that pre-place symlinks for both theme and config temp targets.

2. **The regular-file/size checks are TOCTOU and the catalog scan is not
   bounded as claimed.** `read_bounded` checks path metadata and then reopens
   the path with `std::fs::read` (`theme_store.rs:277-288`; duplicated at
   `cmd/theme.rs:147-159`). A replacement between those operations can turn a
   checked regular file into a symlink or make the read exceed the 64 KiB cap.
   Open once with no-follow semantics, validate the opened handle, and read at
   most `MAX + 1` bytes. Separately, `scan_dir` collects and sorts every
   directory entry before applying `MAX_THEME_FILES`, and applies the limit
   before filtering for theme files (`theme_store.rs:247-255`; CLI equivalent
   at `cmd/theme.rs:116-124`). A large directory therefore defeats the bounded
   work guarantee, while 256 lexically earlier junk entries hide every valid
   theme. Completion takes the first 256 filesystem-order entries before
   filtering (`crates/thegn-core/src/completion/sources.rs:318-341`), making
   the visible catalog nondeterministic. Entry/metadata/read errors in the CLI
   are also silently discarded (`cmd/theme.rs:126-141`), contrary to the
   corrupt/oversized-file warning requirement.

3. **Gogh `variant` is validated and stored but has no conversion semantics.**
   `convert_gogh` always copies imported `background` to `bg0` and
   `foreground` to `text`; it never branches on `scheme.variant`
   (`crates/thegn-core/src/theme_import.rs:136-223`). Consequently a document
   declaring `variant: light` with a dark background produces a dark palette.
   The existing light test only supplies an already-light background and does
   not prove the requirement that a light variant yields a light palette. Add
   contradictory light/dark fixtures and either reject inconsistent schemes
   or define deterministic variant-aware conversion without breaking the
   documented foreground/background mapping.

4. **Loaded user-theme resolution is bypassed by startup/onboarding paths.**
   Startup installs `cfg.palette()` before the asynchronous user catalog is
   available (`crates/thegn-host/src/run.rs:717-720`), so a configured local
   preset initially renders as the default palette. More seriously,
   onboarding preview and dismissal call `palette_with_preset`/`palette`
   without loaded users (`crates/thegn-host/src/handlers/onboarding.rs:175-181`
   and `:294-300`). Dismissing onboarding while a user theme is active
   therefore replaces it with the default palette until another catalog or
   config event happens. Thread the resolved palette/user catalog through
   every live theme consumer and add a test that opens/dismisses onboarding
   with `[theme].preset` naming a user theme.

## Small fixes committed during review

Commit `b587bb71` (`fix(the-7): harden theme builder failure paths`) fixes and
tests the following:

- provider-pending state can no longer be dismissed or mutated before its
  response;
- successful Apply retains the confirmed palette instead of immediately
  rebuilding from stale pre-write config;
- an imported preview must be saved before Apply can persist its name;
- explicit `--config` files are now watched for the builder's write/reload
  cycle;
- the contrast result is visible at 80 columns;
- large catalogs scroll to keep the selected theme visible, including mouse
  hit testing;
- whitespace-only imported names are rejected before conversion.
