## Exact branch evidence

### Wire contract, decoder cost, and payload cap

- The module contract says one encoded frame per WebSocket binary message and
  defines `[tag:u8][len:u32 BE][payload:len]`
  (`control_wire.rs:9-15`). `MAX_WIRE_PAYLOAD` is 1 MiB
  (`control_wire.rs:25-26`), excluding the five-byte wire header.
- `EventDecoder` stores a `Vec<u8>` (`control_wire.rs:527-532`). On each
  complete frame, `next_frame` copies the payload with `.to_vec()` and then
  drains the prefix (`control_wire.rs:558-559`). Draining repeatedly for many
  tiny concatenated frames shifts the remaining suffix each time; a message
  with N frames can incur quadratic shifting. The decoder also currently
  accepts and drains multiple frames from one push (`drain_returns_all_ready_frames`,
  `control_wire.rs:720-727`).
- `next_frame` rejects a declared payload above 1 MiB
  (`control_wire.rs:549-553`) but this happens after tungstenite has delivered
  the message. The client call sites use default configuration, so the outer
  WebSocket frame/message bound is not tied to the control-wire cap.
- `WireError` only covers unknown tags, oversized declared payload, and bad
  payload (`control_wire.rs:341-360`). Exact-message cardinality/truncation
  errors need typed variants whose display text names the observation, such as
  “binary message contained 2 frames; exactly 1 required”.

### Production client paths and confirmed deadlock

- `ControlClient::subscribe_events_opts` creates a 256-capacity
  `EventFrame` channel at `client.rs:863`, then uses default
  `client_async` for Unix/TCP or default `connect_async` for HTTP(S) at
  `client.rs:865-890`. Every successful route invokes the same
  `start_attach`.
- `ControlClient::attach_opts` creates the same 256-capacity channel at
  `client.rs:970`, uses the same default connect functions at
  `client.rs:972-996`, and invokes the same `start_attach`.
- `start_attach` reads a binary message, pushes it into `EventDecoder`, and
  drains every complete frame (`client.rs:1077-1095`). It validates protocol
  version only if the first decoded frame happens to be Hello
  (`client.rs:1110-1119`). It then loops over every decoded frame and awaits
  `frames.send(f)` (`client.rs:1120-1123`) before spawning
  `pump_attach_inner` (`client.rs:1124`) and returning. The receiver is only
  returned to the caller after `start_attach` completes (`client.rs:892-895`,
  `client.rs:999-1002`). Capacity and ordering are exactly as alleged.
- `pump_attach_inner` repeats the concatenate-and-drain policy for each
  binary message (`client.rs:1128-1158`), so strict message validation must
  be shared by bootstrap and the long-lived event/attach pump.
- The existing 10-second `HELLO_TIMEOUT` bounds how long bootstrap waits for
  the first usable greeting (`client.rs:1054-1057`); it does not prevent the
  capacity deadlock, which occurs after receiving a large first message.

### Server-side format and entry paths

- `/v1/events` upgrades into `pump_events`; it sends `hello.encode()` and each
  later `frame.encode()` in individual `Message::Binary` sends
  (`control/http.rs:1689`, `1700-1725`).
- `/v1/sessions/{session}/attach` upgrades into `pump_attach`; it sends Hello,
  then the snapshot, then each live frame separately
  (`control/http.rs:1991-2008`, `2028-2044`). Thus clean production traffic
  conforms to the one-message/one-frame contract.
- The attach client is reached by compositor panes through the host daemon
  client adapter (`thegn-host/src/daemon/client.rs:311-325` calls its
  `attach_session`, which calls `attach_opts` at `client.rs:290`); CLI attach
  also calls `attach` (`thegn-host/src/cmd/attach.rs:81`). Event subscription
  is used by the CLI (`thegn-host/src/cmd/events.rs:61`), host daemon client
  (`thegn-host/src/daemon/client.rs:138`), and plugin handler
  (`thegn-host/src/handlers/plugins.rs:834`). Both attach and event routes
  converge on the same two WebSocket functions above. No server production
  edit is indicated.

## Does the bug remain?

Yes. Both independent defects remain on this branch:

1. **Message correctness / bootstrap ordering:** both client paths accept
   concatenated frames; the greeting branch queues every frame before the
   receiver is visible and can deadlock at frame 257.
2. **Decoder complexity:** the general core decoder repeatedly copies each
   payload and compacts the entire remaining vector once per decoded frame.

Transport bounding is also missing: all six WebSocket connects use tungstenite
defaults. Set both the max frame and max message payload limits from the
control-wire maximum whole-frame size (`MAX_WIRE_PAYLOAD + 5`); confirm the
0.29 API’s exact size semantics while implementing. The limit must be applied
to Unix, TCP, and HTTP(S) setup paths for both event feeds and pane attach.

## Smallest complete fix proposal

1. In `control_wire.rs`, expose/derive the maximum encoded frame length as the
   1 MiB payload cap plus its five-byte header. Rework decoder advancement to
   use a read offset/cursor and avoid a Vec prefix shift per frame. Decode from
   the current slice; compact consumed bytes no more than once per bounded
   input batch (and reset when fully consumed), preserving arbitrary chunk
   support for the existing stream-decoder contract.
2. Add a pure core operation for decoding one complete WebSocket message. It
   must reject empty/truncated data, an over-cap declared payload, trailing
   bytes, or a second frame with typed and specific errors; it must return
   exactly one `EventFrame`. Keep transport types out of core. Both bootstrap
   and pump call this shared operation, so subscriptions and pane attach have
   the same rule.
3. In `client.rs`, construct one configured `WebSocketConfig` at all six
   connect sites, passing it through tungstenite 0.29’s configured client
   connect APIs for local sockets, TCP, and HTTP(S). Bound both individual WS
   frame payload and reassembled message payload at the encoded frame cap, so
   oversized input is refused before buffering/large allocation.
4. Make bootstrap require a single Hello frame and check `proto` before stream
   publication. A malformed/non-Hello greeting returns a typed, actionable
   error; it never queues arbitrary post-bootstrap frames. Start the pump for
   subsequent messages and only forward the validated Hello into the fresh
   channel. Remove the bulk `first` vector and its awaited send loop.
5. Keep unrelated THE-273 deadline policy, THE-184 bounded consumer policy,
   daemon handling, pane actor behavior, and other control surfaces unchanged.

## Failure cases and meaningful regression tests

Core private tests in `control_wire.rs`:

- One ordinary encoded frame decodes successfully; empty and truncated
  one-frame messages fail with named errors.
- A concatenated pair fails with a typed cardinality error naming “2 frames”.
- A declared payload of `MAX_WIRE_PAYLOAD + 1` fails before waiting for its
  body; an exactly-at-cap valid frame is accepted.
- Construct exactly 257 tiny frames (including Hello in bootstrap-shaped
  input): whole-message decoding returns promptly with the frame-count error,
  independent of channels/timing. This covers the input that formerly filled
  the 256-slot channel and blocked on send 257.
- Arbitrary byte chunks, including one-byte chunks, still decode under the
  core streaming-decoder contract. Tungstenite assembles fragmented WebSocket
  data frames into one logical `Message::Binary`; validate that completed
  message with the exact-one-frame helper. Avoid a WebSocket server or timing
  assertion.
- A many-small-frame decoder fixture exercises cursor advancement and one
  compaction per batch structurally; do not rely on elapsed-time benchmarks.

Private tests in `client.rs`:

- The bootstrap validator accepts one compatible Hello, rejects an
  incompatible version, a non-Hello first frame, and Hello concatenated with
  any extra frame with a specific diagnostic. It does not attempt a 257th
  channel send.
- The shared per-message path rejects concatenated/trailing data identically
  for the event subscription and pane attach pumps; clean one-message/one-frame
  traffic continues through both.
- Test the config helper’s frame/message limits equal the encoded-frame cap;
  no network endpoint is needed.
