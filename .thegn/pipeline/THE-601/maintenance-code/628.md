# THE-601 maintenance-code dispatch 628

verdict: revisions-needed

## Concrete design blocker

No production changes were made. The supplied primary plan contains two
decisions, but it refers to “steps 2–7” without including those steps. The issue
acceptance cannot be implemented completely without a lifecycle decision for
pipe readers that remain blocked after timeout cleanup.

`integrate_gate.rs` currently uses `Command::output()` in both the verified and
native runners, so the task's unbounded capture is confirmed. `platform::DesktopChild`
already models retained process ownership, but it does not expose a retained
exit status for gate verdict classification. The Windows implementation also
falls back to direct-child ownership when Job Object setup fails.

The missing decision is what the gate should do if a descendant survives or
escapes process-group/job containment and retains stdout/stderr after termination
was requested. The reader cannot be joined until the writer closes its pipe.
Detaching the reader violates the task; releasing the reused workspace lock
allows a later gate to use files while the previous workload still runs. Waiting
for pipe settlement preserves ownership but can block indefinitely, including
for an escaped descendant or a process stuck in uninterruptible I/O. The primary
plan says to describe OS/filesystem blocking honestly, but does not state which
of these operational outcomes is intended or whether containment setup failure
must refuse the gate before spawn.

Please specify the required policy for this case and for Windows containment
setup failure. Until then, implementing a return-on-timeout path would silently
violate at least one acceptance criterion. The approved decisions about
`gate_timeout_secs`, `gate_setup_timeout_secs` (both default `0`, disabled) and
no caller cancellation token are understood and do not resolve this reader and
ownership lifecycle.
