## Scope and findings

Implemented the primary revision-4 fix on
`blake/the-316-propagate-jira-transition-failures-instead-of-returning`.
The task data exists at `.thegn/maintenance/THE-316/issue.json`; the
prompt's root-level `.thegn/maintenance/issue.json` path is absent in this
checkout.

The shared cause of the reported Jira failures was the HTTP diagnostic shape:
the tracker client emits `jira HTTP <code> <reason phrase>`, while Jira's
definitive-rejection parser tried to parse the entire suffix as a number. That
made definitive 400/404/409/422 transition failures look ambiguous, and the
tests also expected code-only messages. There is no design blocker in the
authorized scope.

## Implementation

- Jira transition classification now parses the leading bounded HTTP status
  code and retains the approved 400/404/409/422 allowlist; auth errors remain
  definitive for 401/403.
- Regression assertions now inspect the actual typed error value and exact
  bounded status diagnostic, rather than using silent `matches!` predicates.
- Added coverage for both code-only and reason-phrase status diagnostics,
  while retaining tests for typed partial-update fields, request ordering,
  retryability, and secret-body redaction.
- Only `crates/thegn-svc/src/issue/jira.rs` and this dispatch artifact changed;
  `crates/thegn-svc/src/issue/mod.rs`, the control wire, and
  `docs/api/control-v1.json` were untouched.
