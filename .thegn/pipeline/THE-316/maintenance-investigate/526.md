## Defects that remain on this branch

### 1. Successful transition is not semantically verified

`update_issue` resolves a target category at `jira.rs:578-592`, posts the transition at `jira.rs:602-611`, then optionally updates the title at `jira.rs:614-634` and fetches the issue at `jira.rs:636-642`. The fetched `JiraIssue` is converted and returned, but its status is never compared with the requested target.

The comparison must use Jira’s semantic `statusCategory`, not domain enum equality: `jira.rs:211-221` maps Jira `new` to `Todo`, `indeterminate` to `InProgress`, and `done` to `Done`; both `Backlog`/`Todo` target `new` (`jira.rs:579-580`), and both `Done`/`Cancelled` target `done` (`jira.rs:581`). A final fetch with a different category can therefore currently return `Ok` even after a 2xx transition response.

### 2. Multi-field partial-write behavior is undefined

The current order is status first (`jira.rs:574-612`), then title (`jira.rs:614-634`). Jira has no transaction for these independent mutations. If the transition succeeds and the title PUT fails, the method returns an error without telling the caller that status landed. If title succeeds and a future/order-changed status operation fails, the same information gap exists in the opposite direction.

The primary coordination decision is to use title first (cheap, idempotent, reversible), then status (workflow-gated and potentially irreversible), and to return an explicit per-field result on partial failure so the caller can retry idempotently. The final status fetch should verify the requested category before returning success.

### 3. Transition lookup error has weak context

The lookup request itself is correctly propagated by `jira.rs:576-577`. A successful lookup response with no matching category becomes `IssueError::Api("Jira transition target unavailable")` at `jira.rs:583-592`. It does not identify the requested semantic status/category or issue key. This is bounded and contains no provider body, but should be improved to name the target category/status while retaining the existing typed error for lookup HTTP failures.

### 4. No other Jira swallow pattern found

The Jira file has no remaining `unwrap_or(serde_json::Value::Null)` transition path. The shared HTTP layer intentionally discards response bodies for empty mutations and reports only bounded, non-raw context (`http.rs:318-360`); this is compatible with the coordination requirement not to expose raw provider bodies or credentials.

### Callers

- Control API: `POST /v1/issues/{id}` is registered as `issues.update` (`crates/thegn-svc/src/control/routes.rs:87-93,188-191`); `control/http.rs:1225-1241` authenticates and validates the ID, then `daemon/service.rs:1700-1711` routes through `IssueRouter` and returns an internal error on failure. - Tracker panel assignment: `crates/thegn-host/src/handlers/tracker.rs:172-207` sends an assignee-only patch off-loop and surfaces errors through the warning/status channel. It does not exercise Jira status transition logic, but shares the same `update_issue` seam.

## Smallest complete implementation plan

1. Add/centralize a small Jira status-category target helper so `Backlog`/`Todo` and `Done`/`Cancelled` retain their existing category equivalence. Improve the unavailable-transition message with the bounded issue key and requested category/status; do not include provider response bodies.
2. In `JiraBackend::update_issue`, apply title first, then resolve/post the status transition. Preserve direct propagation of lookup and POST errors, including auth/network/timeout/API classification. Track each field’s outcome so a failure after a prior mutation reports which field(s) were applied and which remain unapplied.
3. Re-fetch the Jira issue after requested mutations. If a status was requested, inspect the returned Jira status category and return an error if it does not equal the requested category. Only return `Ok(Issue)` after this verification; title success remains represented by the successful PUT plus returned issue data.
4. Primary review must choose the error representation. The existing `IssueError` (`crates/thegn-svc/src/issue/mod.rs:27-79`) has no partial-update variant. Recommended: add a narrow structured partial-update wrapper that contains applied field names and the original boxed `IssueError`, with Display/Debug bounded and `SeamError` classification delegated to the source. If the strict `jira.rs`-only scope forbids that enum support, the fallback is a bounded `IssueError::Api` message, but that loses the original typed classification and should be explicitly accepted before implementation.
5. Keep the change Jira-specific. Do not alter `IssueRouter`, control routes, autopilot state machines, or the generic field-capability work named by related issues.

Required cases, with request sequencing assertions:

1. Transition lookup HTTP error: return 5xx from `GET /rest/api/3/issue/PROJ-1/transitions`; assert the typed error reaches the caller and no mutation/final fetch occurs.
2. Transition POST HTTP error: return a matching transition from lookup, then 4xx/5xx from POST; assert the error is propagated, bounded, and no false success is returned.
3. Empty/204 transition response: return 204 from POST, then a final issue in the requested category; assert success and that the final GET ran.
4. Unavailable transition: return a valid lookup payload with no matching category; assert a bounded error names the requested category/status and no POST occurs.
5. Stale transition ID: return a matching lookup entry with a stale ID, then 404 from POST; assert the POST error is visible and no final success fetch is treated as proof of mutation.
6. Semantic verification: return 2xx from POST but a final issue in a different category; assert an error rather than `Ok`. Include the category-equivalent `Backlog`/`Todo` or `Done`/`Cancelled` behavior so verification does not reject the existing domain mapping.

8. The coordination brief literally requests partial-failure coverage in both title-then-status and status-then-title order. Because the primary decision selects title-then-status, primary review must confirm whether the complementary status-first case is a contract/helper test (recommended) or whether the order requirement should be narrowed. Do not silently restore status-first production ordering just to satisfy that wording.
9. Success path with title and status: assert request order, final GET execution, returned title, and verified target category.
