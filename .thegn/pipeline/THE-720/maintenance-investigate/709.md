## Evidence: the defect remains

The overlay already exists and is narrowing by design:

- `crates/thegn-core/src/config_issues.rs:329-397`: `IssuesOverlay` can constrain providers, account names, Linear team, Jira project, and Kaneo workspace/project. Applying `accounts = []` marks accounts restricted so legacy synthesis cannot bring them back (`:376-380`).
- `crates/thegn-core/src/config.rs:6878-6889`: `Config::repo_issues(Some(root))` clones global issues config and applies the repo overlay; `None` returns global configuration.
- Existing tests in `config_issues.rs` and `config_tests.rs` cover overlay merge and that repo overlays cannot inject tracker accounts (including the named issue test `repo_overlay_cannot_inject_tracker_accounts`, referenced by the issue description). They test the config rule, not all production callers.

The listed caller failures are direct global-config use:

1. Tracker-mode `thegn issue list`: `crates/thegn-host/src/cmd/issue.rs:140-160` builds `IssueRouter::from_config(&cfg.issues)`. `run` has no cwd repo resolution (`:50-105`). This mode is selected by `--status` or `--limit`; the default forge `gh` listing is a separate path.
2. Kaneo project/board/task operations: `crates/thegn-host/src/cmd/kaneo.rs:86-114` forwards global `Config`, and `router` constructs from `cfg.issues`; `projects` uses it at `:136-159`, and `board` resolves its default project from `cfg.issues.kaneo.project_id` before building the router (`:162-180`). Create/comment/label/move also use this router (functions found at `:220-275`). Thus both provider/account restrictions and repo-pinned Kaneo project defaults are bypassed.
3. Control API: `crates/thegn-host/src/daemon/service.rs:1728-1809` builds from `self.config.issues` independently in `issues_list`, `issues_get`, `issues_update`, and `issues_comment`. HTTP handlers currently carry no repo context: `crates/thegn-svc/src/control/http.rs:1207-1318` has list query fields status/limit/project/query, while get/update/comment take only issue id and body. The service seam likewise has no repo argument (`crates/thegn-svc/src/control/mod.rs:1063-1095`). By contrast, `worktree_create` resolves a repository and uses `cfg.repo_issues` off the async runtime thread (`crates/thegn-host/src/daemon/service.rs:1870-1902`).
4. Related hydration mutation: `crates/thegn-host/src/hydrate.rs:3858-3882` handles opt-in `move_on_merge`, but constructs the issue update router from `&cfg` at `:3865`. When a PR merges and linked issue IDs exist, this global router can update an account/team that the repo overlay excludes. This is directly in the bug's restriction-bypass class and should use the worktree's repo-resolved issue config. It is already in a background refresh closure, not the UI loop.

## Production call paths and prerequisites

### Control API

Suggested wire spelling: `repo=<path>` as an optional query parameter on `GET /v1/issues`, `GET /v1/issues/{id}`, `POST /v1/issues/{id}`, and `POST /v1/issues/{id}/comment`. Carry it through `thegn-svc::control::ControlApi` into daemon service. Keep it separate from `IssueFilter.repo`, which is an existing GitHub `owner/repo` filter (`crates/thegn-core/src/issue.rs:135-149`), not a filesystem context.

When supplied, resolve the path to its main worktree and apply `Config::repo_issues(Some(root))`. Do path/git resolution and overlay reads via `spawn_blocking`, matching `worktree_create`; never add blocking work to the event loop or async runtime worker. An explicitly supplied path that is not a repository should return an argument error rather than silently falling back to global scope. When omitted, do not infer the daemon process cwd: preserve global behavior as the acceptance criteria require.

Propagate the optional argument through `crates/thegn-svc/src/control/client.rs` convenience methods so local callers can express the scope. Generic `thegn api call` already addresses the same routes through `API_CALLS` in `control/routes.rs:167-191`; routes/capability identities and catalog surfaces remain unchanged.
