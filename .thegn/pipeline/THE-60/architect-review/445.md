## Blocking findings

1. Remote activation performs synchronous SSH/provider detection, identity
   reads, binary/shims probes, and approved environment resolution from
   `activation_for_launch`; the ordinary `spawn_worktree_shell_pane` path calls
   that launch builder on the event loop. This can block pane creation for the
   transport timeout and violates the repository's no-blocking-I/O loop rule.
2. Target-derived remote `mise.env` requests are never surfaced by
   `repo trust`: the handler skips remote requests and the CLI builds pending
   state from the local root. A remote/provider checkout without a local copy
   therefore cannot be approved through the supported trust flow, so its env
   activation and target install remain permanently denied.
3. The local background resolver writes its cache without the required refresh
   channel delivery or `TerminalWaker` pulse, leaving launches/UI stale until
   an unrelated refresh.
4. Hydrated status never reports missing tools or resolver degradation: its
   `missing_tools` is always empty and a failed/cold approved resolve is shown
   only as generic `shims`, contrary to the design's presence-only status
   contract.

These are functional architecture/security-boundary gaps, so I am not applying
small style corrections or opening an approval-with-notes. The required fixes
and focused tests are in revision 2.
