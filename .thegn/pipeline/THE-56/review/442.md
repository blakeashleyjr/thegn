# THE-56 security/test/bug review — row 442

## Verdict

FAIL — not ready for the merge queue.

## Findings

1. **High — untrusted issue content reaches an unsandboxed, credential-bearing agent.**
   `crates/thegn-host/src/autopilot_driver.rs:222-230` runs `TaskKind::Issue` with
   `sandbox: None`. `crates/thegn-host/src/agent_run.rs:135` therefore launches
   the configured command via `sh -lc`, and `:139-155` never clears or
   allowlists the inherited environment. The command can consequently see
   ambient `GH_TOKEN`/`GITHUB_TOKEN`, SSH agent access, and other credentials.
   The issue body is included in the rendered prompt (`TaskKind::Issue` permits
   `issue_body`), so a malicious issue can prompt the agent to run `gh`, `git
push`, `curl`, or equivalent remote-write/exfiltration commands. The later
   branch/cleanliness checks do not undo a remote action already performed by
   the agent. Run issue workers behind a credential-free isolation boundary (or
   an explicit capability broker) and add a regression test proving issue
   workers cannot inherit credential-shaped variables.

2. **Medium/High — durable journal failures are swallowed, leaving orphaned or
   permanently active runs.** `autopilot_driver.rs:113-114` ignores worktree
   linkage/update failures, `:142` ignores dispatch attachment failure, and
   `:316-322` ignores `set_autopilot_pr`. In particular, if PR creation succeeds
   but `set_autopilot_pr` fails, the run still transitions to `PrOpened`; the
   merge callback searches by the missing PR correlation and cannot close the
   run or perform `done_on_merge`. Dispatch status updates and several state
   transitions are also discarded at `:231`, `:342`, and `:352-369`. Convert
   required journal writes to surfaced `NeedsHuman` failures and add injected
   DB-failure tests for each post-claim checkpoint.

3. **Medium — one matched issue blocks the tracker refresh worker for the full
   agent timeout.** `crates/thegn-host/src/hydrate_tracker.rs:125-136` calls
   `autopilot_driver::pickup` directly from the refresh worker, while
   `drive_claim` synchronously calls `agent_run::run` at
   `autopilot_driver.rs:222`. A hung/default 1800-second agent therefore
   prevents that worker from refreshing later accounts/providers. The database
   `max_concurrent` limit does not provide worker isolation. Dispatch the run
   onto its own bounded background worker and test that refresh remains
   responsive while an agent is blocked.
