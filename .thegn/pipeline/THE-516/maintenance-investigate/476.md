## Bug still present: exact evidence

### Lossy branch-to-path and branch-to-tab conversion

`crates/thegn-core/src/util.rs:76-90` defines `slugify` as ASCII lowercase,
non-alphanumeric-to-`-`, repeated-dash collapse, and trim. Therefore valid
branch labels such as `feat/a`, `feat-a`, `feat_a`, and `FEAT-A` all reduce to
`feat-a`; a Unicode-only label can reduce to an empty component; long labels
are not bounded. This is a display transform, but it is still used as
authority.

`crates/thegn-core/src/worktree.rs:129-151` slugifies human input for the Git
branch candidate and only de-duplicates the resulting exact branch name against
Git. It does not reserve or validate the derived checkout path. The path helper
at `worktree.rs:193-203` then maps every exact branch to:

- in-repo: `<repo>/.worktrees/<slugify(branch)>`;
- external: `<worktrees_dir>/<repo_name(root)>/<slugify(branch)>`.

Thus two exact branches can target one path. External mode additionally uses
only the repository basename, so two roots ending in the same name share the
same namespace. There is no manifest or claim record checked before
`add_checked_with_state` (`worktree.rs:236-285`) creates the checkout.

`crates/thegn-core/src/repo.rs:111-115` maps a repo and exact branch to
`<repo-slug>/<slugify(branch)>` via `branch_tab`. The DB row is keyed by the
filesystem path, not an opaque worktree identity (`crates/thegn-core/src/db.rs:
1410-1421`; `crates/thegn-core/src/models.rs:196-223`). Multiple rows can carry
the same `tab_name`; `db_workspace.rs:550-567` resolves a `(session, tab)` with
`LIMIT 1`, so a collision can route panel/session work to the wrong checkout.

### Repository slug fail-open

The DB does have transactional basename collision suffixing in
`crates/thegn-core/src/db_workspace.rs:116-150`, but both authority helpers
discard its errors:

- `crates/thegn-core/src/repo.rs:83-104`: `repo_slug` and `repo_slug_with`
  return the unsuffixed basename on DB open/lookup failure.
- `crates/thegn-host/src/hydrate.rs:646-653`: no DB synthesizes a basename
  home tab.
- `crates/thegn-host/src/hydrate.rs:889-924`: a workspace-row lookup error
  falls back to the basename slug and continues building the sidebar.
- `crates/thegn-host/src/merge_lifecycle.rs:253-265` builds a basename fallback
  before assigning a slug for an unregistered worktree; the unattended cleanup
  path at `merge_lifecycle.rs:429-442` also derives a raw basename slug.

Consequently two same-basename repositories that are normally `app` and
`app-2` can collapse to `app` during DB contention/corruption or a missing DB.
The fallback is acceptable for read-only presentation only; it is unsafe for
registration, routing, cleanup, or mutation.

### Feature identity remains derived from lossy equality

`crates/thegn-core/src/project.rs:8-25` explicitly says cross-repo membership
is branch-name equality and implements `feature_branch_name` as
`branch_prefix + slugify(feature)`. The persisted project schema contains only
the human project name and nullable workspace membership
(`crates/thegn-core/src/db_migrate.rs:520-543`; `store/project.rs:41-67`); it has
no feature-instance ID or persisted per-repo membership for a feature.

`crates/thegn-host/src/cmd/wt.rs:401-419` resolves one lossy branch string for
all member repositories, and `project.rs:139-162` tests that this remains tied
to `human_base`. Distinct proposed features such as `payments/retry`,
`payments-retry`, and `PAYMENTS_RETRY` therefore federate as one branch feature.

### Rename is still split-brain

`crates/thegn-core/src/worktree.rs:422-467` derives the destination from the
lossy path helper, runs `git branch -m`, then runs `git worktree move`; a failed
move returns an error after the branch has already changed. The comment
documents the split state rather than rolling it back or journaling it.

`crates/thegn-host/src/handlers/worktree_rename.rs:29-64` performs the Git
operation off-loop, and `:67-106` updates the live group and DB only after
success, with a best-effort DB write. The wizard has the same behavior at
`crates/thegn-host/src/wizard.rs:1326-1389`, and explicitly re-keys sandbox
preparation from the moved path. A destination pre-creation or DB failure can
therefore leave Git, filesystem, DB/tab, and provider state describing
different identities.

## Production call paths and prerequisites

All creation surfaces reach the same lossy helpers but do not share an identity
allocator:

1. TUI wizard: `wizard.rs:1201-1227` chooses/dedupes the branch and allocates
   `worktree_path`; `wizard.rs:1394-1417` derives the final `branch_tab` and
   registers the row. Optimistic UI uses the same pair in
   `handlers/creating.rs:98-143` before the DB row exists.
2. Headless CLI: `cmd/wt.rs:252-305` uses `worktree_path` then
   `branch_tab`; `cmd/wt.rs:401-419` derives project features before calling
   that path for every member.
3. Control/daemon: `daemon/service.rs:1813-1862` handles `worktrees.create`,
   computes the path and tab, and writes the cache row.
4. Tracker dispatch: `handlers/tracker.rs:248-281` derives an issue branch and
   path; `:351-385` derives its tab and registers it.
5. Autopilot: `autopilot_driver.rs:112-142` derives branch/path/tab before
   linking issue and dispatch rows.
6. Lifecycle/merge: `merge_lifecycle.rs:247-265` synthesizes a tab while
   filing an externally-created worktree; `worktree_lifecycle.rs:990-1020`
   derives a slug during rollback/destruction. These are authority-bearing
   cleanup paths, not labels.
7. Hydration/session/sidebar: `hydrate.rs:646-707` and `:889-955`,
   `session.rs:442-468` and `:751-768`, and `sidebar.rs:551-555` use repo/tab
   prefixes to resurrect, group, parse, and reconcile worktrees. `split_tab`
   is a parser for a string that currently doubles as identity.
8. Provider/sandbox consumers: `provider_factory.rs:376-410` resolves provider
   sandbox names from the worktree path, while `agent.rs`, `hibernator.rs`,
   `share.rs`, and `sandbox_events.rs` use those names for attach, teardown,
   hibernation, sharing, and event reverse lookup. The current provider names
   include a path hash, but the path is already collision-prone and is not a
   persisted worktree generation.

Required prerequisites before implementation can be considered complete:

- Choose and document versioned canonical encodings for repository identity,
  raw Git branch/ref bytes, worktree admin identity, worktree ID/generation,
  and feature ID. `String`-only branch fields and lossy Git porcelain parsing
  (`worktree.rs:368-373`) cannot satisfy the non-UTF-8 acceptance case.
- Add a schema migration and a compatibility/read-only policy for old rows.
  Git worktree metadata, DB rows, tab groups, cache rows, sandbox/provider
  bindings, hibernation records, queue/autopilot rows, and lifecycle records all
  need an exact claimant before a legacy path/tab is reused.
- Decide the repository canonical source (at minimum canonical Git common-dir
  plus worktree admin identity; remote URL alone is not a clone identity) and
  how moving/cloning a repository affects the ID. This is currently not
  represented by a shared core type.
- Coordinate consumers that are explicitly blocked in the captured relations:
  THE-262, THE-513, and THE-514 must consume the generation rather than invent
  route/path keys. THE-520, THE-518, THE-543, and THE-528 similarly should use
  the same identity when their changes land. THE-557 needs the migration
  quarantine rules for pre-existing worktrees.

## Smallest complete fix

The smallest safe fix is one shared canonical identity/claim layer, not an
isolated hash replacement in `worktree_path` or `branch_tab`:

1. Add typed, versioned `RepositoryId`, `BranchRef`, `WorktreeId` plus immutable
   `WorktreeGeneration` and `FeatureId` in core. Keep raw ref/path bytes and
   separately expose bounded display labels; retain `slugify` only for labels.
2. Add a DB migration with opaque worktree/generation keys, canonical repo ID,
   exact branch-ref encoding, Git worktree-admin identity, manifest path/owner,
   and feature-instance membership. Make these the uniqueness/foreign-key
   columns; retain old path/tab columns only as compatibility labels during
   migration.
3. Centralize allocation under a per-repository mutation lock. Allocate a
   bounded `<repo-id>/<worktree-id>-g<generation>` path (in-repo and external
   modes), create an atomic manifest binding exact repo/common-dir, admin ID,
   raw ref, owner, and generation, and refuse pre-existing, ambiguous,
   symlink/relative-alias, or manifest-mismatch paths. Revalidate immediately
   before remove/move/cleanup.
4. Route wizard, CLI, daemon/control, tracker, autopilot, project, and external
   worktree registration through that allocator. Render repo/branch labels only;
   pass the opaque generation through tab groups, DB lookups, messages, queue
   rows, sandbox/provider names, share/hibernation state, and cleanup. Remove
   authority-bearing `split_tab` parsing and `LIMIT 1` tab routing.
5. Replace rename with a journaled transaction over branch ref, Git worktree
   move, manifest, DB/tab row, and dependent bindings. Lock old and new
   identities, refuse a claimed destination, roll back when possible, and
   persist a recoverable exact split state when rollback is impossible. Never
   report success after only `git branch -m`.
6. Give each project feature an explicit `FeatureId` and persisted member rows.
   A human alias/branch label may suggest a ref but cannot create federation by
   normalized string equality. Preserve existing project UI/CLI names as
   labels, so this is maintenance of authority rather than a new user feature.
7. Migrate legacy rows by enumerating Git worktree metadata and claimants. Map
   only unambiguous exact paths/admin IDs; quarantine collisions and require an
   explicit mapping. On DB failure, authority operations fail closed; read-only
   hydration may show a last-known exact label but must not fabricate `app` or
   register/mutate under it.

## Meaningful regression tests (ordered)

1. Core pure identity tests: slash/dash/underscore/case aliases, Unicode,
   empty/overlong display labels, and exact raw branch refs produce distinct
   opaque IDs and bounded distinct allocation paths.
2. Platform/ref tests: Git-valid non-UTF-8 refs where supported remain exact;
   unsupported platforms return a typed refusal. Relative paths, symlink aliases,
   same-basename repositories, and path-component limits are covered.
3. Claim/manifest tests: pre-created destination, symlink/path swap, manifest
   mismatch, missing/corrupt manifest, duplicate claim, and concurrent create
   all refuse safely and never delete or reuse another claimant.
4. DB migration tests: legacy rows map by exact Git metadata; ambiguous paths or
   duplicate tab strings are quarantined; DB open/lookup failure cannot produce
   an unsuffixed authority slug; read-only presentation uses only last-known
   exact mappings.
5. Routing tests: all create doors register the same opaque generation; two
   colliding labels remain separate in tab/sidebar/panel lookup, cache rows,
   sandbox/provider identity, issue/autopilot linkage, and cleanup.
6. Rename fault-injection tests: failure/crash after branch rename, after
   worktree move, after manifest publish, after DB update, and after provider
   update leaves either the old or new generation recoverable, or a clearly
   journaled exact split state; a stale completion cannot mutate a new
   generation.
7. Feature tests: two feature aliases that normalize alike retain separate
   `FeatureId` membership and cannot cause cross-repo commits/merge/cleanup to
   join; re-open/resume preserves the same membership.
8. Existing targeted suites to extend (without broad execution during this
   investigation): `thegn-core` worktree/project/DB tests, host
   `worktree_rename`, hydration/session, merge lifecycle, sandbox-event, and
   tracker/autopilot tests. Add one end-to-end smoke scenario only after the
   core/host identity tests are green.

## Unresolved dependencies and risks

- The exact canonical repository identity algorithm is a design decision; a
  path hash alone does not survive aliases/moves, while a remote URL is not
  unique across clones.
- Git ref byte preservation requires changing branch/ref transport and parser
  seams beyond the current `String` fields; do not claim the acceptance case is
  covered by a lossy `to_string_lossy` display path.
- The DB is deliberately a cache today, but THE-516 requires an authority
  manifest/claim store. The implementation must define startup behavior while
  the DB is locked/corrupt and must not silently fall back to legacy slugs for
  mutation.
- Existing issue relations (THE-262, THE-513, THE-514 and the other consumers in
  the capture) should be held until they consume this typed generation. This
  branch has no reviewed implementation to cherry-pick or merge.
