## Findings

### 1. High — failed old-ledger rebuild can hide claims on retry

`crates/thegn-core/src/db_migrate.rs:937-986` rebuilds an old partial-v69
`worktree_instances` table by dropping indexes, renaming the old table, creating
the new CHECK-constrained table, copying rows, and finally dropping the old
table. The sequence is not enclosed in a transaction. If one malformed or
ambiguous legacy row fails the copy, SQLite leaves both
`worktree_instances_v69_legacy` and the new table behind. On retry,
`ledger_exists` is true and `operation_revision` exists on the replacement, so
the rebuild branch is skipped (`:929-990`); support indexes and verification
can then succeed against an empty/partial replacement while the old claims are
stranded and invisible.

This violates the primary requirement that old/partial-69 migration fail closed
without silently losing or fabricating authority. I reproduced the exact SQLite
state with a focused non-Cargo script: a one-byte legacy `instance_id` fails the
new CHECK, leaves both tables, and leaves zero rows in the replacement.

A test-only regression was added at
`crates/thegn-core/src/db_migrate.rs:2426-2459`:
`failed_v69_ledger_rebuild_cannot_hide_claims_on_retry`. It is intentionally
expected to expose the current defect until the migration is made atomic or
the stale rebuild state is explicitly recovered/refused.

Required correction: make the rebuild atomic with a recoverable transaction, or
detect and quarantine/refuse every stale `_v69_legacy`/replacement pair before
any retry can stamp or accept v69. Preserve all original claims for explicit
recovery; do not drop or ignore the legacy table.

### 2. High — canonical foundation is not on any authority-bearing call path

The new APIs are currently exercised only by their unit tests, not by creation,
attach, registration, routing, cleanup, or rename callers. The ledger methods
are defined in `crates/thegn-core/src/db_worktree_identity.rs:295-517`, and
inspection is defined in `crates/thegn-core/src/worktree.rs:51-131`, but the
existing doors still use lossy/path authority:

- `crates/thegn-core/src/worktree.rs:466-475` maps every exact branch through
  `slugify` and basename-only external repository directories.
- `crates/thegn-core/src/repo.rs:124-155` keeps slug-derived repository/tab
  keys, including `branch_tab`.
- `crates/thegn-core/src/db_workspace.rs:550-568` still resolves a tab with
  `(session_name, tab_name) ... LIMIT 1`.
- `crates/thegn-core/src/project.rs:18-24` still defines feature identity as
  the lossy `slugify(feature)` branch label.

Therefore `feat/a`, `feat-a`, and `feat_a` still collide in live worktree/tab
behavior, same-basename repositories still depend on the old slug registry,
and the new ledger cannot prevent a caller from opening or mutating an
ambiguous legacy path. This is an explicit deferred full-issue gap rather than
an accusation that chunks 1–2 were supposed to complete later chunks, but it
means the full THE-516 acceptance criteria are not met.

### 3. High — DB failure still fails open to an ambiguous repository slug

The issue’s additional evidence remains present in
`crates/thegn-core/src/repo.rs:124-145`: both `repo_slug` and `repo_slug_with`
return the unsuffixed basename-derived slug when DB open/lookup fails. This
reintroduces the exact same-basename collision during contention or corruption,
and downstream callers continue to use that value for tab/sidebar grouping.
The canonical repository ID API at `repo.rs:19-41` does not replace these
callers or make authority resolution fallible. Authority-bearing callers must
refuse or use a verified last-known exact mapping; they must not synthesize the
basename fallback.

### 4. High — rename remains a non-recoverable split mutation

`crates/thegn-core/src/worktree.rs:695-740` still computes a slug-derived
destination, renames the Git branch first, then calls `git worktree move`.
When the move fails, it returns an error while leaving the branch renamed and
the checkout at the old path. There is no journal, rollback, generation/revision
publication, DB/tab update, or recoverable split-state record. This directly
fails the full acceptance criteria for destination pre-creation, path swap,
`git worktree move` failure, DB failure, and crash recovery. It is listed as a
later deferred chunk by the primary instructions, so it must remain visibly
unverified rather than be treated as fixed by the new types.

### 5. Medium — regression coverage is not yet strong enough for the stated

bounded-ownership contract

The current tests in `crates/thegn-core/src/util.rs:1422-1481` cover one idle
child, one oversized output, one inherited-pipe timeout, a direct budget unit,
and one injected reader setup failure. They do not deterministically exercise
repeated saturation while asserting the bounded reader/child population,
spawn failure reclamation, successful completion reclamation through the real
capture path, or the leader-EOF/reader race. The process/reader budget is also
global static state while these tests run in the normal parallel test harness,
so the direct two-slot assumptions can interfere with sibling tests.

The primary’s requested platform matrix remains unproven: no macOS or Windows
compile/runtime validation establishes birth-time precision, native path/ref
preservation, or the documented Windows direct-child-only cleanup limitation.
