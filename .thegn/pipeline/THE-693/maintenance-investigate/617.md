## Bug status on this branch

The bug remains as a production behavior. The coordination brief records the
primary's CMS measurement: 11 merged worktrees, zero tracked edits, and one
non-ignored untracked item, `?? .claude/`; each was refused as “edited since
landing”. The exact-branch code confirms the refusal path:

1. `crates/thegn-host/src/merge_cleanup.rs:611-622` runs
   `git status --porcelain=v1 -z --untracked-files=all --ignored=matching`.
2. `observe_status` at `merge_cleanup.rs:528-554` accepts only `!! <path>`.
   Every other well-formed record, including `?? <seeded path>`, returns
   `Refusal::Dirty`.
3. `Refusal::Dirty` renders as `edited since landing` at
   `merge_cleanup.rs:354-367`.
4. `merge_lifecycle.rs:368-375` converts it to `CleanupOutcome::KeptDirty`.
   The sweep and CLI report that outcome as “edited since landing” at
   `merge_sweep.rs:377-381` and `cmd/merge.rs:574-575`.
5. `merge_sweep.rs:213-217` shows that `--force` bypasses only the TTL clock;
   it still reaches the same dirty admission guard. `remove_checked` also
   deliberately calls `git worktree remove` without `--force` at

The repository-local contrast is reproducible without a build: this worktree's
`.claude/commands` and `.claude/skills` are hidden by committed

## Seeded-path authority finding

There is not currently one complete authority for everything the primary
observed as “thegn-seeded”:

1. Core `SkillRegistry` plus the harness seam owns embedded skill metadata and
   native skill roots.
2. Host `MQ_COMMANDS` separately owns two Claude command paths.
3. The OpenSpec dev-shell writer owns its generated `.claude/commands/opsx` and
   related skill output outside the shipped Rust seeder.

The cleanup fix must not invent a broad `.claude/*` allowlist. A path is safe to
classify as tool state only when it comes from the same exact authority as the
writer and its bytes still prove managed ownership. An unknown file under a
known directory, a modified managed file, or a path from a writer not included
in that authority must remain protected user work (or an explicit
unrecognized-tool-state refusal), never silently become clean.

## THE-440 interaction and direction decision

THE-440's required implementation says, verbatim:

> “Do not mutate repository-controlled harness settings as an implicit launch
> side effect. Prefer a host-owned, per-session, immutable settings overlay or a
> harness-native command/environment mechanism outside the candidate tree.”

Its acceptance criteria also require a normal permissioned launch to leave
`git status --porcelain=v1 -z` byte-for-byte unchanged. THE-440 implemented
that principle for agent permissions with command-scoped Claude settings and no
worktree write (`a290654b`); it does not authorize another implicit shared
repository mutation.

### Recommended: direction 1, exact seeded-state classification

Teach the cleanup status admission about thegn-owned seeded files, but derive
the set from a shared seeder authority and validate bytes/markers. Keep the
existing `!!` ignored-only handling. Classify every status record before
accepting the tree: seeded-only is removable; any tracked change, ordinary
untracked path, modified seeded file, or unknown generated path keeps the
worktree. This is the smallest complete fix for the observed non-ignored CMS
case and preserves deletion safety.

The authority should expose the exact managed relative files for the effective
config/harness/gate state, including the MQ command table, rather than letting
`merge_cleanup.rs` duplicate `.claude`, `.agents`, or `.pi` literals. It should
also expose the expected managed content/hash so a user edit to a formerly
seeded file cannot be mistaken for tool state. The status scan must aggregate
all records; it must not return clean after seeing the first seeded path.

### Rejected: direction 2, add more `.git/info/exclude` entries

This is already partially implemented for runtime skill/MQ outputs by
`exclude_locally`, and it explains why this repository often hides the problem.
It is not complete for the OpenSpec-generated files, and it makes the common
Git directory a shared mutable side channel for all worktrees. It would also
preserve the current failure mode whenever seeding or exclude update fails.

Reject it as the THE-693 fix because it hides rather than proves tool ownership,
can affect sibling worktrees, and conflicts with the THE-440 no-mutation
principle quoted above. Do not change target repositories' committed
`.gitignore` files. The existing exact exclude behavior should remain covered
as legacy compatibility, but it must not be expanded into a blanket
`.claude/*` workaround.

## Failure cases and safety requirements

- Seeded-only content in a repository that ignores it: preserve existing
  THE-686 ignored-only sweep behavior.
- Seeded-only content in a repository that does not ignore it: classify all
  known, unmodified managed files as tool state and sweep after TTL.
- Seeded content plus a genuine untracked user file: refuse in both normal and
  forced sweeps; retain the worktree and queue evidence.
- Seeded content plus a tracked modification: refuse in both modes.
- A formerly managed file with user edits: refuse as genuine user work; do not
  trust its path alone.
- An unmarked, malformed, symlinked, or unknown file in a seeded directory:
  preserve/refuse. Never use a directory-wide wildcard.
- Seeded-only status that changes between probe and final removal: revalidate
  with the same authority and return `Changed`; never remove on a stale
  classification.
- A status parse error, filter-driver refusal, skip-worktree/assume-unchanged
  entry, submodule, identity mismatch, resource ownership, or queue change:
  preserve all existing fail-closed behavior.
- `--force` may bypass only TTL. It must not bypass status, identity, resource,
  or user-work protection.
