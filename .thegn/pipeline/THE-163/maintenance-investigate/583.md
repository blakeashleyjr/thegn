## Exact evidence that the bug remains

The issue's `run.rs:11347` citation is stale. The corresponding live code is
now `crates/thegn-host/src/run.rs:11724-11738`:

```text
handlers::plugins::drain(...) -> bool
model.plugin_segments = statusbar_views(...)
bars_dirty = true
dirty = true
```

`dirty` is the broad chrome/overlay/geometry channel, while `bars_dirty` is an
incremental channel. Both are armed for every plugin drain that reports a
repaint, including a content-only statusbar `update`.

The render decision is assembled at
`crates/thegn-host/src/run.rs:12798-12806` and
`crates/thegn-host/src/run.rs:13066-13076`:

- `have_damage` includes `dirty`, `bars_dirty`, pane damage, and sidebar damage.
- `Damage { chrome: dirty, bars: bars_dirty, ... }` is passed to the pure plan.

`crates/thegn-host/src/render_plan.rs:135-151` checks `damage.chrome` before
the bars channel. Therefore `{ chrome: true, bars: true }` returns
`RenderPlan::Full`; the plugin update reaches the full render branch even
though the changed content is in the statusbar.

The full branch then clears/recomposes the screen (`run.rs:13300+`), whereas
the existing incremental branch (`run.rs:13206-13299`) reuses `scratch`, draws
only damaged chrome regions, and adds bounded diff rectangles. Its current
bars path redraws masthead and statusbar and pushes those two 1-row rects at
`run.rs:13285-13294`.

## Failure cases and invariants

Current failure cases:

- Changed plugin text/style with unchanged rendered width: `dirty` makes the
  frame `Full`; a statusbar-only update should not recompose panes/sidebar/
  panel.
- Repeated identical view: cache de-duplicates it, so no `dirty`, bars, or
  frame should be produced; preserve this behavior.
- New/removed contribution, plugin load/respawn/disable/exit, or a view whose
  rendered width changes: statusbar placement or visibility can change. These
  must retain broad invalidation until layout is known stable.
- Multiple queued plugin messages: drain coalesces them before the one render
  decision. The aggregate damage must choose the widest necessary class; a
  structural message must not be downgraded because a content-only message is
  also present.
- A live overlay, geometry change, theme/layout change, or worktree switch
  still wins in `render_plan::plan` and must remain `Full`.
- A pane-only wake must remain incremental and must not consult plugin state;
  the pure render decision receives damage as input only.

Hard invariants from the architecture/coordination brief:

- `render_plan::plan` remains pure and precedence remains geometry/full,
  heavy chrome/switch/overlay, bounded content, then `Skip`.
- Identical plugin status updates produce no frame (`Skip`), not an empty
  incremental frame.
- Do not implement THE-165 generation tagging or THE-161 output bounding in
  this lane. The primary explicitly says narrowing render damage does not
  depend on either unlanded issue.
- Preserve plugin cadence and existing compositor coalescing. Do not introduce
  a timer, polling source, or second damage mechanism.

## Smallest complete fix proposal

Use the existing damage/compositor path, but replace the plugin drain's single
repaint boolean with an ordered plugin damage classification in a sibling
module (for example `plugin_damage.rs`):

1. `None`: no visible cache/contribution change; leaves all render damage
   channels clear.
2. `StatusbarContent`: a changed statusbar `View` whose rendered width and
   placement remain stable; set only a statusbar bounded-region channel. The
   current renderer already has `chrome.statusbar` as a one-row diff region;
   this is the smallest region representation available inside the primary's
   stated scope. It avoids the masthead and all center/sidebar/panel work.
3. `Structural`: contribution add/remove, load/respawn/disable/exit, or a
   changed rendered width/placement; retain the broad `dirty`/chrome path so
   `draw_statusbar` recomputes fitting and cluster placement safely.

Implementation shape for the greenlit coding stage:

- Keep the classification and width comparison out of `run.rs`; have the
  plugin handler return an aggregate damage value (or an equivalent small
  result type) while preserving its existing model mutation and response
  behavior.
- Change only the run-site plumbing needed to map `None`/content/structural
  to the existing damage locals. Do not grow `run.rs` with layout or plugin
  policy logic.
- Extend `render_plan::Damage`/`RenderPlan::Incremental` only as needed to
  distinguish a statusbar-only bounded region from the existing `bars` channel
  (which also repaints the masthead). The incremental renderer should draw the
  statusbar for that region and add exactly its one-row rect to
  `pane_diff_rects`; ordinary clock/stats/media bar damage keeps the existing
  two-row `bars` behavior.
- Keep `chrome`/`dirty` precedence unchanged. Structural plugin changes must
  continue to select `Full`, while unrelated layout/theme/full damage remains
  authoritative.
- If primary review interprets “owned bar/region” as exact segment bounds
  rather than the existing statusbar row, the additional smallest extension is
  a pure plugin-segment-span helper shared by `draw_statusbar` and the damage
  path, plus a list of one-row segment rects. The current code has no exported
  segment-span helper; do not duplicate the private placement math silently.
