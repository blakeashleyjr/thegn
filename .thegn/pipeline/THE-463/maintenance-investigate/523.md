## Bug status: confirmed on this branch

### Dead serialized setting

`crates/thegn-core/src/config_calendar.rs:267-269` derives `Deserialize`,
`Serialize`, and `JsonSchema` for `CalendarAccount`, so the public schema and
config wire format include the account fields. The `read_only` field is at
`:280-282`, with documentation saying it refuses writes but also saying all
built-ins are currently read-only. The default at `:370-390` sets it to
`true`; the custom debug implementation also emits it at `:327-333`.

The shipped example exposes `read_only = true` at
`config/config.toml.example:394-405`. The only focused core assertion found is
`crates/thegn-core/src/config_calendar_tests.rs:445-450`, which checks the
default is true. There is no test that a false/true account policy affects a
backend, capability bits, or a write result.

A repository-wide production search found no read of `CalendarAccount::read_only`
outside config/debug/test/example material. In particular, it is not consumed
by the service factory, router, host hydrator, control service, or command
backend. Therefore `read_only = false` currently has no effect, and a future
writable backend could be added without an existing centralized account gate.

### Provider capability and write seam

`crates/thegn-svc/src/calendar/mod.rs` has:

- `CalendarError` at `:30-47`; it distinguishes `Unsupported` from transport
  and policy errors, but has no read-only denial variant.
- `CalendarCaps` at `:85-95`, with `create`, `update`, and `delete` bits.
- `CalendarBackend` at `:284-325`; its optional `create_event`,
  `update_event`, and `delete_event` methods default to
  `CalendarError::Unsupported` at `:304-324`.
- `backend_from_account` at `:327-339`, which selects a concrete adapter but
  does not retain or apply `read_only`.
- `CalendarRouter::from_config_with_pool` at `:361-382`, which stores only the
  account name, hue, and inner backend in `AccountBackend`; the account policy
  is dropped before routing.

Every built-in currently advertises no mutation support. ICS returns default
caps at `crates/thegn-svc/src/calendar/ics.rs:184-186`; ICS URL and CalDAV only
advertise incremental reads at `ics_url.rs:83-89` and `caldav.rs:390-396`; the
command backend only advertises incremental reads at `command.rs:427-432`.
This explains why no current provider performs a mutation, but it does not
make the public policy setting safe for future providers.

### Control and plugin paths that must not be confused with provider writes

- The HTTP route
  `crates/thegn-svc/src/control/routes.rs:142-146` and matching HTTP handler
  `control/http.rs:1441-1453` expose `calendar.ingest`. The control trait
  documents at `control/mod.rs:992-1005` that this pushes events into the local

  not override this default today, so it is currently unimplemented. It is not
  a CalendarBackend mutation route and should not be made an accidental bypass
  or conflated with provider authorization.
- The command plugin is a read/data-source protocol. `command.rs:274-303`
  accepts `manifest`, `events`, and `log`; unknown verbs are ignored. Its
  documented contract at `docs/help/calendar.md:214-249` only describes event
  output. A command plugin is launched from `CommandBackend::list_events` and
  currently has no write verb to negotiate.
- The existing plugin manifest negotiation at `command.rs:386-420` is about
  data-source extension points and account-granted process capabilities. Do
  not redesign that negotiation in this issue. If a future plugin-backed
  writable adapter is added under THE-166/THE-162, its account-bound backend
  must enter the same policy wrapper before any provider/plugin mutation call.

Required prerequisites are therefore small but real: a provider or plugin must
first implement a writable adapter before `read_only = false` can permit any
write; and any future mutation route must dispatch through an account-bound
router/wrapper rather than calling a raw provider object. No schema migration is
needed for the enforce choice because the serialized field remains present.

## Smallest complete fix

Implement one account-policy wrapper in `crates/thegn-svc/src/calendar/mod.rs`
around every backend stored or dynamically registered for an account. Do not
put three independent policy checks into ICS, CalDAV, ICS URL, command, or
future provider implementations.

1. Add a typed mutation operation enum (create/update/delete) and a distinct
   `CalendarError` denial variant, for example
   `CalendarError::ReadOnly(CalendarMutation)`. It must never be represented
   as `Unsupported`: unsupported means the provider cannot do the operation;
   read-only means account policy refused it.
2. Add an account-bound policy adapter that stores only the account identity
   needed for diagnostics, `read_only`, and the inner `Box<dyn CalendarBackend>`.
   Its `caps()` must copy provider capabilities and set
   `create/update/delete` to `provider_bit && !read_only`; unrelated
   `incremental` and `server_expand` bits pass through unchanged.
3. Its three mutation methods must authorize before invoking the inner backend.
   With `read_only = true`, each returns the typed denial and the provider or
   plugin is not called. With `read_only = false`, each delegates unchanged,
   so a genuinely writable provider remains usable. Emit a bounded
   `tracing` warning on the existing calendar diagnostics target with account,
   provider, and operation fields; do not create a new audit store or include
   URLs, tokens, event payloads, or command arguments.
4. Make `CalendarRouter::from_config_with_pool` wrap the result of
   `backend_from_account` before storing it. If an internal account-dispatch
   method is needed for future create/update/delete routes, add it to the
   router and route by the account identity through this wrapper. Do not add a
   new HTTP/CLI/MCP feature in this maintenance change.
5. Preserve the current command-plugin negotiation and read-only plugin
   protocol. The wrapper must surround a command/provider adapter, so a future
   plugin mutation cannot gain authority from its manifest or self-reported
   capabilities. The wrapper is the host/router boundary required by the
   coordination brief.
6. Resolve the raw-constructor bypass explicitly. The current concrete
   adapter constructors are public and are used by in-crate tests, while
   account policy exists only on `CalendarAccount`. Primary should choose one
   of: narrow raw constructors to crate visibility and expose only the
   account-bound factory, or explicitly define the public raw adapter as
   provider-only and require all account-scoped mutation calls through the
   wrapper. The security invariant is that no account-authorized route can
   obtain an unwrapped backend.

This keeps `read_only` in the public schema/example, makes the safe default
real, and avoids pretending that current read-only providers can write. The
repo-wide consumed-config-field ratchet remains a recommended follow-up under
the coordination brief, not part of this fix.

## Failure cases and regression matrix

The implementation tests should use a fake/spy backend whose provider caps and
mutation methods can be made writable, so tests do not confuse “all current
built-ins are unsupported” with account-policy enforcement.

- For each of create, update, and delete with `read_only = true`, the
  account-bound adapter and router return the typed denial, report false in its
  corresponding capability bit, emit one denial diagnostic, and leave the
  spy's invocation counter at zero.
- For each verb with `read_only = false` and provider support true, the call
  reaches the spy and returns its result; caps remain true. With provider
  support false, the result remains `Unsupported`, proving policy and provider
  capability are separate.
- A provider that claims all three write bits while its account is read-only
  is clamped to all false and cannot be called. This is the contradictory
  provider-capability case and the primary fail-closed regression.
- Exercise the same six cases through the router's account dispatch, direct
  account-bound adapter, and a plugin-labelled/command route. The denied
  plugin case must prove no plugin/provider invocation occurs; do not add a
  plugin mutation protocol merely for the test.
- Verify `server_expand` and `incremental` are preserved by the wrapper and
  that account names are routed exactly; a missing/ambiguous account must not
  fall through to another backend.
- Capture the existing calendar tracing target and assert denied records name
  only bounded account/provider/operation facts, never URL, token, command
  argv, or event content.
- Retain the existing built-in test asserting current ICS write calls are
  `Unsupported`; add a separate test proving that a policy denial is not
  misclassified as `Unsupported`.
