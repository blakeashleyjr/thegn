## Finding

### P2 — public field documentation still says the security control is not enforced

`crates/thegn-core/src/config_calendar.rs:280-282` documents
`CalendarAccount::read_only` as “currently belt-and-braces” because “this pass
has no writing backend at all.” That is now false: the approved implementation
retains the public serialized field and enforces it in
`crates/thegn-svc/src/calendar/mod.rs:371-383` (the account-bound factory) and
`:401-478` (capability clamping plus typed denials before the inner backend).
Because the Rust field documentation feeds generated schema/API documentation,
this leaves consumers with a contradictory security contract and can encourage
a future caller to treat the flag as advisory. Update the field comment to say
that the account-bound factory enforces the default read-only policy for all
three upstream mutations; preserve the existing note that current built-ins
advertise no write support.

This is a documentation/contract defect, not a discovered provider invocation
bypass. The raw constructors are crate-private, `backend_from_account` wraps
every built-in, and `CalendarRouter::from_config_with_pool` stores only the
wrapped backend. The wrapper passes `incremental` and `server_expand` through,
clamps only create/update/delete, returns `ReadOnly` before provider/plugin
calls, and logs only account/provider/operation on the existing calendar target.
