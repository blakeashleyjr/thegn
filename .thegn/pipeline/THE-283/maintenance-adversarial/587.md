## Findings

### F-1 — policy-free fallback bypasses the no-redirect contract (P1)

`crates/thegn-svc/src/control/client.rs:1245-1252` falls back from the
policy-bearing builder to `reqwest::Client::new()`. The latter uses reqwest's
default redirect policy, so this is a second transport construction path that
can follow redirects after the configured `Policy::none()` path fails. A
redirected authenticated state-changing request can therefore be replayed or
accepted at a different destination, violating the issue criterion that
redirect policy cannot differ by callsite and the primary plan's “single
construction point” intent. The existing redirect regression only exercises a
successful builder and cannot reach this branch.

The primary plan permits an infallible constructor with a documented fallback,
but that allowance does not satisfy the full acceptance criterion when the
fallback is explicitly policy-free. Clear this by failing closed on client
construction failure or by using a fallback that preserves every currently
required policy; do not claim this review clear while the default-client path
remains.

### F-2 — replacement test does not exercise a config-reload replacement (P2,

test coverage)

`crates/thegn-svc/src/control/client.rs:1500-1554` creates two unrelated local
`ControlClient` values. It proves that an in-flight request holding an old
client clone can finish after the original owner is dropped, but it does not
exercise a reload-owned slot, an atomic/mutex swap, or the decision not to
rebuild when only unrelated configuration (such as theme/UI state) changes.
There is no production reload API in this branch, so the actual reload
lifecycle remains unverified rather than being incorrectly called proven.
The primary should either document this as the intentional lifecycle boundary
or add a test around the real owner/replacement mechanism when that mechanism
exists.
