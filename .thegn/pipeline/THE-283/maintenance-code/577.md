# THE-283 implementation — native dispatch row 577

Verdict: implementation-ready.

## Changes

- `ControlClient` now owns one optional `reqwest::Client`, created only for
  `ControlAddr::HttpOrigin` and cloned directly with the client. Clones share
  reqwest's connection pool; Unix/TCP clients retain their existing Hyper
  one-connection-per-request path.
- All unary HTTP-origin requests use that stored client. The sole construction
  point retains today's `Policy::none()` redirect policy and documents the
  deliberate THE-273 follow-up point. No deadline or response-body cap was
  added, per the approved scope.
- Construction remains infallible as authorized by the primary plan. An
  unusual reqwest builder failure logs a warning and uses reqwest's default
  fallback; this is the recorded trade-off for avoiding constructor-error
  plumbing through existing CLI call sites.
- Added a keep-alive loopback regression proving two requests through cloned
  clients use one accepted TCP connection.
- Added a replacement-lifecycle regression proving an in-flight request held
  by an old client clone completes while a newly constructed client serves a
  changed origin. This models the existing config-reload lifecycle: callers
  replace clients when effective endpoint/TLS/proxy configuration changes;
  there is no mutable ControlClient reload API in this branch.
- Existing redirect/replay tests remain in place and continue to exercise the
  centralized origin client path.
