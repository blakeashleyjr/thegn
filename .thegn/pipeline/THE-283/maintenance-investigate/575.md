## Finding and exact evidence

The bug remains.

- `crates/thegn-svc/src/control/client.rs:76-79`: `ControlClient` stores only
  `addr: ControlAddr`; there is no reusable `reqwest::Client`.
- `client.rs:300-303`: `ControlClient::new` only stores the address.
- `client.rs:318-335`: every unary call routes `HttpOrigin` to
  `send_origin_request`; Unix and raw TCP retain their separate hyper/TCP
  path.
- `client.rs:1222-1257`: `send_origin_request` builds a new
  `reqwest::Client` on every call. The only configured policy is
  `redirect(Policy::none())` at lines 1232-1235. It then calls
  `response.bytes().await` at lines 1252-1255, so the response is not bounded
  by a streaming body limit here. No connect timeout, request/operation
  timeout, explicit proxy policy, or response-limit policy is configured in
  this builder.
- `client.rs:1217-1221` and `client.rs:1247-1250`: THE-280's no-redirect
  behavior is already present and must be preserved; 3xx responses are
  rejected before parsing their bodies.
- `client.rs:1260-1316`: local Unix/TCP requests intentionally establish one
  hyper connection per request. This is the local-daemon behavior the issue
  says to leave unchanged.
- `Cargo.toml:156-159` and `crates/thegn-svc/Cargo.toml:60`: reqwest 0.12
  with JSON, rustls TLS, blocking, and stream support is already available.

The stale issue citation to `reqwest::Client::new()` is no longer exact: it was
changed by THE-280 to a per-request builder, but the lifetime/pool defect
remains unchanged.

## Production call paths and prerequisites

All dedicated unary methods (`health`, `sessions`, status, automation,
issue/dispatch methods, and so on) plus catalog-driven `call_raw` converge on
`ControlClient::request` (`client.rs:318-357`). Only `ControlAddr::HttpOrigin`
uses reqwest; WebSocket `subscribe_events`/`attach` use
`tokio_tungstenite` directly (`client.rs:796-964`) and are out of the unary
pool change.

Relevant production paths are:

1. `crates/thegn-host/src/daemon/client.rs:32-82` discovers or creates a
   `ControlClient`, probes it, and returns it for repeated daemon operations.
   `start_error_state_bridge` clones that client at lines 132-145 and uses the
   clone for the WebSocket feed and roster request. The field must stay
   `Clone`; reqwest clones share its internal pool.
2. `crates/thegn-host/src/cmd/session.rs:355-369` creates one client for the
   session/attach command and reuses it through the command path. This is
   local Unix in normal operation and must remain behaviorally unchanged.
3. `crates/thegn-host/src/automation_executor.rs:204-218` discovers a daemon
   per automation action. A single action can issue multiple unary calls (for
   example `tools.run` opens, waits, and may kill), so the returned client must
   carry one pool for that action. Cross-action pooling is not currently
   represented by a shared client and is outside the smallest `client.rs`
   fix.
4. `crates/thegn-host/src/cmd/merge.rs:374-416` reads the provisioned
   `THEGN_CONTROL_URL`/`THEGN_CONTROL_TOKEN`, constructs `HttpOrigin`, and
   performs route-to-host enqueue calls. The client is already outside the
   loop and is reused for its target loop; keep token attachment request-local.
5. `crates/thegn-host/src/cmd/session_move.rs:454-530` creates short-lived
   clients for migration/notification and normally uses Unix addresses. No
   remote pooling behavior should be added there.

There is no `ControlClient` integration with live config reload in this
branch. Config reload in `run.rs` updates UI/runtime subsystems but does not
replace a control client. The safe lifecycle contract should therefore be:
construct a new client when the effective endpoint/TLS/proxy policy changes;
existing clones keep the old reqwest client until their in-flight work ends;
new calls use the replacement. Theme/UI reloads must not reconstruct it.

Prerequisites for implementation:

- Confirm the authoritative THE-273 connect/request deadline and response
  limits, and whether the established policy requires `.no_proxy()` and
  disabled decompression for this control transport.
- Keep TLS on the existing reqwest rustls/WebPKI configuration. Do not add
  insecure TLS or ambient proxy behavior while moving the builder.
- Decide whether `ControlClient::new` becomes fallible (requiring constructor
  callsite updates) or uses an explicitly reviewed initialization/error holder;
  do not silently fall back to `Client::new()` because that would lose policy.

## Smallest complete fix proposal

1. In `crates/thegn-svc/src/control/client.rs`, introduce one cloneable
   remote HTTP transport state owned by `ControlClient` and initialized once
   per effective `HttpOrigin` configuration. Store the parsed origin and the
   policy-configured `reqwest::Client` together; clone the reqwest client
   directly. Keep Unix/TCP transport fields and behavior separate.
2. Move the complete approved policy into that single builder: THE-280
   `Policy::none()`, THE-273 connect/request deadlines and bounded response
   reads, TLS defaults, explicit proxy behavior, and decompression/body
   handling. `request` must only build a request from this state and must not
   be able to choose a different policy by callsite. Use the existing
   `crate::http::read_bounded_response` if the primary confirms it is the
   shared THE-273 reader; otherwise extract the approved primitive first.
3. Parse/validate the origin once at construction rather than reparsing it for
   every request. Preserve bearer auth as a per-request header, never a client
   default, so cloned clients cannot leak credentials across configurations.
4. Replace `response.bytes()` with the approved bounded streaming reader and
   map limit/deadline failures to fixed, non-secret control errors. Preserve
   existing JSON content-type/protocol parsing and the THE-280 fixed redirect
   error. Do not change WebSocket construction or local hyper/TCP behavior.
5. Treat replacement as an ownership/lifecycle operation, not a global static
   cache: a changed endpoint/TLS/proxy configuration gets a new client, while
   old `ControlClient` clones are allowed to finish. No theme-only reload may
   recreate the client. Update constructor callsites only if the approved
   fallible initialization requires it.

## Regression tests to add or update

Tests belong with `crates/thegn-svc/src/control/client.rs` unless a shared
transport helper is approved. Do not run them during this investigation.

- **Pool reuse:** a deterministic same-origin HTTP fixture should accept two
  unary requests on one keep-alive connection, count accepted sockets, and
  assert one connection for two calls through the same `ControlClient` (and
  that a clone shares it). Include a control response body/content type valid
  for the existing parser.
- **Single policy path:** exercise redirect statuses through the shared client
  and assert no target request, no bearer/body replay, and the existing fixed
  error. Add oversized/chunked response and never-ending/slow response
  fixtures for the approved body and deadline policy. The test should fail if
  a callsite reintroduces a fresh default client.
- **Policy invariants:** assert the configured connect/request deadlines and
  body limit at runtime with local fixtures; include proxy-environment
  isolation if THE-273 requires `.no_proxy()`. TLS should retain normal
  WebPKI verification; do not weaken it for a test.
- **Replacement lifecycle:** hold an old client with an in-flight local
  request, construct a new client for changed origin/policy, let the old call
  finish, and verify the new client reaches only the new origin. This proves
  replacement does not cancel/leak old work and that old pool state is not
  shared across effective configurations.
- **Local regression:** retain existing Unix/TCP tests and add no pooling
  expectation to those paths; their one-request hyper behavior and auth must
  remain unchanged.

material appearing in errors. Unix/TCP local requests must continue to work
with their current one-connection-per-request path.
