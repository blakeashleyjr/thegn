## Exact production evidence and call path

1. **Typed config admits unchecked rate/duration values.** `ProviderEntry` has `rpm: f64` and `burst: f64` at `crates/thegn-core/src/config_model_proxy.rs:77-80`. The only provider checks in `ModelProxyConfig::validate` concern secret refs, routes, and aliases (`:292-330`); no rate or timeout checks exist. Validation returns immediately only when the proxy is disabled (`:281-284`). The global validator does call `cfg.model_proxy.validate()` (`crates/thegn-core/src/config_validate.rs:494-497`), but this validator has no relevant numeric rules today.
2. **Rate-limit math can receive unsafe values.** `RatePolicy::rps` divides directly (`crates/thegn-core/src/proxy/ratelimit.rs:85-89`). `parse_rate_policy` rejects only `rpm <= 0` (`:92-117`): NaN passes that comparison, infinity passes, and invalid burst text falls back to RPM. More critically, config provider values bypass this parser. `TokenBucket::reserve` computes `deficit / rps` and passes it to `Duration::from_secs_f64` (`:65-74`), which can panic for non-finite/out-of-range waits. `RateLimiter::try_acquire` and `reserve` lazily install buckets from the supplied policy (`:120+`).
3. **The daemon config path bypasses typed validation.** `thegn-proxy::config::from_env` deserializes JSON then calls `build` (`crates/thegn-proxy/src/config.rs:32-37`). `build` parses the listen address and immediately builds routes (`:42-60`); it does not call `cfg.validate()`. `expand_backend` copies `p.rpm` and `p.burst` into a `RatePolicy` (`:147-156`). Host config validation is a normal admission path, but config construction itself has no defensive numeric check.
4. **The HTTP client has no deadline policy.** `AppState::new` constructs `reqwest::Client::new()` (`crates/thegn-proxy/src/state.rs:37-50`), so no explicit connect or total timeout is configured.
5. **Non-stream requests can wait indefinitely.** OpenAI dispatch calls `send().await`, then reads all response bytes with `bytes().await` (`crates/thegn-proxy/src/upstream.rs:112-130`). Anthropic does the same (`:184-207`). `route_nonstreaming` reaches `try_chain` for OpenAI `/v1/chat/completions` and Anthropic `/v1/messages` (`crates/thegn-proxy/src/server.rs:140-158, 180-218`). `try_chain` awaits dispatch with no timeout (`crates/thegn-proxy/src/router.rs:299-306`), and the same function handles exhausted, soft, and network-error responses to continue the backend chain (`:308-315, 318+`).
6. **Current stream policy only covers part of the lifecycle.** Config currently exposes `first_byte_timeout_secs`, `idle_timeout_secs`, and `heartbeat_secs` (`config_model_proxy.rs:226-234`), mapped to `RelayConfig` in `config.rs:88-92`. `relay::peek` times out while awaiting usable pre-commit stream data (`crates/thegn-proxy/src/relay.rs:197-250`); `spawn_relay` checks committed-stream idle on heartbeat ticks (`:285-329`). But `try_stream_chain` awaits upstream `open_stream` before calling `peek` (`router.rs:542-577`), so a hang while connecting/waiting for response headers is outside the first-byte timer. Streaming Anthropic requests use buffered `dispatch` (`router.rs:500+`); that path also currently lacks a deadline. There is no end-to-end request lifetime cap.
7. **In-flight cleanup is not cancellation-safe.** Non-stream routing does `inflight.enter`, awaits dispatch, then `inflight.leave` (`router.rs:299-306`). Dropping/cancelling that future between the await and leave leaks the count. A regular returned timeout error would reach `leave`, but cancellation does not. Current streaming route has no in-flight enter/leave in this path; adding streaming caps would enter the explicitly excluded THE-173 scope. Token-bucket tokens are admission accounting, not a held permit; whether to refund an admitted token when a request times out/cancels is not represented by a reservation API and needs a primary decision. A cancellation-safe guard should release the in-flight count on drop; rate tokens should remain consumed for an attempt that was admitted unless the product explicitly defines refundable reservations.

## Smallest complete fix proposal

1. In `config_model_proxy.rs`, add field-specific validation for finite, strictly positive RPM; finite burst at least one; and supported bounds that keep refill/wait arithmetic and duration conversion representable. Validate `first_byte_timeout_secs`, `idle_timeout_secs`, `heartbeat_secs`, and budget window directly as typed values, including zero where it is nonsensical (especially heartbeat zero, which reaches `tokio::time::interval(Duration::ZERO)`). Keep zero only for fields whose contract explicitly defines it (budget window is documented as cumulative). Return `[model_proxy.providers[i].rpm]`-style diagnostics identifying the offending field and provider. Define whether cost and budget `f64`s are within this issue's numeric scope; reject non-finite/negative values if they flow into price/budget math.
2. Make runtime construction validate before expanding routes or materializing a limiter policy. `thegn-proxy::config::build` should fail with the field-specific diagnostic even when called directly from the daemon JSON path, so invalid values cannot get into `ProxyConfig`/limiter state. Harden the core `RatePolicy`/limiter boundary so NaN/infinity/zero/tiny values cannot create a bucket or reach `from_secs_f64`; avoid silently accepting the invalid string-rate behavior either.
3. Establish one explicit deadline policy and document it at config/API points: connect deadline; response-header / first-usable-byte deadline; per-read/body idle deadline; total request deadline. Reuse the existing stream first-byte and idle settings where they represent the same phase. Give non-stream OpenAI and Anthropic the same connect/header/body/total policy; ensure streaming open/header wait is bounded before `peek`, preserve pre-commit timeout as a failover-eligible outcome, and terminate committed streams on idle/total timeout. Use bounded durations and avoid zero durations that panic or make all requests fail immediately. If new configurable keys are needed, update the four coordination-listed ratchets; otherwise use documented bounded constants for phases that need no user knob.
4. Make non-stream in-flight accounting cancellation-safe with an RAII guard around dispatch. Treat timeout as a network/availability failure so `try_chain` advances to the next lane. Preserve existing token-bucket semantics as consumed admission unless a refundable reservation design is explicitly selected. Do not add atomic streaming/fallback caps here; that is THE-173.

### Required scope decision

The above cannot be implemented completely within the coordination note's three-file scope. `state.rs`, `ratelimit.rs`, and `config_model_proxy.rs` cover client setup, limiter safety, and typed validation, but applying header/body/total deadlines to the actual upstream call and retaining failover behavior requires at least `crates/thegn-proxy/src/upstream.rs` and `crates/thegn-proxy/src/router.rs`; the existing stream phase code is in `crates/thegn-proxy/src/relay.rs`. `crates/thegn-proxy/src/config.rs` is needed if a new timeout key is introduced or config validation is enforced at construction. Primary review must approve this file-scope expansion or explicitly split these pieces.
