## Findings

### F1 — `apply_relaunch` does not return its declared result (blocking)

`crates/thegn-host/src/handlers/worktree_launch.rs:305-315` declares
`-> RelaunchOutcome`, calls `apply_relaunch_with(...)`, and then reaches the
closing brace. The delegated value is terminated with `;`, so the function has
no return expression. This is a compile-time type error, and the existing
tests that compare `apply_relaunch(...)` with `RelaunchOutcome` do not make the
source runnable until this is fixed. The wrapper must return the delegated
outcome.

### F2 — the refusal outcome is not part of the worker batch bookkeeping

`RelaunchOutcome` is computed at
`crates/thegn-host/src/handlers/worktree_launch.rs:331-345`, but its callers
discard it at `crates/thegn-host/src/handlers/materialize.rs:287-295` and
`crates/thegn-host/src/run.rs:8706-8717`. `SpecBatch` at
`crates/thegn-host/src/handlers/provision.rs:19-37` carries only `specs` and
`attach`; it has no relaunch/refusal status. A refusal therefore leaves the
`specs` result as `Ok`, reaches `provision.rs:552-568`, and is treated as a
successful shell-spec batch. This does not satisfy the primary instruction
that the refusal be reflected in the batch's own outcome bookkeeping rather
than silently reporting success. The fix must preserve fail-open shell
behavior and must not silently alter retry policy; add a status field or an
equivalent explicit worker outcome and cover both materialize and prewarm.

### F3 — `bounded_reason` still permits unbounded transient allocation

At `crates/thegn-host/src/handlers/worktree_launch.rs:137-142`,
`error.to_string()` first materializes the complete provider/sandbox error,
then `redact_text_line` scans and reconstructs the complete string, and only
afterward does `.take(512)` bound the displayed result. A provider that returns
very large command output or nested context can therefore force large
short-lived allocations on every first refusal even though the emitted detail
is capped. The bound needs to apply during formatting/sanitization, or the
error source needs an explicitly bounded display path. The current size test
only checks the final string and cannot detect this allocation behavior.

### F4 — the registry cap does not cap retained key bytes

`RefusalRegistry` limits the number of entries to 256 at
`crates/thegn-host/src/handlers/worktree_launch.rs:91-103`, but
`admit_refusal` stores full caller/config-derived `worktree` and `agent`
strings at `:150-155`, duplicated in both `reported` and `order`. The
cardinality is bounded, but an attacker or malformed configuration can make
each retained key arbitrarily large, and 256 such keys remain resident for
the process lifetime. Bound or normalize the key representation (with a
collision-safe policy appropriate for dedupe), or impose explicit byte limits;
do not claim the resource bound is complete from the entry cap alone.

### F5 — acceptance tests do not prove that no process was executed

The typed and ordinary regressions at
`crates/thegn-host/src/handlers/worktree_launch.rs:739-845` inspect the
resulting argv and capture the warning, but they never pass the resulting
batch through `Panes::materialize_with_specs` or a process-spawn sentinel.
The injected typed refusal returns before any process boundary, and the
ordinary test's resolver only constructs a `LaunchSpec`; neither proves the
acceptance assertion that an unsafe Codex command was not executed through the
real materialize path. Add a focused test using a sentinel executable/marker
and the real worker-to-materialize seam, while retaining the existing pure
fold tests for shell preservation and dedupe.
