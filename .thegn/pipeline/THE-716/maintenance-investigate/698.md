## Exact-branch evidence and production paths

### Container listing and wake

- The shared ticker derives the container cadence from
  `CONTAINER_REFRESH_INTERVAL = 5s` (`crates/thegn-host/src/hydrate.rs:368`;
  `crates/thegn-host/src/hydrate_refresh_ticker.rs:284-288`). Every 10 half-
  second slots it calls `TickerIo::send_containers` and unconditionally sets
  `wake = true` (`hydrate_refresh_ticker.rs:590-603`); the live worker's
  notifier calls `TerminalWaker::wake()` (`hydrate_refresh_ticker.rs:104-106`).
  This path is still active here.
- `LiveIo::send_containers` reads `containers_live`, but that flag selects only
  the expensive `running_containers_with_stats()` versus
  `running_containers()` call. The cheap list always runs, then a
  `ContainerRefresh` is sent (`hydrate_refresh_ticker.rs:726-743`).
- Exact current subprocess behavior is a little different from the issue
  description: `running_containers_impl(false)` always attempts Podman
  rootless and rootful `ps` (`crates/thegn-core/src/sandbox.rs:1296-1320`),
  and attempts Docker `ps` only when those produced no rows (`:1321-1333`).
  Thus the exact branch does not unconditionally run both Podman and Docker,
  but does unconditionally probe both Podman modes and can probe Docker as a
  fallback. The function comment says one process per backend and empty if no
  runtime is installed (`:1273-1283`), while the implementation has no cached
  `available()` precheck. The authenticated/live measurement may have observed
  two calls for its environment; source does not support “both every tick” as a
  universal claim.
- Existing `available(&Placement::Local, backend)` is the cached three-state
  check used by `container_footprint()` before invoking backends
  (`sandbox.rs:1337-1357`); it should be reused by the listing path. Its local
  `Present` result stays cached and local `Absent` is retained, per
  `sandbox_backend.rs:563-568`.
- Container snapshot consumers are:
  - Sandbox section summary/chip in the panel section rows
    (`crates/thegn-host/src/panel/frame.rs:382-415`,
    `panel/sections/mod.rs:549-574`), and the Sandbox body / full container
    table (`panel/sections/misc.rs:925-965,1008-1025,1048-1075,1103-1183`).
    The summary renders with the section row even when another accordion is
    open; therefore an open panel can consume the list, not just an expanded
    Sandbox body.
  - The monitor Containers tab, whose presence is derived from the current
    container list, and whose rows/actions use `model.containers`
    (`crates/thegn-host/src/monitor.rs:240-258,575-581,615-625`; renderer at
    `monitor/build.rs:1025-1082`). The monitor must be treated as demand while
    open so an initially empty model can be populated and expose the tab.
- The event-loop drain derives active-container health, updates the container
  list, and marks chrome dirty only when health/list differs
  (`crates/thegn-host/src/run.rs:10809-10848`). Hydration explicitly carries
  the list and health across model replacement (`run.rs:10186-10194` and
  `run.rs:10244-10245`).
- There is **no sidebar container/devcontainer badge consumer** of this list:
  sidebar devcontainer status is a separate `devcontainer_status` field
  (`crates/thegn-host/src/sidebar.rs:238-239,397-398`). The Sandbox panel
  summary is the small “chip” that does consume the list
  (`panel/sections/mod.rs:549-574`).
- Current detailed-stats visibility is computed in one event-loop write site:
  the open Sandbox panel section or the monitor Containers tab
  (`crates/thegn-host/src/run.rs:12573-12581`,
  `crates/thegn-host/src/monitor.rs:911-918`). It must remain a distinct
  predicate from basic-list demand because the basic list is also used by the
  Sandbox section summary and is needed to initialize the monitor tab.

### `gh` process attribution

- **`gh run list`:** `RefreshKind::Ci` is emitted on `[ci].poll_interval_secs`
  from the shared ticker regardless of panel visibility
  (`crates/thegn-host/src/hydrate_refresh_ticker.rs:434-440`). The floor is 5s
  (`ci_refresh.rs:17-22`; config validation at
  `crates/thegn-core/src/config_ci.rs:91-94,125-130`); defaults are 30s for
  both polling and cache freshness (`config_ci.rs:109-115`). The off-loop CI
  worker skips a non-forced fetch while cache age is less than `ttl_secs`, and
  backs off after errors (`ci_refresh.rs:24-29,239-243`). The result feeds the
  CI panel and the statusbar CI failure/running badge
  (`panel/sections/mod.rs:385-415`,
  `crates/thegn-host/src/statusbar_badges.rs:111-141`, wired at
  `chrome.rs:1749-1755`); the badge is an always-rendered surface when relevant
  runs exist. So the producer is not panel-gated, but it maintains a visible
  CI status indicator and has a 30s default / 5s configured floor. The issue's
  observed rate is not derivable without its effective config and worktree/cache
  state (e.g. `ttl_secs = 0` disables freshness coalescing).
- **`gh run view`:** two producers exist. Interactive run-detail fetch is
  started for a live CI drill, and a live drill can re-poll its selected run
  (`crates/thegn-host/src/actions.rs:407-435`,
  `crates/thegn-host/src/ci_refresh.rs:119-125`), so that use is visible-surface
  gated. Separately, a successful background run-list fetch calls
  `ingest_failed_logs` (`ci_refresh.rs:288-298`), which expands retained
  terminal failed runs with `run_detail` (`:334-386`) and calls
  `gh run view --job … --log` only when the per-job cached entry is missing or
  its head changed (`:388-418`; provider argv in
  `crates/thegn-svc/src/ci.rs:661-695`). That ingestion is not panel-gated; it
  is gated by `log_cache_runs > 0` (default 10), failed retained runs, and
  missing/stale log cache entries. Its cadence is the enclosing CI fetch's
  effective poll/TTL/backoff cadence (default 30s; configured floor 5s), and
  the log bytes themselves are not repeatedly fetched once cached.
- **`gh issue list`:** the periodic `RefreshKind::Issues` runs every 60s
  (`crates/thegn-host/src/hydrate.rs:23-24`,
  `hydrate_refresh_ticker.rs:442-446`), with no visible-section gate. The loop
  starts the off-loop tracker refresher (`run.rs:11911-11913,12320-12332`);
  it exits without a provider subprocess if no issue account is configured
  (`crates/thegn-host/src/hydrate_tracker.rs:23-45,55-65`). GitHub's issue
  adapter invokes `gh issue list` (`crates/thegn-svc/src/issue/github.rs`;
  `list_issues` at lines 304-341). The cadence floor is therefore fixed at 60s, but the fetch is not
  gated on Issues/Mine being visible; cache refresh also drives linked-issue
  status/overdue notifications (`hydrate_tracker.rs:79-123`).
- **GH disposition for implementation review:** leave the run-history poll as
  verified-fine at its defaults: it feeds an always-visible CI status badge,
  has 30s default polling and a 30s freshness guard, and uses failure backoff.
  Keep the interactive `run view` path as-is. The always-on failed-log
  ingestion does issue `run view` work without an open detail surface, but only
  for retained terminal failures and uncached/changed logs; it is a bounded,
  configured CI behavior rather than an idle container regression. The issue
  list call is clearly ungated, but its fixed 60s cadence exists
  to refresh persistent issue-derived notifications as well as panels. Do not
  remove that background behavior without primary review of notification
  freshness; the observation of ~11 GH calls/min cannot be assigned to this
  producer from source alone. If primary elects to include it, an adaptive
  visible/idle issue cadence is a separate scope decision, not needed to close
  the proven THE-716 container defect.

## Smallest complete proposed fix

1. Add an atomic **basic container-list demand** signal owned by the loop and
   published alongside the existing stats/detailed-stats signals. It is true
   when the panel is open (its Sandbox summary is rendered) or the monitor is
   open (so the Containers tab can be discovered). Keep the existing
   `containers_live` predicate for `stats --no-stream`/`df`; do not conflate
   the two.
2. At each 5s container slot, skip the listing entirely when basic demand is
   false. When demanded, use the existing cached local `available()` result to
   invoke only usable OCI backends; preserve the current backend ordering and
   fallback semantics. If none are configured/present, return an empty set
   without trying `podman`, `sudo`, or `docker`.
3. Keep the worker's last container snapshot. Deliver an initial snapshot when
   demand turns on and subsequent snapshots only when the container set (or a
   displayed detail field) changes. Have the ticker request a loop wake only
   for such a changed/initial snapshot. Recompute active-container health from
   the cached rows when the active worktree changes, so a list that is
   unchanged does not require a periodic wake just to fix health on tab switch.
4. Add deterministic tests through the existing `TickerIo` seam in
   `hydrate_refresh_ticker_tests.rs`: with no demand, advance through at least
   one container slot and assert zero list/probe invocations and no wake
   attributable to that slot; with demand, assert listing cadence, no repeat
   wake for an identical set, one wake on initial/changed set, and correct
   health recomputation after active-container change. Add a focused sandbox
   availability test using a fake runner/call recorder to assert absent backends
   do not execute `ps` and only cached-present candidates are invoked. Tests
   must demonstrate the no-demand assertion fails against the present
   `spawn_worker` control flow: at tick 10 it currently calls
   `send_containers`, then unconditionally wakes (lines 598-603). This is
   source-demonstrated; this investigation did not execute the test.
5. Adapt the THE-706-style no-subprocess regression shape for this worker rather
   than broad hydration: its scope is a 5s ticker pass and its assertions are
   exactly no OCI invocation and no ticker wake with no consumer. The current
   ticker fixture already counts `send_containers` and waker pulses
   (`hydrate_refresh_ticker_tests.rs:9-14,69-71,81-89,114-117`) but currently
   does not model consumer demand or assert a zero-container-wake case.

## Failure cases to cover / guard against

- No OCI engine present: no attempted `podman`, `sudo podman`, or `docker`
  process when the panel/monitor has no consumer; no periodic wake.
- Runtime installed but service stopped: cached unavailable status suppresses
  repeated listing subprocesses.
- Podman rootless/rootful availability and Docker fallback: do not silently
  stop listing a usable fallback or alter ownership/order semantics.
- List remains unchanged: do not wake the terminal every 5 seconds.
- List changes or demand starts: publish once and wake so the Sandbox summary
  and monitor tab update.
- Active worktree changes while list remains identical: active health must be
  recalculated without reintroducing a polling wake.
- Detailed stats surface is closed: basic visible list may run, but
  `stats --no-stream` and `system df` stay behind the existing stricter gate.
- Panel closes/monitor closes: the next ticker slot must not invoke OCI
  binaries; already queued messages remain harmless and bounded.
- Ticker/channel receiver is gone: preserve the current clean worker-exit
  behavior on send failure.
