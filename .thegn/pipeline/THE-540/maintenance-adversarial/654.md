## Findings

### 1. High — GitHub requests are not bound to the validated worktree origin

`crates/thegn-svc/src/ci.rs:531-539, 550-553, 579-600, 603-612` builds GitHub list, read, trigger, rerun, and cancel calls without an explicit repository target. `GitLoc::gh_command` runs `gh` in the worktree (`crates/thegn-core/src/remote.rs:420-444`), so selection is delegated to ambient GitHub CLI context. `gh` supports `GH_REPO` as an override for commands that otherwise operate on a local repo, and its configured default repository is also used for GitHub Actions. Therefore an inherited `GH_REPO=other-owner/other-repo` or a directory default set with `gh repo set-default` can direct an authenticated mutation at another repository while the caller selected this worktree. Under `provider = auto`, parsing the origin only picks the provider; the parsed origin is discarded before the GitHub call. This violates the acceptance requirement to preserve the authorized origin/project/operation.

Primary documentation: [gh environment variables (`GH_REPO`)](https://cli.github.com/manual/gh_help_environment) and [gh repo set-default](https://cli.github.com/manual/gh_repo_set-default).

**Required correction:** derive a canonical GitHub target from the worktree's parsed origin and pass it explicitly to every `gh` operation (with target options before `--`), while preventing ambient repository overrides from retargeting the request. Keep enterprise host support and reject unsupported/ambiguous remotes before authenticated calls.

**Regression test:** set `GH_REPO` to a different fixture repo and configure a differing gh default; capture all generated `gh` argv and assert every list/read/mutation targets the parsed origin. Assert malformed or unsupported origins cause zero provider invocations. No real provider mutation should be used.

### 2. Medium — acceptance-required CLI/control request-path coverage is incomplete

`crates/thegn-svc/src/ci.rs:1392-1423`'s `rejected_identifiers_never_reach_request_construction` increments its `authenticated_requests` counter only when pure argument/endpoint builders return `Ok`; it does not execute or instrument a provider call. The service test at `crates/thegn-host/src/daemon/service.rs:2006-2020` exercises only malformed IDs on `ci.logs`. There are no corresponding CLI tests for `view`, `logs`, `rerun`, `cancel`, or `trigger` (`crates/thegn-host/src/cmd/ci.rs:243-258,294-424,426-474`), nor a request-capture test proving exact provider argv/URL and zero calls for each rejecting ingress. The added provider-boundary test improves service coverage but does not cover those host ingress paths. The issue explicitly requires every CLI/control/provider entry to be covered and rejected inputs to produce zero requests.

**Required correction:** add CLI and control request-path tests using a fake provider/command capture seam. Cover valid exact argv/URL for each supported operation and malformed IDs/selectors/refs with an invocation count of zero. Existing provider pure-builder and JSON parser cases remain useful but do not substitute for this boundary assertion.
