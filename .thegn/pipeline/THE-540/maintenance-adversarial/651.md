## Findings

### 1. High — URL normalization erases GitLab remote traversal before validation

`crates/thegn-svc/src/ci.rs:968-987` parses the raw remote with `url::Url::parse` and then validates only `parsed.path()`. WHATWG URL parsing normalizes literal and percent-encoded dot segments before returning the path. For example, `https://gitlab.com/%2e%2e/group/repo` normalizes to `/group/repo`; the parser then accepts and constructs the project `group/repo` instead of rejecting the ambiguous traversal form. This violates the required rejection of traversal and can change which project an authenticated operation targets.

The added cases in `gitlab_path_parsing` assert that literal and encoded traversal remotes are rejected. I confirmed the normalization behavior with Node's WHATWG URL implementation; the Rust regression test was not run.

**Required correction:** inspect/validate the raw path before normalization (or use a parser that preserves the original path), reject dot segments and encoded delimiters before deriving a project, then keep the final authority/project assertion at the request boundary.

### 2. Medium — branch validator accepts invalid Git ref components

`crates/thegn-svc/src/ci.rs:379-393` checks several `git-check-ref-format` exclusions but does not reject components beginning with `.`. Thus `.hidden` and `feature/.hidden` pass validation and are sent to GitHub/GitLab, although they are invalid Git refs. This leaves the promised independent ref-syntax validation incomplete.

The added assertions in `workflow_argv_and_gitlab_query_preserve_target_identity` cover both cases and are expected to fail currently.

**Required correction:** implement the complete Git ref component grammar, including the leading-dot rule, and retain acceptance of query-reserved characters as ref data.

### 3. High — invalid GitLab remote errors can disclose embedded credentials

`crates/thegn-svc/src/ci.rs:798-800` includes the entire raw `origin` URL in an error when parsing fails. A remote such as `https://user:token@gitlab.example/group/repo` is rejected by the parser, but the resulting error contains `user:token`. CLI output and provider error logging can expose credentials that were embedded in the remote URL.

**Required correction:** report a safe component/reason or a redacted URL; never interpolate remote userinfo or the complete raw remote into an error. Add a regression asserting the secret is absent from the emitted error.

### 4. Medium — GitLab target validation and request host resolution race

`GitlabCi::project_seg` resolves and validates `origin` at `crates/thegn-svc/src/ci.rs:797-809`, but returns only the encoded project segment. Each subsequent `self.command(...)` independently resolves `origin` again at `crates/thegn-svc/src/ci.rs:773-791` to choose `GITLAB_HOST`. If the worktree's remote changes between those subprocesses, a request can combine project A from the first remote with host B from the second. With a configured GitLab token, this can send the credential-bearing request to the retargeted host and violates the primary instruction to bind the final request to the authorized origin/project/operation.

**Required correction:** snapshot the parsed remote once per operation and pass that same host/project value to both endpoint construction and command environment setup. Add a deterministic test of the single-snapshot boundary rather than relying on a timing race.
