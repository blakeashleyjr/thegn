## Bug remains: exact evidence on this branch

The issue’s old `engine.rs:78` citation is stale, but the defect remains in
the current file:

1. `crates/gtui-app/src/engine.rs:41-48` stores one `TimeRange` in
   `QueryEngine`; there is no relative-vs-absolute window type and no clock.
2. `engine.rs:78-96` creates one interval. The initial tick, every periodic
   tick, `EngineCmd::Requery`, and `EngineCmd::SetTimeRange` all call
   `query_all()`.
3. `engine.rs:102-129` builds each target query with
   `time_range: self.time_range.clone()` (`112`). No `now` is captured in the
   refresh cycle, so every periodic/manual requery repeats the same `from` and
   `to`. Panels in one cycle do share the same range, but it is stale.
4. `crates/gtui-embed/src/embed.rs:67-74` computes `Utc::now()` once while
   constructing the tile, creates a 15-minute `TimeRange`, and passes it into
   `ObserveApp::new`; that value becomes the engine’s fixed range.
5. `embed.rs:82-90` computes a new absolute range only when `[` or `]` is
   pressed, then `ObserveApp::set_time_range` (`crates/gtui-app/src/app.rs:103-107`)
   stores/sends that range. Subsequent automatic refreshes still reuse it.
6. `embed.rs:142-160` maps `r` to `Requery`, so manual refresh is stale too.

The downstream call path confirms this is a real query-window bug, not just a
display issue:

```
[observe] enabled
  -> thegn-host/apps/registry.rs:30-35
  -> apps/mod.rs:256-296 start_slot_tile/build_observe_tile
  -> gtui-embed::ObserveTile::new
  -> ObserveApp::new
  -> QueryEngine::spawn/run/query_all
  -> DataSource::query(Vec<Query>)
  -> Prometheus/Loki request start/end or host frame selection
  -> PanelUpdate channel + ChangeHook/waker -> ObserveApp::tick/render
```

Prometheus converts the resolved query range to API seconds at
`crates/gtui-query/src/prometheus.rs:31-69` (`43-53`); Loki converts it to
nanoseconds at `crates/gtui-query/src/loki.rs:30-68` (`43-51`). Thus a fixed
engine range produces repeated stale HTTP windows. The built-in host source
currently ignores `Query.time_range` and returns its retained ring, but it
still receives the same stale query object and is covered by the engine
contract.

## Prerequisites and unresolved dependencies

- THE-184 is unlanded, as recorded by the issue and coordination brief, but is
  not a prerequisite for this sequential engine fix. Do not add concurrent
  panel fetches, bounded queues, deadlines, or cancellation work from THE-184.
- THE-186 is downstream of THE-188 per the captured relation.
- The current `gtui-core::datasource::TimeRange` (`datasource.rs:7-11`) is an
  absolute resolved range. The smallest low-churn design is to retain it as
  the datasource wire payload and introduce a separate engine-level
  `QueryWindow` policy (`Relative(duration)` vs `Absolute(TimeRange)`). A
  broader core model change is not justified by this bug.
- Coordination names `crates/gtui-app/src/engine.rs` and its tests as scope.
  However, the current app/embed API only passes `TimeRange`; to make the
  existing `[`/`]` live window explicit while retaining a path for absolute
  historical windows, implementation may need a narrow adapter change in
  `crates/gtui-app/src/app.rs` and `crates/gtui-embed/src/embed.rs`. The
  recommended minimum is to keep existing callers source-compatible where
  possible, add a relative-duration command/constructor, and reserve the
  absolute variant for historical callers. The primary should approve this
  boundary before coding.
- There is no pause/resume action in `EngineCmd`, `ObserveApp`, or
  `ObserveTile` today, and no Observe config-reload path that rebuilds a live
  tile. Therefore no user-facing pause/resume or reload feature should be
  added under “no new features.” The implementation must document/test the
  policy boundary: paused relative windows retain their last resolved range;
  resume resolves once from the current clock and re-queries; a future config
  reload must preserve the selected window kind and duration unless explicitly
  changed. If the primary requires executable pause/resume commands in this
  issue, that is a scope expansion requiring a decision.

## Smallest complete fix proposal

1. Add an engine-owned `QueryWindow` enum with structurally separate
   `Relative(Duration)` and `Absolute(TimeRange)` variants. Keep
   `TimeRange` as the resolved payload passed to `Query`.
2. Inject a `now` provider into `QueryEngine` (a small `Send + Sync` callback or
   equivalent clock seam). Production uses `Utc::now`; tests use a queued fake
   clock. No wall-clock call belongs in the range builder itself.
3. Track the last resolved instant for relative windows. At the start of each
   `query_all`, call the provider exactly once and clamp it to the previous
   resolved instant when the wall clock moves backward. Resolve one range, then
   clone that range into every panel/target query. This preserves duration and
   prevents inverted windows while ensuring all panels in one cycle agree.
4. Make the current built-in 15-minute window and `[`/`]` duration changes
   relative. Preserve an explicit absolute path for historical callers so an
   absolute range is returned byte-for-byte unchanged on every refresh.
5. Do not alter panel sequencing or add THE-184 concurrency. Keep the existing
   result channel and waker behavior unchanged.
6. Define the non-user-facing lifecycle contract in code comments/tests:
   pause freezes the last resolved relative range and suppresses automatic
   refresh; resume resolves from the current monotonic-clamped clock and
   re-queries. Since no current command/action exposes pause, do not add a new
   key or config knob in this maintenance fix. A config reload with no current
   Observe reload path must not silently convert relative to absolute.

## Failure cases to guard

- Two periodic refreshes with fake times `T` and `T+Δ` produce `[T-D,T]` and
  `[T+Δ-D,T+Δ]`, with exactly the same configured duration `D`.
- One refresh with multiple panels/targets gives all captured queries the exact
  same `from` and `to`, even though panels are queried sequentially.
- An absolute historical range is identical across periodic and manual
  refreshes and never consults the clock.
- A backwards wall clock does not make `to < from` and does not move a relative
  range backward; the next forward clock value can advance it again.
- Manual `r` uses the same window policy as scheduled refresh; it must not
  regress to the original construction-time range.
- `[`/`]` changes only the relative duration and keeps later refreshes live;
  minimum/maximum duration clamping remains unchanged.
- Empty datasource, failed datasource, zero/very short refresh intervals, and
  tab shutdown retain their current error/channel behavior. These are
  prerequisites for focused tests, not reasons to change backend behavior.
