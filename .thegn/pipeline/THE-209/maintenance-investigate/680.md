## Finding

The defect remains on this exact branch. `dispatch reap --apply` treats daemon connect/list errors as an empty live-session set, then feeds that set into the same planner used when liveness was successfully observed. The planner interprets every non-live active worker as gone and recommends `CloseDone` or `MarkFailed` from artifact/report facts. The CLI applies those verdicts with a status-only compare-and-set.

Daemon restart and session absence are also treated as proof of exit after a successful query: a session ID omitted from the current daemon's listing is not a positive exit fact. The daemon's periodic reaper has the analogous issue because it passes only the current live-session map's keys to the same planner. Its 60-second startup delay mitigates an adoption race but does not prove that an omitted session exited.

## Production call paths and prerequisites

1. CLI dispatch reaches `cmd::dispatch::run` → `Action::Reap` → `reap` (`crates/thegn-host/src/cmd/dispatch.rs:264-268`).
2. `reap` calls `live_session_ids` before opening the DB and planning (`dispatch.rs:1084-1089`). `live_session_ids` maps both `session::connect` failure and `client.sessions()` failure to `(Vec::new(), false)` (`dispatch.rs:1184-1199`).
3. `reap_plan` snapshots active `spawning`/`running` rows and `reap_plan_rows` maps session-ID membership to a boolean (`dispatch.rs:1048-1081`). A missing `session_id` also becomes non-live.
4. `thegn_core::pipeline_reap::classify` treats `session_live == false` as worker gone, then emits `CloseDone` for a committed clean artifact plus valid report, or `MarkFailed` when the artifact is absent/uncommitted (`pipeline_reap.rs:121-150`). `NeedsDecision` is the existing human path for committed artifact without a valid report.
5. `reap` applies `CloseDone`/`MarkFailed` via `Db::compare_and_set_dispatch_status` (`dispatch.rs:1150-1179`). The CAS in `crates/thegn-core/src/db_dispatch.rs:132-161` guards only observed row status; it does not guard session identity or exit evidence.
6. The daemon starts the periodic self-heal from `daemon/mod.rs:391-392`. `daemon/pipeline_reaper.rs:64-78` waits 60 seconds, then uses `svc.sessions` keys (live entries only) as the live set and retries on a five-minute cadence. It shares `reap_plan_rows`, then closes done rows or parks failed rows (`pipeline_reaper.rs:83-150`). An absent row session ID is still classified as gone.
7. Capacity/duplicate protection is status-based: `pipeline_claim::occupies` returns `row.status.is_active()` and active rows count toward both duplicate detection and stage capacity (`crates/thegn-core/src/pipeline_claim.rs:115-123, 177-193`). Unknown rows left in `spawning`/`running` therefore remain capacity-occupying without changing claim logic.

## Exact evidence that the issue remains

- `crates/thegn-host/src/cmd/dispatch.rs:1030-1037` says daemon unreachability makes every session absent and calls that safe; it is not safe for a still-running worker.
- `dispatch.rs:1184-1191` converts both connection failure and session-list failure into an empty ID vector.
- `dispatch.rs:1084-1089` ignores the `daemon_up` distinction when building the plan; it always plans against the empty vector.
- `dispatch.rs:1118-1123` emits the unsafe assertion that daemon absence is correct after restart and safe.
- `crates/thegn-core/src/pipeline_reap.rs:39-45, 128-150` represents liveness as a boolean and treats false as enough to enter terminal policy.
- `dispatch.rs:1153-1179` applies terminal transitions after a successful or failed daemon query alike. `db_dispatch.rs:132-161` only CASes status.
- `crates/thegn-host/src/daemon/pipeline_reaper.rs:70-77, 105` likewise projects only currently live IDs into the planner; restart delay is a timing mitigation, not an exit record.

## Existing positive evidence and limitations

- Schema v63 already stores `agent_dispatches.exit_code` and `exited_at_ms`; `Db::stamp_dispatch_exit` documents first-writer-wins per run and that retry clears the pair (`crates/thegn-core/src/db_dispatch.rs:455-464`). `pty_drain.rs:1245-1258` writes the stamp on worker exit. `pipeline_run::row_liveness` calls the stamp the only positive exit evidence and treats its absence as unknown (`crates/thegn-core/src/pipeline_run.rs:279-293`). The reap planner currently does not read it.
- `DaemonService::list_sessions` includes recently exited in-memory tombstones with `exited_at_ms` (`crates/thegn-host/src/daemon/service.rs:449-479`), but these are bounded/expiring daemon memory records, not durable evidence across restart. The offline CLI currently discards these records and keeps only IDs without `exited_at_ms` (`dispatch.rs:1192-1197`).
- `compare_and_set_dispatch_retry_run` changes `session_id` and clears exit stamps (`db_dispatch.rs:50-82`), but `stamp_dispatch_exit` updates by row ID alone. Thus the existing stamp cannot yet be called generation-bound without verifying/fixing the delayed-old-exit versus retry race. The planned reap CAS also needs to guard the row's observed session ID and exit stamp in the same DB update/transaction as the status change.
- An absent session after restart, an unreported or evicted tombstone, a missing row session ID, a failed/misdirected query, a timeout, or a live child outlasting daemon teardown is unknown absent positive persisted exit evidence. Artifact/report presence is not worker-liveness evidence.

## Smallest complete fix proposal

Keep the policy in the existing shared core planner. Replace boolean session liveness with an explicit state that distinguishes `Live`, `Exited` (positive persisted evidence for this row's current session generation), and `Unknown`. Make `Unknown` a non-actionable reconciliation/retry verdict with a clear operator message. Only `Exited` should reach artifact/report classification; session absence, missing session IDs, daemon connect/list errors, restart, and tombstone expiry must remain `Unknown`. The CLI should expose daemon reachability/query failure in JSON and human output while preserving active statuses. The daemon self-heal should supply the same positive-exit/unknown facts to the shared planner instead of interpreting missing live-map membership as exit.

Reuse schema-v63 exit facts, but close the generation race before claiming them authoritative: bind exit stamping to the session ID/run being exited, and atomically guard reaping on observed status, session ID, and the same positive exit stamp. The precise source of the exited session ID at the `pty_drain` stamp call must be confirmed during implementation. Preserve the current transactional status/note behavior and CAS conflict semantics. No new polling or shorter cadence is needed; transient unavailability is reported and later normal invocation/slow daemon cadence can reconcile.

This path keeps ambiguous active rows in the roster, so current status-based duplicate and capacity checks continue to reserve their slots. Do not add an independent lease/supervisor judgment mechanism here; that is THE-208.

## Failure cases the implementation must pin

- `connect` refused/permission denied/wrong endpoint and `sessions()` error/timeout: unknown; `--apply` leaves every active row unchanged.
- Daemon restart with a still-running adopted or orphaned child, and a live worker whose control plane is temporarily unavailable: unknown absent matching persisted exit evidence; no failed/done transition and capacity remains occupied.
- Session-list success but row ID absent, tombstone expired, or `session_id` absent: unknown, not exited.
- Matching durable exit stamp plus artifact/report states: existing done/failed/human-decision policy runs.
- Exit stamp from an old attempt arriving after retry publishes a new session: it must not stamp or reap the new attempt.
- A new session/exit generation or status mutation after planning but before apply: atomic guard rejects stale transition.
- Repeated unknown passes do not append notes, change status, or trigger a tight retry loop.
