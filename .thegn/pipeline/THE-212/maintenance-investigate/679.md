## Bug status and production call paths

The bug **remains** on the exact branch and the issue's race is reproducible from the code structure:

1. `session open --stage --chunk` resolves the worktree, reads issue facts/parent, then calls `dispatch::chunk_gate()` at `session.rs:976–978`. That helper reads/parses the incoming chunk and the roster/files outside a write transaction (`dispatch.rs:407–480`). Later, `session.rs:998–1010` calls `Db::claim_dispatch()` to atomically check duplicate/stage capacity and insert. The check and claim are separate operations, leaving an interleaving window.
2. `dispatch claim --chunk` reaches `dispatch.rs:551–588`; it constructs `NewDispatch { chunk_path: chunk, ... }` and calls `Db::claim_dispatch()` directly. No call to `chunk_gate()` exists on this path, so overlapping or unmet-`after:` scope is not checked at all.
3. Retained `dispatch put --chunk` calls the same non-transactional `chunk_gate()` before `put()` (`dispatch.rs:307–326`, `373–385`). It therefore has the same race and does not apply stage capacity/duplicate admission as part of one boundary.
4. `Db::claim_dispatch()` does correctly use `BEGIN IMMEDIATE`, read the roster, call `pipeline_claim::decide_allowing_duplicate()`, insert and append any duplicate-override note before commit (`db_dispatch.rs:311–363`). That decision only considers duplicate work and configured stage capacity. It has no parsed chunk scope/after decision. Thus capacity ≥2 does not prevent two overlapping chunks, and `dispatch claim` bypasses file scope entirely.
5. The gate considers same-issue/same-worktree siblings, ignores terminal rows except `done` contributes to the `after:` set, and reads active sibling chunk files best-effort (`dispatch.rs:432–510`). Current behavior can treat an unreadable/malformed sibling as an empty scope.
6. `AgentDispatch` and `NewDispatch` persist only `chunk_path`, explicitly a pointer to the current file (`issue.rs:266–273, 378–403`; v60 migration `db_migrate.rs:614–625`). `dispatch list --json` also re-reads the file to show `chunk_files` (`dispatch.rs:699–727`). A post-validation edit/replacement can therefore change what the stored claim appears to own.
7. Forced behavior is inconsistent: `dispatch put --force` skips the read and gate, and returns a `forced` JSON marker, but accepts no reason/actor; `session open --chunk` has no force option; `dispatch claim --allow-duplicate <reason>` only overrides duplicate detection and is unrelated to scope overlap. No shared audited forced-overlap path exists.

Current tests in `dispatch.rs:1813–1944` cover ordinary gate overlap, issue/worktree sibling filtering, `after:` status, unreadable sibling behavior, force bypass, and bad incoming files. They test `chunk_gate()` independently and do not cover claim integration, transaction races, replacement between parse and claim, or the `dispatch claim --chunk` bypass. `test/smoke.sh:1940–2000` exercises the existing `dispatch put` gate only.

## Smallest complete fix proposal

Move chunk admission into one shared row-creation operation at the core DB boundary. Before taking SQLite's write lock, the host reads and parses the incoming chunk and materializes the sibling facts needed for the decision. Pass immutable normalized scope data (including `files`, `overlaps`, `after`, chunk identity, and a content digest or equivalent binding) into a shared DB admission API. Inside one `BEGIN IMMEDIATE`, reload current roster/status/capacity state, make the chunk-scope and `after:` decision against the prepared facts, apply duplicate policy and stage limit, insert the row with its admitted normalized scope, and commit. This preserves the no-filesystem-I/O-under-write-lock constraint while closing inter-claim races and binding a claim to exactly what was reviewed.

Route `session open`, `dispatch claim`, and retained `dispatch put` with a chunk through this API. Keep no-chunk legacy `dispatch put` behavior unless the primary elects to standardize all staged puts. A changed/missing/unparseable incoming chunk refuses before claim; forced overlap must be a deliberate shared override requiring a reason and actor, committed atomically with the row and exposed through roster/JSON. It must not silently authorize an unparseable scope. Preserve existing duplicate override semantics and capacity enforcement.

Persisting normalized scope and override audit requires a storage shape beyond `chunk_path`; a nullable JSON scope column plus structured override actor/reason (or an equivalently queryable representation) is the minimal direct model. Existing rows without captured scope need an explicit compatibility policy: materialize them before claim and fail closed if their scope cannot be established, or define a conservative legacy marker. Do not continue treating unreadable active siblings as empty when that could authorize overlap. Scope equality/overlap should reuse the existing pure `pipeline_chunk` parser/verdict logic rather than duplicate glob or `after:` rules.

- **`overlaps:` meaning:** preserve the existing pure rule: scopes may share only when each chunk's declaration permits the sibling. Confirm this remains intended while moving verdict evaluation into admission.
