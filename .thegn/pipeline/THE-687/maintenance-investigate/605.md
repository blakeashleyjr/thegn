## Exact evidence that the bug remains

1. `crates/thegn-host/src/merge_sweep.rs:196-224` projects due landed rows and
   unconditionally refuses a row whose `result_oid` is NULL or otherwise absent
   at `:208-213` with `landed commit identity is missing`. There is no derivation
   or cache repair on this branch, so the four captured rows remain permanently
   unsweepable. `--force` only changes the due-row selection at `:191-194` and
   does not bypass this guard.

2. The direct cleanup admission at
   `crates/thegn-host/src/merge_lifecycle.rs:330-376` also requires a nonempty
   selected OID and passes it into `cleanup::Verified::probe`. The probe at
   `crates/thegn-host/src/merge_cleanup.rs:521-532` proves both the worktree
   branch head and the supplied landed identity are ancestors of the target.
   Thus the fix must supply a real, Git-verified identity; it must not call
   cleanup with `None` or weaken the branch/target ancestry proof.

3. The captured coordination brief records the live database measurement:

   ```text
   SELECT COUNT(*), SUM(result_oid IS NULL OR result_oid='')
   FROM merge_queue WHERE status='landed';        -- 33 | 4
   ```

   The four rows share `updated_at` seconds `2026-09-11 21:47:24–25`, while
   contemporaneous landed rows have an OID. The same-second cluster is
   consistent with one queue drain handling several already-merged branches.

4. The guarded final-fold writer is not able to create the bad pair:
   `crates/thegn-core/src/db_aux.rs:85-124` rejects
   `MergeFinalStatus::Landed` unless `result_oid` is nonempty, and
   `persist_merge_outcome` calls that validation at `:343-348` before its
   upsert at `:364-386`. `crates/thegn-host/src/integrate_persistence.rs:159-171`
   also rejects an advanced landed report with an empty commit. Therefore the
   bad rows come through the separate queue-aware status-transition paths.

## Writer identified and production call paths

The common defect is `AttemptOutcome::UpToDate`: it proves the branch tip is
already an ancestor of the target, but carries no commit identity
(`crates/thegn-host/src/integrate.rs:1348-1377`; the return is at `:1441-1447`).
The three queue-facing consumers then publish `status='landed'` without a
nonempty result:

| Path                         | Current write                                                                                                                                                                | Why it produces the invalid pair                                                                  |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| CLI queue drain / fold actor | `crates/thegn-host/src/merge_driver.rs:306-317` calls `set(..., "landed", None, ...)`; `set` builds empty `MergeStatusFields` and `replace_merge_status` clears `result_oid` | This is the likely bulk writer for the four same-second rows.                                     |
| `thegn merge land`           | `crates/thegn-host/src/cmd/merge.rs:834-838` calls `update_merge_status(..., "landed", None, ...)`                                                                           | `db_aux.rs:420-444` uses `COALESCE` for a missing OID; a queued row whose OID is NULL stays NULL. |
| In-app ready-row land        | `crates/thegn-host/src/handlers/merge_queue.rs:1102-1108` calls the same `update_merge_status` shape                                                                         | It has the same NULL-preserving behavior.                                                         |

The direct non-queue `thegn land` command in `crates/thegn-host/src/cmd/land.rs`
does not write a queue row; its comment and implementation leave queue
bookkeeping to `thegn merge land`. The queue-aware CLI path above is therefore
the relevant `thegn land`/fold plumbing, not a separate hidden writer.

The current regression test codifies the defect: `merge_driver_status_tests.rs`
at `:194-196` injects `AttemptOutcome::UpToDate` and asserts
`already.result_oid.is_none()`. The DB transition APIs in
`crates/thegn-core/src/db_aux.rs:392-444` have no invariant guard, so a caller
regression can recreate the bad state even if the known call sites are fixed.

## Consumer prerequisites and safety boundary

The existing sweep path is:

1. `cmd/merge.rs` enters `merge_sweep::sweep` only for `on_landed = "expire"`.
2. `merge_sweep.rs:145-189` resolves the main checkout, target, repository
   identity, local/remote location, and prior cleanup holds, then applies TTL
   (or only the TTL bypass for `force`).
3. `merge_lifecycle::remove_landed_with_config` checks the current queue row,
   claims the physical path, and calls `Verified::probe` before hooks,
   teardown, or removal.
4. `Verified::probe` verifies exact linked-worktree identity, branch/target
   refs, branch-head ancestry, optional landed-OID ancestry, index/worktree
   safety, and later revalidates before removal.

The missing-OID repair must be inserted after the local-location and due checks
but before cleanup admission. It should:

- read the branch and target refs from the canonical repository, using bounded
  Git plumbing already used by cleanup;
- first prove `branch_tip` is an ancestor of `target_tip`; if that fails, keep
  the row and never sweep it, including under `--force`;
- derive the first target-side integration commit that contains the branch tip
  (a true fast-forward may use the branch tip itself; a merge must use the
  target-side merge commit, not an arbitrary current target tip), and validate
  the candidate as a commit and as an ancestor of the target;
- atomically fill only a still-landed row whose identity/timestamp still match
  the snapshot, then reload the row before calling cleanup; and
- pass the reloaded row plus the derived OID through the unchanged
  `remove_landed_with_config`/`Verified::probe` path.

If the graph is missing, ambiguous, remote, or no valid target-side integration
commit can be derived, the sweep must report a refusal and retain the worktree.
The derivation is a repair of cache metadata, not a substitute for merged-ness
proof. The OID write must be best-effort cache bookkeeping, but a failed or
lost compare-and-write must not be treated as authorization to remove.

The four captured rows are expected to be the ordinary local, branch-tip-
reachable cases; the primary should confirm their graph shape before approving
the implementation. A squash/rebase history in which the branch tip is not
reachable from the target cannot be safely reconstructed from this row alone
and must remain refused unless the primary identifies an existing authoritative
Git relation that proves the exact integration commit.

## Smallest complete fix

1. Make `AttemptOutcome::UpToDate` carry a verified commit identity (preferably
   the same shared Git derivation helper used by the sweep). Update all three
   queue-aware callers to pass `Some(&commit)` when recording `landed`, and
   update the driver test to assert the full identity rather than NULL.
2. Add a central guard to both `replace_merge_status` and `update_merge_status`:
   no operation may leave a row with `status='landed'` and a NULL/empty effective
   `result_oid`. The guard may allow a NULL argument only when an existing
   nonempty OID is preserved by the legacy COALESCE API; a new landed transition
   with no effective identity must return an error without changing the row.
   This closes all current and future queue status writers, while preserving the
   already-reviewed `persist_merge_outcome` validation.
3. Add a narrow compare-and-write/backfill operation for the sweep (or an
   equivalent exact-row transaction) keyed by worktree, branch, target, landed
   status, and the observed timestamp. It must reject empty derived strings and
   return whether the row was still authoritative. Reload the row after a
   successful write so the updated timestamp and OID are included in cleanup's
   exact-identity recheck.
4. Replace the unconditional missing-OID `continue` in `merge_sweep.rs` with
   the safe derivation/backfill flow above. Keep all existing filter-driver,
   ignored-state, status-race, submodule, special-index, TTL, branch-retention,
   location, and cleanup-hold behavior unchanged.

## Failure cases to preserve

- Cached nonempty OID: current behavior and ancestry proof remain unchanged.
- Missing OID but branch tip is verifiably integrated: derive the real
  target-side result, persist it once, reload the row, and allow the existing
  cleanup proof to decide removal.
- Missing OID with branch not merged, missing objects, invalid refs, remote
  location, ambiguous history, or failed cache backfill: retain the worktree;
  `--force` must not change that result.
- Every status writer must reject `landed` + NULL and `landed` + empty string.
- A stale/racing queue row must be re-read and refused or retried safely; it
  must never be removed using a stale derived identity.
- Existing cleanup protections remain intact: dirty/ignored-state policy from
  THE-686, applicable filter-driver protection from THE-685, index/submodule
  guards, final status/identity revalidation, branch deletion holds, repository
  identity, and TTL semantics.
