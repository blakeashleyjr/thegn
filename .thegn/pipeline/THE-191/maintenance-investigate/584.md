## Bug status on this exact branch

The bug remains.

`crates/thegn-host/src/cmd/plugin.rs:99-164` implements `plugin list` by
calling `discover(cfg, &dir)` and `negotiate` directly. Human output prints
mode, config enabled/disabled, negotiation status, and source at lines
151-161; JSON prints the same config/install fields at lines 116-124. It does
not contact a resident supervisor, daemon, or runtime snapshot. Its existing
`disabled` value at lines 155-159 means disabled by configuration, not
crash-disabled.

The live compositor path is separate:

- `crates/thegn-host/src/plugins.rs:264-365` discovers and negotiates on a
  setup thread. Config-disabled plugins are skipped at 286-290; a resident
  spawn failure only leaves `LoadedState.writer = None` at 299-334; the first
  `PluginMsg::Loaded` is sent only after the setup pass at 363-365.
- `crates/thegn-host/src/handlers/plugins.rs:27-44` has the loop-local state:
  `writer: Option<SessionWriter>`, `restarts: u32`, `disabled: bool`, and a
  provider bridge. These fields are not a typed public health state and are
  not exposed to `plugin list` or control clients.
- `handlers/plugins.rs:391-473` applies messages. A message is keyed only by
  plugin id; responses are deliberately not re-routed by name at 410-417,
  but ordinary messages and exits still are.
- `handlers/plugins.rs:475-515` clears the writer/bridge on exit, increments
  restarts for delays of 1s, 5s, and 25s, and sets `disabled = true` after the
  cap. The only user-facing crash-disabled text is the transient frame model
  status at 506-512.
- `crates/thegn-host/src/run.rs:11634-11654` shuts down the old host, replaces
  `PluginsState`, and starts a new host on config reload. There is no event
  generation tag on `PluginMsg`, so a late old-session message can still be
  identified only by the same plugin id; this is the THE-165 boundary.
- `crates/thegn-svc/src/plugin/session.rs:56-80` exposes `SessionOutcome` and
  `SessionEvent::Exit { code }`, but no supervisor status snapshot. The
  supervisor registry at 93-105 is private and tracks custody/task state,
  not host restart/backoff or config state.
- `crates/thegn-svc/src/plugin/session/owner.rs:70-145` reads stderr only to
  tracing at 136-139. Cleanup retains bounded internal `errors` in
  `SessionOutcome` at 245-253, but that receipt is not forwarded with the exit
  event and is not available to the list command.

Consequently the current code cannot distinguish the requested runtime states:

| Requested state      | Current evidence / result                                                                                               |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `disabled-by-config` | Present only as `PluginSpec.enabled == false`; output is an ad-hoc `disabled`.                                          |
| `starting`           | No state; setup has not yet emitted `Loaded`, and spawn failure is indistinguishable from a non-resident/absent writer. |
| `healthy`            | Implicitly `writer.is_some()` after load; never serialized as a stable state.                                           |
| `degraded`           | Implicitly writer absent during backoff or provider loss; only logs/status text expose it.                              |
| `crash-disabled`     | `PluginEntry.disabled` plus a transient model status; absent from list/JSON.                                            |
| `stopped`            | No durable distinction between deliberate shutdown/reload and a crash exit.                                             |
| `stale-generation`   | No generation field or event tagging exists; THE-165 is unlanded.                                                       |

## Production call path and prerequisites

1. `main.rs:1283` dispatches `Command::Plugin` to `cmd::plugin::run`; the
   standalone command has only `Config` and `config_path` inputs.
2. The compositor creates one `ResidentSupervisor` in `run.rs:1095-1098`,
   creates loop-local plugin channel/state at 7123-7131, and starts the host
   after the first frame at 13870-13885.
3. The setup thread calls the loader and `ResidentSession::spawn`; callbacks
   publish `PluginMsg::Event { plugin, event }` through the loop channel.
4. The loop drains messages at 11724-11738; `handle_exit` schedules respawn or
   disables the entry, and provider bridges are removed/replaced through
   `sync_provider_registry`.
5. The only existing operator control service is the daemon control plane.
   `thegn-svc::control::ControlApi` and `DaemonService` do not own or expose
   the compositor's plugin state. Existing `ControlClient` calls therefore
   cannot be reused for live plugin health without adding an attachment path.

The implementation must first choose one transport/ownership boundary:

- either publish the loop-owned authoritative snapshot through a new
  read-only control route that the CLI can query, with an explicit bridge from
  the compositor to the control service; or
- make a supervisor-owned, atomically published local snapshot the one source
  consumed by both the control/CLI projection and the compositor.

A second config-derived cache, PID/process probing, or a list-command-local
reconstruction would violate the primary decision. If no live supervisor
snapshot is available, the output must say so explicitly and must not infer a
health state.

## Smallest complete fix proposed

1. Define a typed, serde/schema-visible runtime state enum with exactly the
   stable names from the primary brief. Put the state and bounded metadata in
   one `PluginSupervisorSnapshot`/row type owned by the supervisor boundary,
   not in separate human and JSON formatters. Include plugin id, mode,
   config-enabled fact, state, bounded restart count, bounded next
   backoff/age metadata, and a bounded/redacted last-failure summary. Do not
   expose command, environment, paths, tokens, or raw stderr.
2. Make the existing runtime transition points publish that snapshot: initial
   `starting`, successful resident/one-shot readiness `healthy`, backoff or
   missing provider `degraded`, deliberate close `stopped`, and restart-cap
   `crash-disabled`. Preserve the current 1s/5s/25s cap and reload behavior.
   Carry the existing `SessionOutcome`/exit cause into the bounded failure
   field; reuse the existing bounded/redaction helper rather than formatting
   raw stderr in the CLI. Control characters must be removed before either
   output surface sees the value.
3. Add one read-only status projection for both human and JSON `plugin list`
   (or the corresponding control status verb if the primary selects the
   control route). On a missing/unavailable snapshot, emit an explicit
   unavailable diagnostic and a non-success status rather than guessing from
   config or process existence. Keep stable state strings and one exit-code
   policy in the shared projection.
4. Document the restart policy: runtime state is process-lifetime supervisor
   state; after a clean daemon/compositor restart the snapshot begins at
   `starting` and reconciles to `healthy`/`degraded`/`stopped`. A snapshot from
   an unavailable owner is not treated as live health. Do not claim
   `stale-generation` until THE-165 supplies the generation identity/tagging;
   record that state as an explicit follow-up in the implementation/spec
   change.
5. If the selected route changes the control surface, update the typed control
   catalog/route/client and flag `docs/api/control-v1.json` for the primary's
   centralized regeneration. The CLI must query the authoritative source,
   not duplicate its state machine.

## Failure cases and regression tests

Tests should be ordered as follows after the primary chooses the attachment
boundary:

1. Pure state/projection tests: assert every stable state serializes to the
   same exact name in human and JSON projections; assert unavailable snapshot
   is explicit and has the documented exit result.
2. Transition tests drive config-disabled → starting → healthy, a crash to
   backoff/degraded, successful respawn, repeated crash to
   crash-disabled, deliberate stop/reload to stopped, and reload reconciliation.
   Assert restart count and next-delay metadata are bounded and correct.
3. Failure-display tests feed long stderr/error text containing paths, ANSI,
   newlines, and control characters. Assert the published last failure is
   bounded, control-free, redacted as required, and identical through human
   and JSON output.
4. Snapshot ownership tests prove the CLI/control reader consumes one
   authoritative snapshot and does not report healthy from a config-only row or
   a process that exists without a snapshot.
5. Reload/late-event tests must remain limited to the current identity facts:
   verify old-session events cannot be presented as a new generation once
   THE-165 lands. Until then, do not add a made-up generation assertion;
   document `stale-generation` as pending.
6. If the control catalog changes, run the focused route/catalog/schema tests
   and regenerate the control schema centrally; do not broaden this row into a
   workspace gate.
