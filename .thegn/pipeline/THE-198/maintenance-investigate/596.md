# THE-198 investigation — native dispatch row 596

## Verdict

**Plan-ready.** The maintenance defect remains on this exact branch: the
workspace still globally ignores `RUSTSEC-2023-0071`, and the resolved graph
still contains `octocrab 0.54.1 -> jsonwebtoken 10.4.0 -> rsa 0.9.10`.

Recommended disposition: remove the unused native octocrab GitHub layer and
its dependency closure, keep the already-shipped `gh` CLI forge layer as the
sole GitHub implementation, remove the RSA advisory ignore, and add a focused
default-routing regression plus the normal advisory/lockfile gates. This is a
maintenance/security containment change, not a new product feature.

No production source was edited during this investigation. No build, Cargo
command, cargo-audit/cargo-deny command, or broad test was run, per the row
request. The primary agent must review and greenlight implementation.

## Exact evidence that the defect remains

1. `deny.toml:17-22` defines the advisory list and still has the unscoped
   entry `"RUSTSEC-2023-0071"`. Its comment describes a local GitHub App JWT
   use, but current production source does not use GitHub App authentication.
2. `Cargo.toml:155` declares workspace `octocrab = "0.54"`; the service
   manifest consumes it at `crates/thegn-svc/Cargo.toml:55-57`.
3. `Cargo.lock:4635-4655` resolves `jsonwebtoken 10.4.0` and lists `rsa` as
   its RustCrypto dependency. `Cargo.lock:5751-5775` resolves `octocrab 0.54.1`
   and lists `jsonwebtoken`; `Cargo.lock:7035-7054` resolves `rsa 0.9.10`.
   This is a lockfile-established path; `cargo tree -i rsa` was intentionally
   not run because the row request forbids Cargo execution.
4. The resolved octocrab manifest in the local registry has default feature
   `jwt-rust-crypto`, which enables `jsonwebtoken/rust_crypto`; jsonwebtoken's
   `rust_crypto` feature enables the `rsa` dependency. This is why the RSA
   package is compiled even though the application does not use App auth.
5. RustSec's advisory record says there are **no patched versions**, and
   explicitly says `rsa 0.9.10` remains affected as of 2026-09-12:
   <https://rustsec.org/advisories/RUSTSEC-2023-0071.html>.

The branch therefore has both a policy defect (a global vulnerability ignore)
and an avoidable vulnerable dependency in the shipped dependency graph. The
runtime private-key exposure described by the old comment is not currently
reachable from the application's own call sites; that distinction must be
preserved in the implementation review.

## Dependency and operation reachability

### Dependency-provided RSA operations

The resolved octocrab source (local registry, version `0.54.1`) defines
`AppAuth { key: jsonwebtoken::EncodingKey }` and `create_jwt` in `src/auth.rs`
(`15-22`, `55-90`). It calls `jsonwebtoken::encode` with `Algorithm::RS256`.
The corresponding jsonwebtoken RustCrypto implementation parses an RSA
private key and constructs a `SigningKey`/`BlindedSigningKey` for private
signing. Its verification path uses a public key and is not the private-key
operation at issue.

Those operations are dependency-reachable in the current graph, but not
application-call-reachable:

- `crates/thegn-svc/src/forge/native.rs:592-609` builds the octocrab client
  with `.personal_token(token)`, never `.app(...)` or `AppAuth`.
- `rg` over repository Rust sources found no direct use of `jsonwebtoken`,
  `EncodingKey`, `AppAuth`, `create_jwt`, `generate_bearer_token`,
  `RsaPrivateKey`, or `RsaPublicKey`.
- The only current octocrab production use is the GraphQL client construction
  and request in `native.rs`; test fixtures use octocrab's empty client only.

### Production call paths and prerequisites

The current default path is:

```text
host main.rs:1198 installs ForgeSet
  -> forge_handle.rs:22 -> ForgeSet::from_config
  -> forge/mod.rs:268-274 default GitHub ladder
  -> forge/mod.rs:242-255 layers GithubNative then GithubCli
  -> native.rs:707-743 pr_status/pr_list
  -> gate (local GitLoc, closed circuit, public GitHub origin, token,
           and for pr_status a same-host checkout scope)
  -> native.rs:598-608 octocrab personal-token GraphQL request
```

The concrete producers are:

- Full PR panel hydration calls `forges.for_loc(&loc).pr_panel(...)` at
  `crates/thegn-host/src/hydrate.rs:3479-3484`; the native layer can answer
  its current-PR status before the common panel composition fetches extras.
- The sibling open-PR feed runs off-loop at
  `crates/thegn-host/src/hydrate.rs:3691-3722` and calls `forge.pr_list(&loc,
300)`. It uses a local root checkout and the native gate before GraphQL.
- Other host PR/queue operations resolve the same `ForgeSet` through
  `forge_handle::get()` (for example `actions.rs:784-790`, `pr_queue.rs:153-157`,
  and `handlers/pr_queue.rs:229-233`), but `GithubNative` marks operations
  other than current `pr_status`/`pr_list` unsupported, so they fall through
  to `GithubCli`.
- Enterprise entries already bypass native at `forge/mod.rs:246-250` and use
  the CLI directly.
- The control API's `pr_status` is a cache read by contract, not a direct live
  forge call: `crates/thegn-svc/src/control/mod.rs:1008-1011`.

Native prerequisites are therefore all local/operator-side: a local
`GitLoc`, a public `github.com` origin, a resolvable `GH_TOKEN`,
`GITHUB_TOKEN`, or `gh auth token`, a valid checkout scope, and a non-open
circuit. A remote/provider `GitLoc` is refused before token admission at
`native.rs:517-521` and `543-547`. The network request is made to GitHub, but
the current request carries a personal token; no private RSA key enters the
application or the request.

## Failure cases and trust-boundary assessment

- **Current policy failure:** `cargo deny` cannot distinguish this exact
  transitive package from future RSA uses because the ignore is advisory-wide
  (`deny.toml:18-22`). Future code could add an AppAuth/private-key path while
  inheriting the same ignore.
- **Current graph failure:** default octocrab features compile RustCrypto RSA
  despite the application selecting only personal-token authentication.
- **Current runtime private-key case:** not reachable from repository call
  sites found on this branch. The old `deny.toml` wording claiming GitHub App
  JWT signing is current behavior is stale.
- **Remote/untrusted entry:** native forge refuses remote locations before
  token admission. The control `pr.status` endpoint only reads cached rows.
  These are useful boundaries, but they are not a substitute for removing an
  unnecessary vulnerable package from the binary.
- **Operational regression risk of removal:** the native GraphQL optimization
  would disappear. The existing CLI implementation already provides the same
  forge seam operations: `crates/thegn-core/src/github.rs:176-185` implements
  PR listing, and `crates/thegn-core/src/github.rs:123-146` implements PR
  status; `GithubCli` wires them at `github.rs:840-859`. CLI auth reuses `gh`
  credentials and is already the fallback and the entire enterprise path.

## Smallest complete implementation plan

1. **Primary decision:** approve removal rather than another RSA version
   attempt. RustSec reports no patched RSA release, and the application's only
   native auth is a personal token. Do not substitute `rsa 0.10.0-rc.*`; RustSec
   still lists the release candidate as affected.
2. Remove the workspace/service `octocrab` dependency and update `Cargo.lock`
   so `octocrab`, `jsonwebtoken`, and `rsa` disappear from the shipped graph.
   Update the root dependency comment at `Cargo.toml:128-132` accordingly.
3. In `crates/thegn-svc/src/forge/mod.rs`, make the public GitHub ladder
   contain only `GithubCli`; remove the `GithubNative` module/re-export and
   delete the native GraphQL implementation and its two octocrab-specific test
   modules. Keep the existing generic ladder tests for fallback/error behavior
   where they still apply.
4. Remove `RUSTSEC-2023-0071` and its stale GitHub App comment from
   `deny.toml`. Do not touch unrelated advisory entries.
5. Add/adjust a focused forge routing regression in
   `crates/thegn-svc/src/forge/mod.rs`: `github(false)` must have exactly one
   layer, its probe must be the `GithubCli` (`id == "github"`), and it must
   retain the full CLI capability set. This prevents a future default path from
   silently reintroducing a native/JWT layer, including on any caller that
   resolves a forge through `ForgeSet`.
6. Preserve the existing local-only/cache boundaries in the implementation
   diff; no remote request path should gain a new live forge or credential
   operation as part of this maintenance fix.

### Alternative considered but not recommended

Switching octocrab from its default `jwt-rust-crypto` feature to
`jwt-aws-lc-rs` may remove the `rsa` crate, but it retains an RSA private-key
signing implementation in a network-capable SDK, adds a new native crypto
dependency, and leaves the unused AppAuth surface present. It is less complete
containment than removing the unused SDK path and would require a separate
toolchain/CI review.
