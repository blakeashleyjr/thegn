## Mechanism status and security constraint

The exact loss point remains unresolved. The CLI result establishes a live failure on this revision, but only after `Config::load_layered` has run its full tolerant pipeline. Source shows the enum types, aliases, normalizer, and post-processing structure; it does not explain why the reported valid values become defaults. Do not patch the schema walker or `config_enum!` based only on the `$ref` suggestion. First add/execute boundary observations for raw normalize output, direct `toml::from_str::<Config>`, the `apply_json_overlay` round-trip, and the final loader result; repeat through strict `admit_layers`.

Security needs explicit handling in the fix: the account token is a string field. Diagnostics must name a dropped known key but never include its value, and the regression must use only synthetic canary data. The reproduction currently emits no token because the whole account was dropped. `Config::value_at` serializes the typed config (`config.rs:7334-7338`) and `config get --json` emits that value directly (`cmd/config.rs:344-357`); retaining `issue_accounts` may therefore expose a literal token unless the display projection is redacted. Treat this as a required check in the minimal fix, not as permission to print the token while diagnosing.
