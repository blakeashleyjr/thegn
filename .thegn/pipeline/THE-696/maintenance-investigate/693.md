## Production path and prerequisites

1. `thegn wt new` parses `cmd::wt::Action::New`; the top-level nested command dispatch is in `main.rs:388-392,1309`.
2. Single-repo `new` and batched `new_batched` converge on `create_and_register`. The helper creates the Git worktree, records its DB identity with `put_worktree`, then optionally pins the environment. Folder filing belongs after registration and before successful output/return.
3. The standalone folder verb must resolve a real Git worktree path to its canonical worktree root, repository root, branch and tab identity. If the DB row is absent, register it via `put_worktree` first, then make the assignment through `set_worktree_folder_if_identity`; never use the bare update for this path.
4. Folder resolution is workspace-scoped: `ensure_folder(repo_path, input)`; look up the resolved folder row and pass its exact stored name to the identity helper. A false result is an error (missing/stale/foreign worktree or folder identity), not success output.
5. A clear/unfile request clears only the target worktree's assignment. Folder deletion remains unfile-on-delete as the existing DB/TUI contract dictates.
6. The capability row must be wired through the normal catalog route/request projection to control API, MCP, and plugins as the catalog surfaces promise. The API schema snapshot and surface coverage need updating without adding a `surface-gaps` excuse.

## Dependencies and decisions for primary

1. **Headless config default is underspecified under the scope fence.** The issue asks for a `[[worktree_templates]].folder` default and a pipeline-level default; coordination allows the template field but explicitly excludes pipeline auto-filing. Current CLI creation cannot select a template. Decide whether this lane defers that acceptance criterion and adds only explicit `wt new --folder`, or define which template/config entry `wt new` should apply by default. No implicit “first template wins” policy is evidenced in current code.
2. **Missing-row wording versus primitive contract.** The required identity assignment primitive is not itself an upsert. The proposed no-new-SQL resolution is Git identity discovery + `put_worktree` registration + identity-checked folder assignment. Primary should confirm this is the intended interpretation of “upsert” for the standalone command.
3. **Catalog surface semantics.** Issue asks control API, MCP, and plugins. The final capability surface set and scope should match the nearest worktree mutation; API routing/schema work is part of the capability item, not a separate optional follow-up.

## Failure cases the implementation must cover

- Empty or whitespace-only folder name is rejected before folder creation.
- Repeating `wt folder <worktree> <name>` with case/outer-whitespace differences reuses one folder in that repo.
- Same folder name in another repo does not cross-assign or reuse the first repo's folder.
- A Git worktree with no DB row is registered and then assigned; a missing/non-worktree path is refused.
- Folder deleted or renamed between resolution and identity write yields a failure, without filing into a replacement row id.
- Folder assignment refuses a worktree that resolves to another repo.
- Clear leaves the folder row intact; deleting a folder with worktrees unfiles them, matching current behavior.
- `wt new --folder` files newly registered worktrees in both single-repo and `--program` creation; an invalid folder cannot report successful creation as filed.
- Capability route requires the appropriate scope and is reachable through each declared surface; coverage does not grow a surface gap.
