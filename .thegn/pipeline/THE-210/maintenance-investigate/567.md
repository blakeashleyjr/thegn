## Exact production evidence

### Current gate lifecycle

1. `fold_active_repo` resolves the main checkout, resolves the repo-specific
   merge-queue configuration, discovers candidates, and calls
   `run_selected_fold` (`crates/thegn-host/src/integrate.rs:549-579`).
2. The CLI `thegn integrate` reaches the same `run_selected_fold` after its
   confirmation/selection path (`crates/thegn-host/src/cmd/integrate.rs:38-159`).
3. `thegn merge drain` collects queue rows and calls
   `merge_driver::drive_queue` (`crates/thegn-host/src/cmd/merge.rs:590-680`).
   Its driver invokes `integrate::attempt_land` for each branch
   (`crates/thegn-host/src/merge_driver.rs:145-166`).
4. `thegn land` also calls `integrate::attempt_land` directly
   (`crates/thegn-host/src/cmd/land.rs:32-54`).
5. The single-branch fold creates a folded tip, then calls `gate_tip` before
   CAS publication (`crates/thegn-host/src/integrate.rs:1451-1508`). A
   `GateVerdict::Failed` is branch blame; `GateVerdict::Error` becomes
   `AttemptOutcome::GateError` and is not sent to the fixing agent
   (`crates/thegn-host/src/integrate.rs:1366-1372, 1491-1498`).

### Reused-worktree preparation

- `Workspace::prepare_with` canonicalizes the caller path before capturing the
  repository (`crates/thegn-host/src/integrate_gate.rs:430-443`). This is a
  useful partial fix for relative and symlinked callers.
- With `gate_reuse_worktree = true` (the default at
  `crates/thegn-core/src/config.rs:985-989`), it derives a state directory,
  opens/verifies it, and acquires `wt.lock` before examining or checking out
  `wt` (`crates/thegn-host/src/integrate_gate.rs:464-475`). The lock is stored
  in `Workspace` and therefore remains held through materialization, optional
  setup, gate execution, verification, and return/cleanup
  (`integrate_gate.rs:408-417, 566-625, 706-741`).
- A lock failure is currently propagated by `?` at line 469. `gate_tip` catches
  it as `GateVerdict::Error`, but replaces the concrete reason with the generic
  string `gate preparation or identity unavailable`
  (`crates/thegn-host/src/integrate.rs:727-745`). The nested error is only in
  the bounded log. This is fail-closed, but it does not isolate and does not
  satisfy the primary request for an actionable headline.
- Reused state is keyed by `gate_base`, which hashes `repo_root` using
  `DefaultHasher` and appends the path basename
  (`crates/thegn-host/src/integrate.rs:686-702`). The caller is canonicalized,
  but the lock identity is still a path-derived hash, not an explicitly pinned
  repository authority/common-directory identity. There is no test proving
  equivalent filesystem identities, especially Windows case-folded aliases,
  select one lock/root.
- The non-Unix implementation of the platform seam returns `Unsupported` for
  verified directories and regular files (`crates/thegn-host/src/platform/gate_path.rs:151-181,
387-420`). Therefore Windows currently refuses before it can run the
  throwaway path; the existing fixture intentionally documents that behavior
  (`crates/thegn-host/src/integrate_gate_tests.rs:672-683`). This is an
  availability gap, not an unlocked shared-worktree race.
- A unique worktree is already the intended shape when reuse is disabled:
  `prepare_with` creates a private temp parent and does not install a lock
  (`integrate_gate.rs:477-486`). The missing behavior is selecting that path
  when reuse cannot be safely admitted.
- The gate command and setup command are only started after `Workspace` is
  prepared and materialized (`integrate_gate.rs:706-725`), and verification is
  performed after each command. Any fallback must preserve that interval and
  must not reuse the shared `wt` or its target cache when isolation is selected
  unless the target cache is independently safe.

### Existing safety tests and what they prove

- `reused_gate_requires_lock_and_preserves_ignored_artifacts` currently holds
  the lock and expects the second invocation to return an error containing
  `already running` (`integrate_gate_tests.rs:700-721`). This must become a
  regression test for an isolated second gate, or be split to retain a typed
  refusal test for fallback-preparation failure.
- `concurrent_distinct_oid_gate_refuses_instead_of_rechecking_out_active_tree`
  proves the current Unix behavior does not mutate the active shared checkout
  (`integrate_gate_tests.rs:723-772`). It does not prove both processes can run
  safely, which is the requested replacement behavior.
- `platform/gate_path.rs` tests cover nonblocking Unix locks, release on owner
  exit, symlink/hardlink/replacement rejection, and special-file refusal
  (`gate_path.rs:493-567`). They do not cover a cross-platform unavailable-lock
  selection seam.
- Existing tests verify setup failure is an infrastructure `Error` and does
  not run the main gate (`integrate_gate_tests.rs:975-991`), which should remain
  unchanged in meaning.

## Does the bug remain?

Yes, against THE-210’s acceptance criteria, with an important qualification:

| Scenario                                   | Exact branch behavior                                                                                                               | Assessment                                                                 |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Unix lock already held                     | `Lock::acquire` returns `WouldBlock`; preparation aborts before `wt` checkout (`gate_path.rs:450-461`; `integrate_gate.rs:464-475`) | Safe but refuses instead of isolating                                      |
| Unix state directory/open/lock setup fails | Error propagates before shared worktree access                                                                                      | Safe/fail-closed, but no fallback                                          |
| Unsupported/non-Unix platform              | verified gate path returns `Unsupported`; gate is refused (`gate_path.rs:151-181`, `387-420`)                                       | No silent shared mutation, but no required isolated execution              |
| Reused gate succeeds                       | Lock covers prepare/materialize/setup/gate/verify; existing checkout is rechecked at the requested OID                              | Largely satisfies the serialization interval                               |
| Caller aliases                             | `canonicalize(repo_root)` collapses ordinary relative/symlink aliases                                                               | Partial; no pinned common-authority identity or case-folded-platform proof |
| Operator sees setup/lock failure           | `GateVerdict::Error`, but `gate_tip` headline is generic (`integrate.rs:734-742`)                                                   | Correct classification, insufficient diagnosis                             |

The old issue wording about `gate_lock() == None` and continuing into `gate_tip`
describes pre-THE-597 code and is not literally present at HEAD. The live bug
is the missing isolation fallback and incomplete identity/diagnostic contract.

## Smallest complete fix proposed

Keep the existing verified workspace and gate lifecycle. Change only the
admission/identity decision and its tests:

1. Introduce a small gate-state identity helper in the platform/gate seam that
   returns a pinned canonical repository authority (prefer the verified Git
   common directory plus filesystem identity; do not use the raw caller path or
   an unbound `DefaultHasher` path string). Use that identity for both the
   reused gate root and lock path. Preserve private no-follow directory and
   sidecar checks on Unix; add the needed Windows platform implementation or a
   clearly isolated unsupported result at this seam.
2. In `Workspace::prepare_with`, attempt reused-state admission and lock
   acquisition as one decision. If locking is unsupported or state/lock
   acquisition fails, discard that reused-state selection and create the
   existing unique temp-parent workspace. Do not touch or repair the shared
   `wt`; do not use the reused target directory for the isolated path unless a
   separately safe configured target is explicitly available. Keep a concrete
   fallback reason for diagnostics.
3. Ensure the unique path is viable on Windows. The smallest safe route is a
   platform-seam implementation for the existing verified identity operations;
   if that cannot be made safe in this lane, isolate the Windows branch before
   Unix-only reused-state admission and use a native unique worktree path with
   equivalent checkout/identity verification. Never silently select the shared
   reused path without an exclusion mechanism.
4. Preserve the lock object for the entire `Workspace` lifetime when reuse is
   selected. The fallback must likewise retain all cleanup/verification guards
   until setup, gate, and cleanup finish. If isolated preparation itself fails,
   return `GateVerdict::Error` with the operation, path, and OS error; never
   return `Failed` and never dispatch an agent.
5. Preserve the existing `GateVerdict` distinction and replace the generic
   `gate_tip` headline with a sanitized bounded reason such as
   `reused gate lock unavailable at <path>: <error>; isolated gate used`, or
   `isolated gate preparation failed at <path>: <error>`. This makes `land` and
   `merge drain` actionable without exposing secrets.

Likely production files are `crates/thegn-host/src/integrate_gate.rs`,
`crates/thegn-host/src/integrate.rs`, and the platform seam
`crates/thegn-host/src/platform/gate_path.rs`; configuration and queue
architecture should not change.

## Ordered implementation and regression-test plan

1. Add/adjust the platform identity and lock-selection seam; first preserve the
   current Unix descriptor-relative no-follow invariants and define a typed
   unsupported/acquisition error for selection.
2. Add a deterministic injected lock/state failure test. Assert the shared
   `gate_base(repo)/wt` is absent or unchanged, the unique gate command runs,
   and `git rev-parse HEAD == THEGN_GATE_OID` for the requested OID.
3. Replace the current held-lock refusal expectation with a two-process (or
   barrier-backed) concurrency test: process A holds the reusable lock and
   gates OID A; process B falls back to a unique worktree and gates OID B;
   both verdicts pass, each command records its own OID, and the shared `wt`
   remains at A. Include different-repository concurrency to show no global
   serialization.
4. Add an alias/identity test using relative and symlinked entry paths, and a
   platform-specific identity test for Windows case-folded/equivalent paths.
   Assert one gate root/lock identity. Keep symlink/hardlink/replacement
   refusal tests in `gate_path.rs` green.
5. Add unsupported-platform coverage (compiled on Windows CI or through the
   platform abstraction) proving reuse is never selected without exclusion and
   the unique path is used. Do not retain the current “Windows always refuses”
   fixture as the success contract.
6. Add fallback-preparation-failure coverage proving the result is
   `GateVerdict::Error`/`AttemptOutcome::GateError`, carries the concrete

   refs/worktrees, and does not enter fixing-agent routing.
7. Run only the focused validation after implementation: the relevant
