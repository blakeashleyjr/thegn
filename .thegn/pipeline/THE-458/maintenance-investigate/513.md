## Finding

The bug remains on this exact branch. A hostile but valid event can make the
background calendar lane walk its entire lifetime before it knows whether the
requested window contains anything, and the accepted path can repeat the walk.
The current APIs also have no expansion budget or typed overflow state.

### Exact evidence

- `crates/thegn-core/src/calendar/mod.rs:278-305`: `CalEvent::dates_in` resolves
  the first/last dates and pushes every date from `first` through `last` into a
  new `Vec`. It only uses `succ_opt` to stop at a representable boundary; it
  does not accept or clamp to a requested window.
- `crates/thegn-core/src/calendar/mod.rs:343-373`: non-recurring
  `CalEvent::occurrences` calls `dates_in(home).iter().any(...)` merely to test
  overlap, then clones the event and both time values for an accepted result.
  An event wholly outside the window still receives the full date walk.
- `crates/thegn-core/src/calendar/mod.rs:411-433`: `expand_by_date` calls
  `occurrences`, clones the event into `inst`, calls `inst.dates_in(home)` a
  second time, filters dates only after that walk, and `inst.clone()`s once per
  in-window bucket entry. A wide in-window event therefore clones its complete
  payload for every occupied date.
- `crates/thegn-core/src/calendar/mod.rs:308-322`: midnight-exclusive handling
  is inferred after resolving the end. The current behavior must be retained
  for all-day DTEND and timed endings at local midnight, but it has no typed
  malformed/overflow result.
- `crates/thegn-core/src/calendar/recur.rs:364-391` and `:403-477`: recurrence
  expansion is window-filtered but starts at DTSTART's period. It does not
  account for an occurrence whose start is before `from` and whose duration
  crosses into the window. For old endless daily rules it can also walk every
  period from DTSTART; the empty-period guard does not bound non-empty periods.
- `crates/thegn-core/src/calendar/recur.rs:484-529`: sub-daily recurrence walks
  forward from DTSTART, capped only by `MAX_STEPS`; it does not seek to the
  requested window or account for a bounded duration lookback.
- `crates/thegn-core/src/calendar/mod.rs:377-406`: `nominal_span` and `shift`
  use direct chrono subtraction/addition. The occurrence path therefore needs
  the approved checked-arithmetic behavior at Chrono extrema; an inverted span
  currently becomes zero for recurrence duration, while non-recurring
  `dates_in` returns the first date (`:295-297`).
- `crates/thegn-host/src/hydrate_calendar.rs:45-84` and `:88-118`: month fetch
  and periodic refresh load cached source rows, widen the visible range by
  seven days, call `expand_by_date`, and deliver all buckets to the UI.
- `crates/thegn-host/src/hydrate_calendar.rs:319-356`: reminder evaluation
  loads a day-before/day-after cache window, calls the same unbounded
  `expand_by_date`, flattens every per-day bucket, and passes the duplicated
  `CalEvent` values to `reminders::due`. A multi-day occurrence is therefore
  evaluated repeatedly and its payload is duplicated before the reminder
  comparison. `due` itself only accepts `&[CalEvent]`, so it cannot distinguish
  a complete expansion from an incomplete one.
- `crates/thegn-host/src/calendar_docs.rs:70-82,148-154` and
  `crates/thegn-host/src/detail/calendar/mod.rs:72-106,340-355`: the UI stores
  `BTreeMap<NaiveDate, Vec<CalEvent>>`; merge clones each bucket vector, and a
  successful payload is marked loaded unconditionally. There is no error or
  overflow state. `detail/calendar/render.rs:289-306` consequently displays
  `no events` whenever the map is empty after a nominally successful load.
- `crates/thegn-host/src/run.rs:11703-11710,12094-12113`: periodic sync and
  reminder checks are dispatched from the refresh loop. The reminder cursor is
  advanced at dispatch (`:12104-12113`), before the background expansion has
  proved that evaluation completed, so an overflow must not be represented as
  an empty success without changing this contract.
- `crates/thegn-core/src/config_calendar.rs:57-59,79-97`: `max_events` is
  documented as protecting the expansion pass, but it currently only exists as
  a source-row config field.
- `crates/thegn-svc/src/calendar/mod.rs:149-158,180-193` constructs providers
  without passing `CalendarConfig.max_events`. The provider structs initialize
  their private caps to zero (`ics.rs:21-45`, `command.rs:58-84`, and the same
  pattern in `ics_url.rs`/`caldav.rs`), so the provider-level `partial` checks
  are not an end-to-end admission boundary on this branch. This is THE-465
  scope, not a reason to duplicate its implementation here.

## Production call paths and prerequisites

### Month rendering

`DetailAction::FetchCalendar` is created by
`detail/calendar/keys.rs:19-39`, dispatched by
`actions.rs:1324-1340,1398-1403`, and runs
`hydrate_calendar::spawn_month_fetch`. That worker optionally syncs all
accounts over the configured horizon, reads cache rows, widens the month,
expands and buckets them, then sends `RefreshKind::CalendarMonth`. The event
loop (`run.rs:11705-11710`) merges the payload into `CalendarDocs` and applies
it to the open `CalState`; the popup grid and agenda read those per-day values.

Periodic refresh follows the same expansion path at
`hydrate_calendar.rs:88-118`. Provider rows originate in
`CalendarRouter::list_events` (`crates/thegn-svc/src/calendar/mod.rs:200-224`),
then `sync_accounts` writes them through `apply_page` into the DB before the
month/reminder readers load them.

### Reminders

The ticker emits `RefreshKind::CalendarReminders`; `run.rs` dispatches
`spawn_reminder_check`, which reads the DB off-loop and currently expands the
same cache through per-day buckets before `calendar::reminders::due`. A safe
fix must make a bounded/failed expansion explicit to this consumer: an
overflow, invalid span, or arithmetic failure must not call `due` with an empty
or silently truncated list.

### Required dependency ordering

1. THE-457 must settle the recurrence-side bounded expansion contract: how a
   recurrence is sought before the requested window, how long-duration
   instances get a bounded lookback, and how pathological pre-window walks
   return a typed refusal. THE-458 must use that contract and must not claim to
   fix all recurrence validation/arithmetic.
2. THE-465 must make source admission (`max_events`) real and non-disableable.
   THE-458's output budget begins after admitted source rows and must not be
   used as a substitute for source admission.
3. Primary review must approve one common expansion budget/failure model for
   occurrences, occupied-date entries, shared/publication handles, and
   aggregate payload bytes. The local code has no existing budget type to reuse.
4. THE-454's reviewed work is transport-only and can land independently. Its
   remote body/redirect/DNS protections do not alter this core expansion plan.

## Failure cases to preserve or add

- A century-scale timed or all-day event queried for one day must do work
  proportional to the intersected day, not its lifetime; an event wholly
  outside the window must be rejected before occupied-date enumeration.
- A multi-day event whose end is exactly local midnight, including an all-day
  exclusive DTEND, must not mark the ending day. A timed event ending before
  its start must follow the approved malformed-span error policy rather than
  becoming a plausible one-day event.
- An event starting near `NaiveDate`/`NaiveDateTime` extrema must not panic when
  trimming an exclusive end, advancing a date, or shifting an occurrence. Every
  boundary operation needs checked behavior.
- A recurring long-duration event whose start is before the requested window
  must be included when its interval overlaps the window. A recurrence whose
  required lookback or pre-window walk exceeds the budget must return the
  typed partial/error state instead of walking centuries or silently omitting
  it.
- RDATE/EXDATE, DST-zone occurrences, and sub-daily rules must continue to use
  local wall time and the existing gap policy while obeying the same budget.
- A large description/location/url/extra payload on a multi-day occurrence
  must be stored once per materialized occurrence and referenced by cheap
  bucket handles, not cloned once per date.
- Many admitted source rows must exhaust the aggregate budget deterministically.
  The month must retain its last valid result and visibly show overflow/error;
  an initial failed load must not say `no events`.
- Reminder evaluation over an exhausted/invalid expansion must return a typed
  incomplete result and raise no reminders from a partial list. A complete
  multi-day occurrence must be evaluated once, not once per occupied date.

## Smallest complete fix

Keep the provider fetch/cache boundaries and the existing visible-window
semantics, but replace the unbounded map-of-owned-events expansion seam with a
single bounded core result consumed by both host paths:

1. Add a core expansion budget and typed result/error model, coordinated with
   THE-457/THE-465. The accounting must reserve/check before allocation and
   count at least: materialized occurrence records, occupied-date bucket
   entries, public/shared handles, and aggregate bytes for event payloads plus
   result containers. Define deterministic `InvalidWindow`, malformed/inverted
   span, checked-arithmetic overflow, and budget-exhausted outcomes. Do not
   return a plausible partial map as `Ok`.
2. Add a span resolver that compares resolved half-open interval boundaries
   before enumerating dates. It should explicitly handle floating all-day
   exclusive DTEND and timed local-midnight endings, clamp the resulting date
   interval to `[from, to]`, and iterate with checked date arithmetic only
   inside that clamp. Keep a separate overlap check for the non-recurring path;
   it must never call a whole-span `dates_in` allocation.
3. Consume the approved bounded recurrence API from THE-457. Supply a bounded
   lookback derived from the occurrence's checked nominal span (with a hard
   budget cap), so starts before `from` can be considered. Seek or bound
   daily/weekly/monthly/yearly and sub-daily pre-window work; refuse a
   pathological lookback/walk with the typed expansion error. For each
   candidate, resolve its actual `[start,end)` interval and then apply the same
   clamped occupied-date iterator.
4. Represent one materialized occurrence once and bucket references to it (an
   index arena or `Arc`-backed occurrence store is appropriate). Preserve the
   UI's concrete, recurrence-free start/end projection, but make
   `CalendarPayload`, `CalendarDocs`, and `CalState` carry cheap references or a
   shared expansion snapshot instead of cloning complete `CalEvent` payloads
   per bucket. The same result exposes a unique occurrence list for reminders,
   so `due_reminders` no longer flattens per-day buckets.
5. Thread the typed result through month delivery and reminder evaluation.
   Month state keeps the last valid expansion, marks an error/overflow state,
   and renders an explicit unavailable/limited note rather than marking the
   month loaded and saying `no events`. Reminder state only advances its
   successful evaluation cursor after a complete result (or otherwise retains
   a retryable interval) and never interprets `Err`/overflow as an empty
   calendar. Keep all expansion off the event loop.

Likely production files, pending the primary-approved API shape:

- `crates/thegn-core/src/calendar/mod.rs` — span resolution, bounded result,
  occurrence arena/handles, checked date/time behavior, and public exports.
- `crates/thegn-core/src/calendar/recur.rs` — only the bounded seek/lookback
  integration required by the THE-457 contract; do not absorb unrelated
  recurrence validation.
- `crates/thegn-core/src/calendar/reminders.rs` — accept the unique bounded
  occurrence view and preserve complete-vs-incomplete semantics.
- `crates/thegn-host/src/hydrate_calendar.rs` — use the common expansion result
  for month and reminder consumers; return typed delivery/error status.
- `crates/thegn-host/src/calendar_docs.rs`,
  `crates/thegn-host/src/detail/calendar/{mod.rs,render.rs}` — shared handles,
  last-valid/error state, and visible overflow messaging.
- `crates/thegn-host/src/run.rs` (and likely `hydrate.rs` only if the channel
  type needs a result variant) — do not advance reminder evaluation state on
  an incomplete expansion.
- `crates/thegn-host/src/detail/calendar/display_tests.rs` or focused host
  tests — verify last-valid/error projection without broad UI changes.

Do not modify the remote provider transport files for this issue. Wire-up of
`max_events` belongs to THE-465; this issue should consume its admitted input
and own only post-admission expansion/bucketing/publication limits.
