## Direct evidence that the bug remains

1. `crates/thegn-core/src/config.rs:423-441` defines `WarmDirenv::Auto` as
   “warm + `direnv allow`”, and makes it the default. The constructed default
   is repeated at `config.rs:4136`. The shipped example still says auto mode
   trusts the repo and sets `warm_direnv = "auto"` at
   `config/config.toml.example:2721-2732`.
2. `crates/thegn-core/src/direnv.rs:41-57` treats a regular `.envrc` plus
   `flake.nix` with no fresh `.direnv/*.rc` as a cold worktree. Inputs are only
   `.envrc`, `flake.nix`, and optional `flake.lock` mtimes
   (`direnv.rs:59-67`); there is no canonical repository identity or content
   closure.
3. `direnv.rs:219-243` starts a detached thread for a cold worktree. Auto mode
   maps to `Some(true)` at `direnv.rs:291-301`. `direnv.rs:304-337` then runs
   `direnv allow <worktree>` followed by `direnv exec <worktree> true`.
   Both commands inherit the Thegn process environment and use
   `Command::output()` without an output cap or subprocess deadline.
4. `direnv.rs:245-289` confirms the advertised timeout is only a condvar wait.
   A timeout returns `false` while the helper thread and its child continue;
   there is no deterministic cancellation or whole-tree reap.
5. `direnv.rs:105-138` performs the post-success blessing pass. It discovers
   `.direnv/*.rc` with following metadata and opens matching leaves for write
   with ordinary `File::options().write(true).open(...)`. Symlink/hardlink/
   special-file and parent-replacement checks are absent; it changes mtimes.
6. `crates/thegn-host/src/run.rs:740-752` invokes the async warm during startup,
   after config/session load but before any launch-specific sandbox decision.
   A nonempty `session.id` is the only caller-side prerequisite; the helper
   gates on the cold flake shape and `direnv` availability.
7. `crates/thegn-host/src/agent.rs:3622-3635` invokes warming while composing a
   local non-`None` sandbox spec. `sync_warm=true` is used by the off-loop
   `direnv_warm::launch_spec_synced_with` path; `sync_warm=false` starts the
   detached warm. The warm remains host-side even though the resulting pane is
   later sandboxed.
8. `crates/thegn-host/src/wizard.rs:1521-1534` synchronously warms a finalized
   newly-created worktree before the first pane. This call is not guarded by a
   resolved local sandbox; config mode plus the cold flake shape are enough.
9. The launch fan-in is broad: `launch_spec_center_with`/`launch_spec_center`
   (`agent.rs:3316-3360`) cover split and watchdog shell paths; the off-loop
   materialize worker calls `launch_spec_synced_with` at
   `handlers/materialize.rs:203-254`; daemon agent opens call the same full
   resolver at `daemon/agent_open.rs:187-207`; normal picker/preset launch uses
   `handlers/launch.rs:132-176`; and the layout prewarm uses
   `run.rs:5454-5480`.
10. `crates/thegn-core/src/sandbox.rs:1019-1053` also auto-mounts the host Nix
    daemon for a local flake-backed worktree whenever `warm_direnv != off`.
    Thus the current auto path has both host pre-evaluation and an automatic
    host-daemon backstop.

## Failure cases and unresolved dependencies

- A hostile `.envrc` can read inherited credentials, agent/control sockets and
  other host authority, write host files/Git metadata, access network services,
  or leave a descendant alive after Thegn returns.
- A child that floods stdout/stderr or keeps a pipe open can make
  `Command::output()` wait indefinitely; the 20-second `warm_now` bound does
  not bound the child or pipes.
- A fork/setsid descendant is outside the current direct-child `kill`/wait
  model. The existing process-group helpers are in the host platform seam, not
  the substrate-free core direnv module.
- `.direnv` leaves can be symlinks, hardlinks, FIFOs, devices, directories, or
  be reached through a replaced parent; the blessing write has no no-follow or
  containment proof. A newer mtime can also be forged without a byte/revision
  match.
- Approval is not content-addressed. The current key is effectively a path plus
  mtimes and the direnv approval database, not canonical repo identity plus the
  complete `.envrc`/flake/include/tool configuration closure.
- Existing tests (`direnv.rs:352-485`, config coverage at
  `config_tests_coverage.rs:895-917`, and shell-string tests at
  `shell_snippet.rs:87-149`) cover pure cache decisions/config parsing and
  command shape only. They do not exercise hostile code, secret isolation,
  output floods, descendants, cancellation, startup auto-execution, symlink or
  revision races, or host fallback.
- THE-251 is the natural dependency if a host compatibility evaluator is
  retained: the current `sandbox::output_with_timeout` (`sandbox.rs:55-110`)
  kills only its direct child and also captures without a byte ceiling. The
  host `platform::spawn_grouped`/`GroupHandle` seam is a possible implementation
  substrate, subject to the core/host dependency direction.
- THE-420 covers cached Nix devShell activation; THE-215 and THE-225 cover host
  HOME confidentiality and host Git/control-metadata writes. THE-304 and
  THE-233 cover preflight/worker isolation. THE-337 is the analogous language
  server boundary. THE-429/THE-434/THE-430/THE-435 are related mutable-repo,
  hook, CI, and config-admission work and are not present as fixes in this
  branch.

## Smallest complete fix proposal

The smallest safe implementation is to remove host-side direnv warming from
the implicit lifecycle rather than hardening an evaluation path that is still
host-authoritative:

1. Make the default and example `warm_direnv` value `off`; stop mapping any
   implicit/default mode to `allow=true`. Preserve old config parsing only as a
   compatibility/deprecation mapping to off, or remove the obsolete `auto` mode
   after the primary agent chooses the config-compatibility policy.
2. Remove the host `direnv::warm`/`warm_now` production calls from startup,
   worktree creation, launch-spec resolution, materialize, prewarm, daemon
   resume, and agent-open paths. Keep pane-side evaluation only when an actual
   sandbox/provider owns the process; do not make `allowed-only` a disguised
   host evaluator. This also removes the host `.direnv` blessing write from the
   trusted path.
3. Keep the bare-host fallback explicit and truthful: it must not call
   `direnv allow` on the host. If the product needs to prevent an already
   approved user-shell hook from evaluating on a degraded host fallback, the
   fallback must be changed to a clean shell or require a separate explicit
   host-execution confirmation; this is a policy decision the primary agent
   must greenlight because it changes `on_missing = warn` behavior.
4. Decouple the automatic Nix-daemon backstop from `warm_direnv` and ensure
   default-off does not silently re-enable repository evaluation. Review
   `inject_devshell`/`devenv::prewarm` and provider `DevShellClosurePush` as the
   THE-420 boundary; either keep them explicitly out of THE-418 with a linked
   dependency, or disable their host-side repository evaluation in the same
   safety change. Do not claim the `.envrc` fix covers these paths.
5. If product requirements insist on retaining host compatibility warming,
   stop and obtain approval for the larger alternative: a content-addressed
   trust record bound to canonical repo/worktree identity and the full input
   closure, plus a dedicated credential-free worker with minimal environment,
   private staging, bounded stdout/stderr/time/resources, process-tree kill and
   deterministic reap, and no repository-controlled host writes. Reuse the
   existing host process-group seam and THE-251 design rather than adding a
   second ad-hoc timeout facility.

## Ordered implementation and regression-test plan

1. Add the config compatibility/default change and update the config example,
   sandbox OpenSpec requirement, doctor/status wording, and env/config ratchet
   expectations. First invariant: a fresh `Config::default()` cannot schedule a
   host direnv action.
2. Remove or make unreachable the host warm orchestration and cache blessing;
   leave target-side `direnv` execution behind the resolved sandbox/provider
   boundary. Add a pure launch-path decision test that proves startup,
   create, split, materialize, prewarm, daemon resume, and agent-open all
   return “no host warm” under default config.
3. Add a hermetic adversarial regression harness with an isolated HOME/XDG
   state directory, a fake `direnv` executable, a hostile `.envrc`, and
   sentinels for file mutation, secret/socket reads, stdout flood, and a
   forked descendant. Exercise first open/materialization with a cold flake;
   assert no sentinel changes before an explicit scoped approval (or assert
   host compatibility is unavailable if that mode is removed).
4. Add ownership tests for the shell/provisioning paths: OCI/bwrap/provider
   command strings may evaluate `.envrc` only in the target; bare-host fallback
   must not synthesize `direnv allow`/`direnv exec`; provider/host-container
   provisioning remains target-side. Include backend-unavailable and
   remote/provider fallback cases.
5. If `.direnv` cache consumption remains, add no-follow fixtures for symlink,
   hardlink, FIFO/device, directory leaf, replaced parent, mixed revision, and
   mtime-only forged freshness. The test must prove an external sentinel mtime
   is unchanged. If host warming is deleted entirely, retain a regression that
   no production path calls the blessing helper and document existing cache
   files as untrusted target input.
6. If compatibility evaluation is retained, add focused process tests for
   output byte cap, long-lived pipe holder, timeout/cancel, fork/setsid
   descendant cleanup, nonzero exit, minimal environment, network denial, and
   deterministic reap. These are not satisfied by the current condvar timeout.
7. Run only the scoped tests selected by the implementation owner first; defer
   build/cargo/broad gates to the primary agent's approved implementation pass.
   This investigation ran no builds, cargo commands, or broad tests.
