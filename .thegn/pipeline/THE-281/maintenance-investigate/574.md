## Bug status and exact evidence

The bug is still present at current source lines 1195–1207:

```rust
let raw_host = url.host_str().context("control HTTP origin has no host")?;
let host = if raw_host.contains(':') {
    format!("[{raw_host}]")
} else {
    raw_host.to_string()
};
```

`url.host_str()` already includes `[` and `]` for an IPv6 URL host. The
current code therefore produces `[[::1]]:8443` for
`https://[::1]:8443`, while `websocket_url` serializes the same parsed URL as
`wss://[::1]:8443/...`. The invalid value is put into a WebSocket request's
`Host` header, so the HTTP unary path can work while upgrade requests fail.

Current tests at lines 1648–1664 only validate origin admission and WebSocket
URL strings for a DNS name and IPv4 address. They do not call
`origin_authority`, cover IPv6, inspect the upgrade authority, or compare the
unary and WebSocket endpoint authorities.

The locked dependency is `url 2.5.8` (via reqwest). Its source confirms:

- `Url::host()` returns `Host<&str>` with `Domain`, `Ipv4`, and `Ipv6`
  variants (`url/src/lib.rs:1201–1207`).
- `Host`'s `Display` implementation emits IPv6 as `[address]`
  (`url/src/host.rs:186–197`), so it is the typed authority-safe formatter.
- `Url::port()` is the explicit/non-default port and returns `None` for a
  default port; the crate documents this at `url/src/lib.rs:1244–1271`.
  Thus the existing port branch already implements the required default-port
  rule for `http`/`https` (and the generated `ws`/`wss` URL).
- The same parser's IPv6 routine accepts hexadecimal/colon IPv6 syntax but
  not a zone identifier, so `https://[fe80::1%25eth0]` is not supported by
  this dependency. No dependency or parser expansion is warranted in this
  maintenance fix.

## Production call paths and prerequisites

1. Unary remote calls enter `ControlClient::request` at lines 318–335. The
   `ControlAddr::HttpOrigin` arm calls `send_origin_request`, which derives a
   URL with `origin_request_url` and lets reqwest target that URL directly.
   It does not use `origin_authority`, which explains why unary HTTP calls
   remain functional.
2. Event subscriptions enter `subscribe_events_opts` at lines 796–857.

3. Pane warm-attach enters `attach_opts` at lines 892–964 and follows the
   same authority/URI split: `origin_authority` at 915–918, `Host` at
   921–925, and `connect_async` at 959–963.
4. Host-side consumers include the daemon event/error bridge
   (`crates/thegn-host/src/daemon/client.rs:104–155`), compositor pane attach
   (`daemon/client.rs:280–292`), CLI attach (`cmd/attach.rs:79–83` and
   `cmd/session.rs:640–646`), and the plugin feed bridge
   (`handlers/plugins.rs:816–830`). These use the same client methods; local
   Unix/TCP clients are unaffected, while a remote `HttpOrigin` reaches the
   broken branch.
5. `HttpOrigin` production construction is visible in remote/control paths
   such as `crates/thegn-host/src/cmd/merge.rs:405–408`; local service
   fixtures also construct it in `daemon/service.rs:2267–2270`. The origin
   must pass `parse_http_origin`: scheme `http` or `https`, a host, no
   credentials, no path other than `/`, and no query or fragment. Its bearer
   token is added to the upgrade request after authority construction.

The upgrade failure requires all of these prerequisites: an `HttpOrigin`
client, an IPv6 literal, and an event or attach WebSocket operation. An
external TLS terminator/proxy must route the valid authority to the daemon;
the server protocol and route shapes do not need to change. Direct `wss://`
input is intentionally not accepted by `parse_http_origin`; the existing
contract accepts HTTP(S) origins and derives `ws`/`wss` for upgrades. The
`wss://[::1]` acceptance case is therefore tested as generated output from
`https://[::1]`, not as a new input scheme.

## Smallest complete fix

Production change scope: `crates/thegn-svc/src/control/client.rs` only.

1. In `origin_authority`, keep `parse_http_origin` and its typed URL result.
2. Replace the `host_str` plus `contains(':')` heuristic with
   `url.host().context(...)?` and format that typed `Host` with `Display`.
   This preserves one bracket pair for IPv6 and leaves domain/IPv4 output
   unchanged.
3. Keep the existing `url.port()` match. It appends only an explicit
   non-default port and therefore does not emit `:443` for HTTPS or `:80` for
   HTTP; the generated WSS/WS URL has the corresponding normalized behavior.
4. Do not change `parse_http_origin`, `websocket_url`, control protocol
   routes, dependencies, or any host-side caller.

## Failure cases to lock down

The focused test table should assert exact authority strings and generated
WebSocket URLs for:

- `https://[::1]:8443` → authority `[::1]:8443`, URI
  `wss://[::1]:8443/v1/events`;
- `https://[::1]` → authority `[::1]`, URI `wss://[::1]/v1/events`;
- `http://[::1]:8080` → authority `[::1]:8080`, URI
  `ws://[::1]:8080/v1/events`;
- IPv4 with and without a non-default port;
- DNS with and without a non-default port;
- explicit default ports (`https://host:443` and `http://host:80`) without a
  port in the authority/serialized WebSocket URL;
- a scoped/zone-id IPv6 form only if the URL dependency accepts it. With the
  current locked `url 2.5.8`, source inspection shows it does not, so this
  case should remain documented as unsupported rather than expanding scope.

Add a transport-consistency assertion for each accepted origin: derive the
HTTP URL with `origin_request_url` and the WebSocket URL with
`websocket_url`, then assert equal parsed host, port, path, and query after
accounting only for `http`→`ws` or `https`→`wss`. This directly protects the
unary/upgrade endpoint invariant that allowed the bug to hide.
