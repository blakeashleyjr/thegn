# THE-677 maintenance-plan revision

Dispatch 630 · branch `blake/the-677-reap-stale-generations`

## Scope and decision

This is an implementation plan only. No production or test source is changed
here. It replaces the issue's original “never removes the live generation”
acceptance criterion with the primary plan's bounded-retention policy: retain
the newest **K = 3** generations per build unit, consider older generations
only after a **24-hour** age floor, and synchronize each profile's prune with a
non-blocking exclusive lock on `target/<profile>/.cargo-lock`. The existing
whole-worktree reclaim remains a separate policy and byte report.

The user-visible guarantee should say exactly what the implementation can
establish: it retains the newest K inventory entries for each defined unit and
does not prune candidates younger than the configured floor. It cannot promise
that an artifact is or is not live for an arbitrary upcoming Cargo invocation;
that would require Cargo's current unit hash decision, which the background
scan must not ask Cargo to compute.

## Proposed `[disk]` keys

Use these names consistently in `DiskConfig`, `ConfigOverlay`, environment
mapping, and `config/config.toml.example`:

| TOML key                  | Default | Environment key                      | Meaning                                                            |
| ------------------------- | ------: | ------------------------------------ | ------------------------------------------------------------------ |
| `generation_keep`         |     `3` | `THEGN_DISK_GENERATION_KEEP`         | Newest generations retained per unit; clamp/reject values below 1. |
| `generation_min_age_secs` | `86400` | `THEGN_DISK_GENERATION_MIN_AGE_SECS` | Minimum age before an otherwise-prunable generation is eligible.   |

`generation_min_age_secs` should use the existing duration bound and strict
configuration validation conventions. Set `generation_keep = 0` to no special
disable mode; zero is invalid because it contradicts the unconditional newest
generation retention. Disabling the feature should be represented by a
separate explicit boolean only if implementation review shows that users need
one; do not infer disablement from K=0.

## Pure inventory and result types

Add to `thegn_core::disk_reclaim` a filesystem-free input model:

```rust
pub struct Generation {
    pub generation_id: String, // opaque stable id for one fingerprint record
    pub newest_mtime_secs: u64,
    pub bytes: u64,
}

pub struct UnitInventory {
    pub unit_id: String, // stable grouping key, independent of generation_id
    pub generations: Vec<Generation>,
}

pub struct GenerationPolicy {
    pub keep: u32,
    pub min_age_secs: u64,
}

pub struct GenerationEviction {
    pub unit_id: String,
    pub generation_id: String,
    pub bytes: u64,
}
```

The decision function takes `&[UnitInventory]`, policy, and `now_secs`, and
returns deterministic eviction identities plus expected bytes. It sorts
newest-first by `(newest_mtime_secs, generation_id)` within each unit, protects
the first K unconditionally, then chooses only entries whose age is at least
the floor. Age calculations must saturate when `now_secs` predates an
inventory timestamp. The planner must not access the filesystem, invoke Cargo,
or infer paths; the host maps returned opaque IDs to the enumerated footprint.

## Ordered implementation chunks

### 1. Define and test the pure retention policy

**Scope:** `crates/thegn-core/src/disk_reclaim.rs`

Add the inventory/policy/result types and pure planner alongside the existing
whole-target policy. Keep the two policies' candidates and reports distinct.
Specify tie ordering and malformed input behavior (duplicate IDs should be
deduplicated or rejected before planning; prefer rejecting/avoiding duplicate
host inventory entries). The newest generation is retained even when K is
invalid at a direct API call; config validation separately prevents K=0.

**Regression cases:** retain newest K even if old; retain a generation younger
than the floor even when older than K; age exactly at the floor is eligible;
K=1 retains the newest; equal timestamps tie deterministically by ID; empty
unit and empty inventory are no-ops; future timestamps saturate to age zero;
multiple units never affect each other's retention; report bytes equal the
selected inventory bytes.

### 2. Wire and validate the new configuration

**Scope:** `crates/thegn-core/src/config.rs`,
`crates/thegn-core/src/config_tests.rs`,
`crates/thegn-core/src/config_tests_coverage.rs`,
`crates/thegn-core/tests/env_overlay_coverage.rs`,
`crates/thegn-core/tests/config_example.rs`,
`test/env-overlay-ratchet.txt`, `config/config.toml.example`

Add the two `DiskConfig` fields/defaults, overlay fields and setters, the
`THEGN_DISK_*` mappings, duration range validation for the seconds field, and
the example documentation. Exercise both environment keys in the overlay
coverage table/tests. Update the relevant pinned key list only as required by
the existing ratchet; do not weaken or bypass the example/env coverage gates.

**Regression cases:** default values; TOML deserialization and example
validation; each environment variable overlays its matching field; invalid
zero K and out-of-range age fail strict validation with field context.

### 3. Enumerate and prune generation footprints in the host scan

**Scope:** `crates/thegn-host/src/measure/disk.rs`,
`crates/thegn-host/src/measure/mod.rs` (tests if needed), and only the minimal
host dependency manifest change if a portable non-blocking flock primitive is
not already available.

At the existing background disk scan tail, enumerate each freshly measured
worktree's `target/{debug,release}` profiles; do not walk profiles unrelated to
the fresh scan. Acquire each profile's `.cargo-lock` with a non-blocking
exclusive lock before inventory or deletion. A failed lock skips the whole
profile for this round. Keep the lock through pruning. Do not block, run Cargo,
or do this work on the event loop.

Enumerate `.fingerprint/` records, derive one generation record per retained
ID, measure its complete artifact/fingerprint/incremental footprint, and pass
only inventory values to the core planner. For each planned ID, operate on the
full mapped footprint. If a path is missing, unreadable, symlinked outside its
profile, or otherwise unsafe, skip that generation and record the failure;
never partially guess a footprint. Keep normal scan errors best-effort so they
do not fail the disk pump.

**Host regression cases:** a held profile lock causes no inventory deletion;
unlocked profiles prune only planned IDs; each selected generation includes
all mapped deps, fingerprint, and incremental paths; an unrelated profile is
untouched; missing/failed footprint paths are reported and never cause a
partial guessed deletion; a failed profile scan does not suppress other
profiles. Use temporary directories and an injectable lock/filesystem seam so
tests do not rely on the machine's Cargo state.

### 4. Separate reclaimed-byte reporting and document the trade-off

**Scope:** `crates/thegn-host/src/measure/disk.rs`,
`crates/thegn-host/src/measure/mod.rs` tests as needed,
`CLAUDE.md`, and the relevant disk behavior section in
`docs/ARCHITECTURE.md`.

Accumulate actual successfully removed bytes by profile and emit a
generation-specific structured log/notification field. Keep it separate from
the existing `target/` whole-worktree reclaimed amount; when generation
eviction removes nothing, report zero/no generation reclaim rather than
reusing the worktree figure. Preserve partial-failure counts and distinguish
planned bytes from actual bytes. Document K, the age floor, the Cargo lock,
and the explicit cold-rebuild trade-off. Correct the old issue wording in the
design/handoff; do not claim “never removes a live generation.”

**Regression cases:** generation bytes and whole-target bytes remain separate;
reported bytes count only removed files; zero eviction reports zero; one
profile's failures do not inflate another profile's count.

## Findings to resolve during implementation review

1. **Build-unit grouping is underspecified.** A `.fingerprint/<pkg>-<hash>/`
   directory gives a Cargo fingerprint record, but the plan must define how
   different fingerprint IDs are proven to belong to the same build unit
   before “newest K per unit” has meaning. Package-name grouping alone can
   collapse distinct target/profile/feature/build-script units; treating every
   fingerprint ID as its own unit means no generations are ever reaped. Do not
   silently parse private Cargo JSON or call the hash a reproducible unit key.
   Chunk 3 should document the chosen grouping rule and its Cargo-format
   assumptions; if it cannot, stop before deletion and report the blocker.

2. **The claimed cost bound is too strong.** Keeping the newest K records is
   achievable, but a mistaken footprint association or deletion may cause
   Cargo to rebuild downstream dependents or a test binary as well as one
   crate. “At most one unit recompiles; never a workspace rebuild” is not
   established by the proposed policy. Narrow that claim to the inventory
   retention invariant unless a separate mechanism proves the build-cost
   bound.

3. **“If any part cannot be removed, leave the rest” needs transaction
   semantics.** Sequential unlinking cannot restore already deleted paths when
   a later unlink fails. Chunk 3 must either implement a staging/rollback
   protocol that preserves a coherent footprint on pre-delete failure, or
   revise this sentence to report partial deletion accurately and ensure Cargo
   can tolerate the remaining partial state. Do not describe best-effort
   sequential deletion as all-or-nothing.

4. **Cross-platform locking is unresolved.** The repository supports Windows
   and Apple builds; confirm the selected lock primitive has the same
   non-blocking semantics on every supported platform. If `.cargo-lock` cannot
   be locked safely on a platform, skip generation pruning there. A failed or
   unsupported lock must never fall through to an unlocked prune.

These findings do not invalidate the sequencing or the pure-policy design,
but findings 1 and 3 are implementation gates: settle them before enabling
automatic deletion.
