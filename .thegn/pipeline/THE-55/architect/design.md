# THE-55 — move a session between profiles

Status: architecture handoff

## Decision

Add an explicit, admin-only CLI operation:

```text
thegn session move <worktree> --to-profile <name> [--kill] [--dry-run] [--json]
```

The operation runs from the source profile selected by `--profile` / `THEGN_PROFILE`. It moves the selected worktree's persisted session presentation and dispatch ledger into an already-existing target profile. The git worktree directory, branch, and all git objects remain in place; the target database merely gets a cache/resurrection record. No target profile environment is loaded and no credential directory, token, identity, or config overlay is copied.

The operation is a short-lived host orchestration over two independent SQLite stores:

1. Read and validate a source snapshot and the target conflict plan.
2. Inspect the source daemon. Refuse live daemon sessions unless `--kill` was explicitly supplied; with `--kill`, kill through the source control socket and confirm the sessions are gone.
3. Commit the sanitized import in one target-DB transaction.
4. Read back and fingerprint the target rows as confirmation.
5. Only after confirmation, delete the selected source rows in one source-DB transaction.
6. Best-effort push a non-secret “session migrated” notification through the target daemon, if its existing DB registry can discover one.

There is no cross-database atomic transaction. The protocol is intentionally target-first and resumable: a crash after target commit and before source deletion leaves an identical target fingerprint; a retry adopts that existing import and performs only the pending source deletion. A target import is never silently reported as complete while source deletion or confirmation failed; those cases return the existing retryable command outcome and an audit record.

## Current implementation verified

The profile boundary is already process-wide. `profile::reroot` chooses the named state root and applies profile credential environment before command execution (`crates/thegn-core/src/profile.rs:104`), while the default and named roots are derived by `profile_root` (`crates/thegn-core/src/profile.rs:83`). The profile module also unsets inherited GitHub tokens and only mounts existing profile credential directories (`crates/thegn-core/src/profile.rs:155`). The host reroots before opening a DB (`crates/thegn-host/src/main.rs:843`), so the move must not reroot into the target in-process.

The DB is a SQLite cache/resurrection layer, not the source of truth for the worktree: `Db::open_at` exists for an explicit, non-global store (`crates/thegn-core/src/db.rs:314`), and `Db::open_memory` supplies the required isolated test substrate (`crates/thegn-core/src/db.rs:306`). Current resurrection reads `tab_groups` and `group_tabs` to rebuild the host session (`crates/thegn-host/src/session.rs:408`); pane-session identifiers are therefore ephemeral references, not transferable identity. The worktree row currently carries location, ordering, sandbox pick/observation, folder, and env metadata (`crates/thegn-core/src/models.rs:196`), while group tabs carry pane trees, cwd/command hints, daemon-session maps, and scrollback (`crates/thegn-core/src/models.rs:240`).

The current DB schema separates the relevant tables: `tab_groups`/`group_tabs` (`crates/thegn-core/src/db.rs:563`), `session_state`/`ui_state` (`crates/thegn-core/src/db.rs:585`), `agent_dispatches`/`agent_dispatch_notes` (`crates/thegn-core/src/db.rs:718`), and live `session_attention` (`crates/thegn-core/src/db.rs:920`). The persisted running-pin payload is written to `session_state.pin_state` (`crates/thegn-host/src/run.rs:1119`) and consumed during resurrection (`crates/thegn-host/src/run.rs:7343`). Named reusable `layouts` are global templates (`crates/thegn-core/src/db.rs:758`) rather than a worktree's current layout and must not be copied.

The daemon already has the needed edge seams: `SessionInfo` exposes the worktree hint and live/tombstone distinction (`crates/thegn-svc/src/control/mod.rs:57`), the client lists sessions and kills one (`crates/thegn-svc/src/control/client.rs:158`, `crates/thegn-svc/src/control/client.rs:271`), and it can push a notification (`crates/thegn-svc/src/control/client.rs:305`). Existing per-profile discovery is keyed by the active state root (`crates/thegn-host/src/daemon/mod.rs:55`); target discovery must instead use the target DB's daemon registry and target state scope without changing process environment.

The CLI's session verbs are currently thin daemon clients (`crates/thegn-host/src/cmd/session.rs:1`) and connect before their main match (`crates/thegn-host/src/cmd/session.rs:327`). `move` must be dispatched before that connection so a cold migration works. The top-level session namespace is already the right owner (`crates/thegn-host/src/main.rs:575`). The command module list has room for a focused `session_move` module (`crates/thegn-host/src/cmd/mod.rs:11`); do not grow `session.rs` into a migration god file.

## Row policy

The selector is the exact stored worktree path, resolved against the source DB. It selects every `tab_groups` row for the active session whose `worktree` equals that path, not merely a guessed group name. This handles the current one-group-per-worktree shape and old/multi-group rows without silently losing a group. If no such group exists, the command may still move the registered worktree and dispatch rows, but must say that no layout group was found.

Core owns a typed `MigrationBundle`, a pure `MigrationPlan`, and deterministic conflict/id-map policy. SQL is an explicit column allowlist; never use `SELECT *` or copy arbitrary tables.

If target already has the path, target metadata wins and is not overwritten. The source row is deleted only after target confirmation.                                                                                                                                                                                     |

Opaque user-authored `pane_cmds`, scrollback, dispatch reports, and notes are state requested by the move and may contain text that a user typed; the audit output never prints their contents. “Credentials never cross” means no credential store, token, account, pairing, or profile config is read or copied. The dry-run output must warn that opaque text is carried unchanged.

The source and target session name remains the existing session name; it is not a profile identity and does not require an ID remap. Only dispatch IDs are remapped. Group ordinals and tab ordinals are preserved. Worktree paths, artifact paths, and git branches are preserved exactly—there is no filesystem move and no git mutation.

## Conflict, liveness, and resume rules

- Target profile must already exist. Resolve its on-disk state path with a new pure/path-only profile helper; do not call `reroot`, load target config, or apply target credentials. Reject source==target after normalization.
- Refuse when the source profile has another interactive instance (`profile::instance_running`, which subcommands reach before the interactive lock is acquired). This prevents a compositor persist from racing source deletion. Target profile may be running; its separate DB/WAL is made visible by the next resurrection.
- Preflight live sessions as the union of source daemon sessions whose `SessionInfo.worktree` is the exact path, daemon IDs referenced by selected `pane_sessions`, and dispatch `session_id`s. If a referenced live ID cannot be disproven because the source daemon is registered but unreachable, abort. Stale IDs from a confirmed stopped daemon are cleared by the import policy.
- Without `--kill`, any confirmed live source session aborts before either DB is written. With `--kill`, call the existing source `DELETE /v1/sessions/{id}` seam for every live ID and list again; any survivor aborts before import. `--dry-run` never kills and never writes.
- Preflight all target group-key, UI-key, and running-pin conflicts before writing. If the target contains a prior import with the same bundle fingerprint, classify it as `resume`; if it differs, abort. A pre-existing target worktree registration is not a conflict and remains target-owned.
- The target transaction writes the worktree (only if absent), groups/tabs, UI keys, the active session's `pin_state` only, dispatches, and notes. It returns counts, target IDs, and a stable fingerprint over sanitized rows. A read-back of those same allowlisted rows must match before source deletion.
- The source transaction deletes only the exact selected group/tab/UI/dispatch/note/attention rows, clears only the selected session's `pin_state`, and deletes the source worktree row. It must not call the broad `del_worktree` path, whose cache cascade has a larger policy surface (`crates/thegn-core/src/db_workspace.rs:331`). A source delete failure after target commit is a retryable, auditable partial result.
- After source cleanup, the target daemon notification is best-effort. Notification failure is reported as a warning after the primary migration result; it cannot roll back a confirmed move.

Human and JSON output must identify source profile, target profile, exact worktree, selected group names, per-table counts, live IDs/killed IDs, `target_committed`, `target_confirmed`, `source_deleted`, `resumed`, and notification status. It must not include row payloads or credentials. Use the command's retryable exit contract for a target-confirmed/source-pending result.

## Capability, wire, completion, and help surfaces

Add `sessions.migrate` to the single core capability catalog as `Verb::MigrateSession`, `Admin`, CLI-only. The catalog is the one source of truth for surfaces (`crates/thegn-core/src/capability.rs:183`); update `Verb::ALL`, scope mapping, and exhaustive tests (`crates/thegn-core/src/control.rs:396`, `crates/thegn-core/src/control.rs:489`). Do not expose this as a daemon control method or add it to `API_CALLS`: the operation crosses two profile stores and must not become a remotely callable daemon-to-daemon primitive.

Add completion catalog rows for `session move/worktree → Worktree` and `session move/to_profile → Profile` (`crates/thegn-core/src/completion/catalog.rs:242`). Run the completion-slot ratchet. The ratchet file must only shrink; no new pinned line is allowed. Because both new value slots have real sources, the expected text-file delta is none.

The control schema snapshot (`docs/api/control-v1.json`) must remain unchanged: it is generated from control routes/types (`crates/thegn-svc/tests/control_schema.rs:67`), and this design intentionally adds no route or wire type. Run its snapshot test in the implementation chunk to prove that boundary. Update `docs/help/cli.md` and `docs/help/daemon-and-sessions.md` with the syntax, cold/live/`--kill` behavior, row scope, target-first resume semantics, and credential boundary. Do not add a palette action: palette actions are in-process `ACTION_SPECS`, while this operation is an auditable two-profile process boundary and is not cheap or safe to invoke as a UI callback. Help ratchets must run and remain clean; no action-ratchet entry is expected.

No config key is introduced, so `config/config.toml.example` needs no synthetic entry. No DB schema bump is needed; all current tables and additive columns are handled by the existing v61 open/migration ladder (`crates/thegn-core/src/db.rs:136`, `crates/thegn-core/src/db_migrate.rs:186`).

## OpenSpec verification

The draft at `openspec/changes/add-session-profile-migration/` correctly establishes the cold, target-before-source, no-worktree-disk-move, no-credential-transfer shape, and its live-session `--kill` guard. Those claims are already supported by the current profile reroot/socket and resurrection code cited above; the existing daemon client also makes the proposed kill and notification seams real.

The draft must be pruned/expanded before implementation:

- Its “natural unit” is only `tab_groups`/`group_tabs`; it omits the issue-required worktree registration, both persisted pin surfaces, layout state, dispatch rows, dispatch notes, and source daemon-session ID remapping.
- Its `(session_name, group_name)` collision rule is retained but made complete: selection is exact worktree path and can yield multiple groups; worktree registration conflicts are target-wins, while group/UI conflicts are strict.
- Its source-flock claim needs the current startup sequencing. Subcommands return before the interactive singleton lock in `main`, so the host can use `instance_running` as a real “another compositor” guard; do not add a second lock or change the advisory global semantics.
- Its target notification idea is retained only through target DB daemon discovery. Do not load target config/credentials or invent a cross-profile daemon protocol.
- Its `pane_sessions` clearing and “re-adopt” language is made precise: source daemon sessions are killed only with explicit `--kill`; imported rows contain no source IDs, and the existing target resurrection/launch path creates fresh target daemon sessions. No physical session process is transferred.
- Its interruption/idempotency scenario is retained and strengthened with a sanitized fingerprint and explicit retryable partial result. Only `session_state.pin_state` crosses (with target active-tab preservation); named layouts, caches, transports, and all credential-bearing/profile-global tables are excluded.

The existing profile OpenSpec remains the governing whole-process firewall specification (`openspec/specs/profiles/spec.md:1`); this change must not weaken it by rerooting or loading a second profile in one process.

## Chunk order and gates

Two chunks are sufficient and file-disjoint. Chunk 1 is the substrate/policy seam and must land before chunk 2, because chunk 2 consumes its public bundle/plan/store API. Chunk 2 owns all host orchestration and user-facing docs. Each coder commits early with the exact subject in its chunk file. Scoped gates only: `just quick <crate>` and targeted `cargo nextest run -p <crate> <filter>`; never `just test`, `just ci`, a full-workspace compile, or e2e. Any smoke/binary invocation must set `XDG_STATE_HOME` to a fresh temporary directory and must never point at the live state DB.
