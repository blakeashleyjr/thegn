## Bug status and exact production evidence

The defect remains on this exact branch.

### Service parser and client

`crates/thegn-svc/src/lsp/framing.rs:8-13` sets `MAX_FRAME_LEN` to 64 MiB. This is a per-frame byte bound, not a decoded JSON depth, collection, string, or aggregate budget.

`crates/thegn-svc/src/lsp/mod.rs` is the production parser and client path:

- `:418-423` collects every location in a result array.
- `:428-483` recursively visits every symbol and every `children` array. `collect_symbol` has no depth/node limit and uses `to_string()` for names, paths, and containers. A deeply nested valid response can exhaust the reader thread stack.
- `:486-524` recursively flattens hover arrays into intermediate `Vec<String>` plus joined output, with no depth, item, or markdown-byte limit.
- `:527-541` clones every signature and documentation string.
- `:543-558` clones every code-action title/kind.
- `:562-600` clones every diagnostic message/source/code and every diagnostic array item.
- `:977-1000` parses each framed body into an unconstrained `serde_json::Value`; there is no JSON-depth or decoded-value budget before the mapping functions run.
- `:1050-1057` sends each parsed publication to the diagnostics sender. A failed send is best-effort, but the sender itself is not bounded in the current construction.

### Host delivery, application, and retained state

- `crates/thegn-host/src/lsp.rs:50-67` constructs `std::sync::mpsc::channel()`, which is unbounded, and exposes its receiver to the bridge thread.
- `crates/thegn-host/src/run.rs:6645-6661` creates an unbounded Tokio diagnostics channel. The bridge copies every publication from the service receiver into it and pulses the terminal waker.
- `crates/thegn-host/src/run.rs:9260-9275` drains the entire Tokio receiver with `while try_recv()`, applying all available publications in one loop turn. A server publishing unique documents faster than the UI drains can grow the queue and monopolize the loop.
- `crates/thegn-host/src/lsp.rs:127-163` stores `HashMap<root, HashMap<file, Vec<DiagnosticItem>>>` with no roots/files/items/bytes cap. Replacement is latest-per-file only after delivery; queued publications remain unbounded. Empty publications clear a file, but there is no generation or stale-publication identity.
- `crates/thegn-host/src/run.rs:10201-10215` correctly preserves task diagnostics and re-merges LSP state across hydration swaps, but that persistence also makes the uncapped store process-lived until a root is closed.
- `crates/thegn-host/src/panel/sections/mod.rs:690-710` and `panel/sections/problems.rs` render the retained diagnostics but expose no LSP overload, truncation, or stale health.

### Downstream consumers and prerequisites

All LSP result APIs are consumed off the UI loop, but their outputs still enter UI-owned vectors:

- `run.rs:2374-2530`: Symbols outline, references, hover, signatures, and code actions are fetched in `spawn_blocking`, then sent through unbounded `outline`/`hover` channels. `outline_rows` and references map every parsed result; `HoverPopup::build` retains all generated lines before render-time row clipping.

- `search_everywhere.rs:1355-1382`: calls `workspace_symbols`; its final merge has a user-result cap, but the LSP parser has already materialized an unbounded vector.
- The existing fake LSP integration (`crates/thegn-svc/tests/lsp_client.rs` and `src/bin/fake_lsp.rs`) covers the happy path and capability gating only. It does not exercise hostile size/depth/flood behavior.

## Smallest complete fix

Keep this as one bounded LSP contract, with constants in code rather than new user configuration. Exact numeric values need primary approval; the following are conservative candidates for the implementation design:

| Area                    | Candidate cap/contract                                                                                                        | Required behavior                                                                                                                       |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| framed JSON body        | 8 MiB LSP JSON payload, still below THE-310's 64 MiB transport ceiling                                                        | Reject the body before `serde_json::Value` construction and report a bounded parse/truncation health event.                             |
| JSON structure          | depth 64; 4,096 elements per array; 4,096 object members                                                                      | Fail closed or return an empty bounded result with deterministic `depth`/`count` metadata; never recurse on server-controlled children. |
| strings                 | 64 KiB ordinary strings; 4 KiB paths/codes/sources; 256 KiB total hover/markdown projection                                   | Truncate at a Unicode boundary with a deterministic marker and increment the relevant health counter.                                   |
| result projections      | 4,096 locations/symbols/signatures/actions per response; 256 symbol nodes per nesting level and 64 levels total               | Parse/flatten iteratively with an explicit stack and stable input order; stop at the exact limit and mark `truncated`.                  |
| diagnostics publication | 512 diagnostics/file; 4,096 files/root; 32 roots; 16 MiB total retained bytes                                                 | Deterministic newest-generation retention/eviction; empty publication remains an explicit clear.                                        |
| delivery queue          | 256 document keys and 8 MiB queued bytes                                                                                      | Latest-per-document coalescing, nonblocking producer path, bounded drops with overload health.                                          |
| host application        | fixed per-turn item cap plus deadline (for example 32 documents or 2 ms when input/control is pending; 128 or 5 ms otherwise) | Stop draining this source at the slice; preserve queued work for the next wake and guarantee input/control progress.                    |

Implementation shape:

1. Add a small LSP JSON-limit/parser-budget helper beside `lsp/mod.rs`. Preflight depth/aggregate JSON bytes before deserialization, then use explicit iterative stacks for symbols and hover content. Make all collection/string/path projections pass the same budget helper. Keep public feature fallbacks unchanged (`NotAvailable`/empty result), but attach `truncated`, `dropped`, and `invalid/oversize` facts to a bounded `LspHealth`/parse outcome so callers can expose them without retaining raw hostile data.
2. Add `server_generation` and monotonic publication sequence to `PublishedDiagnostics`. Replace the raw unbounded sender/receiver path with one bounded coalescing inbox keyed by `(root, document)`. The inbox must compare generation/sequence before replacing a key, preserve clear publications, account bytes, and use deterministic root/document order with per-root fairness. A full queue evicts according to the documented deterministic policy and increments overload/drop health rather than blocking an LSP reader thread.
3. Make `LspDiagnostics` enforce roots/files/items/bytes limits while applying the inbox. Track active overload, parser truncation, dropped, and stale counters separately from retained data. Retain only bounded display projections; root/file identity used for coalescing must not be derived from sanitized display text.
4. Add a minimal pure helper to `loop_policy.rs` for an LSP source slice (item limit, deadline, and input-priority variant), modeled on the existing PTY `drain_budget`. Change only the LSP drain at `run.rs:9267` to use it. It must leave work queued, yield when input/control is pending, and avoid a whole-host receiver migration; that remains THE-657.
5. Sanitize only at UI-facing projections (`to_panel_item`, symbol rows, and `HoverPopup` inputs): strip ANSI/OSC and other terminal controls and cap display text. Preserve bounded source values/keys separately for diagnostics identity and stale sequencing. Add a compact LSP health indicator to the Problems summary/panel, carried across hydration swaps like the existing loop-owned diagnostics, so drops/truncation/stale data are visible without turning health into another unbounded stream.

This avoids changing LSP feature semantics, server lifecycle, provider registry, or unrelated receivers. It also avoids making the 64 MiB THE-310 frame cap carry responsibilities it was not designed to carry.

## Failure cases the fix must cover

1. A `documentSymbol` response with thousands of nested `children` entries and depth beyond the cap does not stack overflow, does not allocate an unbounded result, preserves stable prefix order, and reports truncation.
2. Huge arrays of locations, symbols, signatures, actions, or diagnostics stop at the exact count cap; exact-limit input is accepted without a false truncation flag, while limit+1 is flagged.
3. Huge names, paths, codes, messages, source labels, hover markdown, and signature documentation are bounded at Unicode boundaries; terminal controls cannot reach panel rendering.
4. A valid JSON body near the transport maximum but above the LSP JSON cap is rejected before recursive `Value` construction; malformed/deep JSON fails closed with health metadata and does not kill unrelated host work.
5. A slow consumer receiving repeated replacements for one document retains only the newest generation/sequence, including an empty clear; a late older generation cannot resurrect stale diagnostics.
6. A server publishing unique files/root partitions faster than the loop drains stays within queue and retained-byte caps; drops and overload become visible, and a normal publication after the flood is delivered.
7. A flood from root A cannot consume the full per-turn budget or starve root B; multi-root application makes bounded progress for both.
8. A queued LSP flood does not delay a pending key/control action beyond the existing frame/input policy; the LSP source resumes on later wakes.
9. Closing/retaining roots releases bounded state, repeated replacements and clears do not leak bytes, and hydration swaps preserve diagnostics plus health without duplicating entries.
