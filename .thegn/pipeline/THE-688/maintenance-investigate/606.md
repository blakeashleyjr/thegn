## Branch status and whether the bug remains

The bug remains on this exact branch by static call-path inspection. `LocalResources::revalidate` in `crates/thegn-host/src/merge_cleanup.rs:82-96` refuses if any of these are true:

1. `has_cleanup_tenancy(path)`;
2. `has_persisted_worktree_session(path)`;
3. `has_cleanup_dispatch(path)`.

`has_persisted_worktree_session` is implemented at `crates/thegn-core/src/db_workspace.rs:37-46` as `SELECT EXISTS(SELECT 1 FROM tab_groups WHERE worktree=?1)`. The `tab_groups` row is persisted layout (`session_name`, group/name/kind, worktree, ordinal, active tab and related layout identity fields), not a PID, lease, expiry, or live ownership record. Opening a worktree as a tab therefore creates a durable veto.

The real process-local liveness check is immediately after the database predicates at `crates/thegn-host/src/merge_cleanup.rs:94-96`: `worktree_lifecycle::automatic_cleanup_session_absent`. Its implementation at `crates/thegn-host/src/worktree_lifecycle.rs:1361-1371` checks `session_runtime()`’s `latches` and `ending` maps and returns `active session requires explicit cleanup` when either contains the current worktree/process key. This guard must remain unchanged.

The sweep path is production-reachable from `merge_sweep::sweep_with_db` (`crates/thegn-host/src/merge_sweep.rs:132-249`): it filters landed rows, applies TTL unless `force`, and calls `merge_lifecycle::remove_landed_with_config`. That function admits cleanup through `LocalResources::settle` (`crates/thegn-host/src/merge_lifecycle.rs:368-420`), then revalidates the same resources immediately before removal (`:443-498`). Thus the persisted-layout veto blocks both ordinary expired cleanup and `--force`; it is not merely a display/report condition.

## Production call path and current bookkeeping gap

The automatic path is:

`run.rs` startup/post-fold or the sweep action → `merge_sweep::spawn/sweep_with_db` → `merge_lifecycle::remove_landed_with_config` → `cleanup::LocalResources::settle/revalidate` → `worktree_lifecycle::automatic_cleanup_session_absent` → `destroy_one_checked`/`Verified::remove_checked` → Git worktree removal → cache transaction.

The physical removal succeeds before the post-removal bookkeeping transaction at `crates/thegn-host/src/merge_lifecycle.rs:508-562`. That transaction currently checks queue/cache identity, calls `db.del_worktree(worktree)` at `:539`, and conditionally removes the queue row; it does not delete `tab_groups`.

The existing interactive/headless lifecycle cleanup does delete layout rows after successful removal: `worktree_lifecycle.rs:584-589` and `:652-657` call `workspace_remove::forget_worktree_path_in_db`, whose implementation deletes named groups and then calls `delete_tab_groups_for_worktree` at `workspace_remove.rs:309-318`. Automatic merge cleanup does not call that helper, so a successfully swept worktree can leave an orphaned persisted layout.

`WorkspaceStore::delete_tab_groups_for_worktree` is currently session-scoped (`crates/thegn-core/src/store/workspace.rs:324-330`, implemented at `db_workspace.rs:1081-1093`). Because `has_persisted_worktree_session` searches all `tab_groups` sessions, the complete automatic cleanup should delete every `tab_groups` row (and its `group_tabs`) matching the removed worktree path. The smallest isolated design is a new all-session store operation used inside the existing post-removal transaction, without changing the semantics of the existing session-scoped operation used by `wt rm`/interactive cleanup. If the primary confirms the database invariant that one worktree can only occur in the current session, the implementation may instead reuse the existing operation with the recorded `WorktreeRow.session_name`; that invariant was not assumed here because the schema and predicate are explicitly session-agnostic.

## Failure cases and safety constraints

Current failure: any persisted layout makes the worktree `Refused`, even after TTL expiry and with `force=true`; the queue/cache and physical worktree remain.

After the planned change, these must still refuse in both force modes:

- a live session latch or an in-flight session-end entry (`automatic_cleanup_session_absent`);
- a host-tenancy row (`has_cleanup_tenancy`);
- an unknown/nonterminal or pending dispatch (`has_cleanup_dispatch`);
- all existing identity, dirty/changed, resource, provider, branch, submodule, special-index, and queue consistency guards.

`--force` may bypass only the TTL clock. It must not bypass the process-local liveness guard, tenancy, dispatch, or any existing cleanup safety check. Physical removal is deliberately no-force; Git’s own refusal remains a backstop for real user edits.

The post-removal layout deletion should be in the same existing DB transaction as cache/queue bookkeeping. Normal success must leave no `tab_groups` or `group_tabs` rows for the removed path. If that transaction fails after physical deletion, retain the existing partial-bookkeeping behavior and surface a bookkeeping error; do not widen this issue into rollback/refactoring.
