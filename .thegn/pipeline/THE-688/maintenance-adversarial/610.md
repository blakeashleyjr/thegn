## Findings

### 1. High — a session can start after the last liveness check and be deleted

The final resource check is a point-in-time sample, not an admission lock:

- `crates/thegn-host/src/merge_cleanup.rs:93` calls
  `automatic_cleanup_session_absent` through `LocalResources::revalidate`.
- `crates/thegn-host/src/merge_lifecycle.rs:476-498` passes that check into
  `destroy_one_checked`.
- `crates/thegn-host/src/worktree_lifecycle.rs:766-830` runs the final guard at
  `:826`, then proceeds to physical removal at `:830-858`.
- `session_start_once` independently inserts the liveness latch at
  `crates/thegn-host/src/worktree_lifecycle.rs:1260-1285`; it does not contend
  with `try_physical_destroy_path` or the destroy claim.

An interactive/session worker can therefore call `session_start_once` after the
`:826` guard returns and before `worktree::remove` runs. The sweep then removes
the checkout despite a live session latch. `--force` does not change this
ordering. The new regression at `merge_sweep.rs:691-728` only seeds a latch
before admission and cannot expose this interleaving.

The liveness check needs to be paired with an admission lock shared by session
start and destroy, or the destroy claim must make session start fail/ wait until
physical removal is complete. Add a deterministic interleaving regression that
publishes a session latch immediately after the final guard and asserts that no
remove operation is entered.

### 2. High — queued layout snapshots can recreate the deleted rows

Automatic cleanup deletes layouts through a direct `Db` transaction at
`crates/thegn-host/src/merge_lifecycle.rs:524-540`. Session persistence instead
queues a full clear-and-insert snapshot on the process-global writer at
`crates/thegn-host/src/run.rs:5850-5866`; `db_task::persist` is FIFO only within
its own channel (`crates/thegn-host/src/db_task.rs:96-112`). There is no writer
barrier or tombstone in the cleanup path.

A stale snapshot can already be queued when a worktree closes or its last pane
exits. Once the session latch/ending entry is gone, the sweep can pass
`automatic_cleanup_session_absent`, remove the physical worktree, and commit
the all-session layout deletion. If the queued writer obtains SQLite afterward,
its older snapshot reinserts the removed worktree's `tab_groups` and
`group_tabs`. The next resurrection can see the path again, and the original
"no rows remain after successful cleanup" acceptance condition is violated.
`session_end` completion does not flush `db_task`, and the existing
`db_task::flush` is only used on shutdown/workspace-switch paths.

The cleanup transaction needs ordering against queued layout writes (for
example, a writer barrier before deletion plus a prevention mechanism for later
stale snapshots, or a serialized cleanup job/tombstone). Add a regression that
queues a snapshot, performs cleanup, releases the writer, and asserts that no
layout rows for the removed path can reappear.

### 3. Test gap — the new integration coverage does not exercise either race

The host tests are otherwise aligned with the primary plan, but all new cases
are serial: the live-session case pre-registers its latch, and the collection
case writes layouts synchronously before invoking the sweep. They do not cover
the two concurrent call paths above, nor do they verify that a queued snapshot
cannot overwrite the post-removal deletion. The added core regression at
`crates/thegn-core/src/db_workspace.rs:1586-1615` does cover rollback of the
new child/parent deletion when surrounding bookkeeping fails; it does not
substitute for the host-level race tests.
