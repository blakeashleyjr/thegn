## Exact-branch evidence and call path

1. `resolve` materializes configured `[sandbox].env_passthrough` values from the launcher environment into `SandboxSpec.env` (`crates/thegn-core/src/sandbox.rs:991-1004`). This is the source of host credentials such as `GH_TOKEN`.
2. `ensure` calls `oci_create_opts` and appends its result to `<runtime> run ...` (`sandbox.rs:1738-1796`).
3. `partition_secret_env` classifies a value as secret only when placement is local **and** it matches the launcher environment (`sandbox.rs:2323-2347`). For every remote placement, all pairs are returned as inline pairs. The nearby comments explicitly say remote specs retain all pairs inline because SSH argv is the only carrier.
4. `oci_create_opts` emits each inline pair as `-e KEY=VALUE` (`sandbox.rs:2499-2518`). `ensure` then calls `spec.placement.control_argv(&argv)` and starts that SSH command (`sandbox.rs:1800`). `SshPlacement::control_wrap` shell-joins the entire runtime argv into one SSH argument (`placement.rs:174-180`). Thus the canary is in local `ssh` argv and in the remote shell command/OCI runtime argv.
5. The behavior is pinned by `remote_oci_keeps_all_env_inline_as_carrier` (`crates/thegn-core/src/sandbox_tests.rs:1486-1518`), which sets `GH_TOKEN=ghp_secret` and asserts `-e GH_TOKEN=ghp_secret` is present. This is direct branch evidence that the finding remains, despite the captured audited line numbers no longer matching current source.

Additional secret-bearing route to account for in complete acceptance: `SandboxSpec.env_overrides` is used for scoped API keys (`sandbox.rs:493-497`); `wrap_script` renders every value as `export KEY='VALUE'` (`sandbox.rs:2020-2045`); and remote OCI `backend_enter_argv` includes that script in the `exec` argv (`sandbox.rs:2071-2100`) before SSH wraps it via `interactive_argv`. This can leak a scoped key even after fixing the container-create `-e` route. Host usage is at `crates/thegn-host/src/agent.rs:1003-1067, 3432-3504`. Whether all override values are secret-bearing must be verified when implementing; at minimum the scoped-key case must be tested.

## Error/log surfaces and failure cases

- SSH control operations use `status_with_timeout` or `output_with_timeout`; the former returns only status and the latter returns stdout while discarding stderr (`sandbox.rs:55-143, 2828-2849`). The container-create path captures stderr (`sandbox.rs:1800-1801`) and may parse mount paths from it, but its generic failure is currently redacted to runtime/container name (`sandbox.rs:1820-1862`). These current paths do not intentionally log the canary.
- The placement lifecycle runner formats the full argv and captured stderr into returned errors (`placement.rs:560-573`). It is not the ordinary OCI SSH-create route, but establishes that command/error formatting is not globally safe for future secret-bearing commands.
- `sandbox_build::build_image` returns the last runtime stderr line in both progress and the error (`crates/thegn-core/src/sandbox_build.rs:89-125`). This is an adjacent OCI subprocess error surface; if the selected fix changes its use or secret-bearing inputs reach it, redact before forwarding.
- The present hard failure cases are: secret-bearing remote OCI create exposes values in local `ps`/process diagnostics and remote command audit/process listings; retries or diagnostics that reuse rendered argv can repeat the leak; runtime errors that echo a received secret could carry it into logs/errors; and secret staging failures must not fall back to inline argv. Cleanup must happen after success, failure, timeout, and interrupted SSH sessions. No remote secret-file/stdin protocol currently exists in core.

## Smallest complete fix proposal

Keep local behavior intact. For a transport-wrapped remote OCI launch, separate secret pairs from ordinary pairs and execute secret-bearing control/exec operations through a bounded secret-input path: place only safe variable names, a non-secret operation description, and a fixed remote helper invocation in argv; deliver the secret payload on SSH stdin using an unambiguous bounded encoding; on the remote side create a private temporary secret file or equivalent short-lived process environment, invoke the OCI CLI without values in argv, and guarantee cleanup on every exit path. Fail closed if transport/staging fails; never reconstruct the old inline argv as fallback. Prefer reusing one helper for create retries and scoped `exec` overrides so both paths share limits, redaction, and cleanup.

Before coding, primary review should choose the remote representation and protocol details. A newline-delimited env file is not automatically safe for arbitrary values containing newlines, and remote shell parsing must not turn payload bytes into command text. Bound total key/value bytes and key count, validate key syntax, use restrictive permissions before writing, trap cleanup, and redact any helper/runtime stderr that could echo values. The private file must live on the remote execution host (an SSH placement), not the local `$XDG_STATE_HOME` env-file used by local OCI/systemd. If those requirements cannot be met on a supported remote shell/runtime path, refuse the secret-bearing launch with a redacted error.

Also make command diagnostics safe by construction: no secret value in SSH or OCI argv, command strings, structured logs, progress text, returned errors, or parser-generated failure details. Keep current generic runtime/container error summaries for secret-bearing operations; do not include raw argv or stderr. Dry-run/doctor reporting should expose only source/provenance (for example, “passthrough key present”), never values.
