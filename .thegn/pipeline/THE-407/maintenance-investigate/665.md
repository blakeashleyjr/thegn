## Finding: issue remains on this exact branch

1. `crates/thegn-core/src/config.rs:3522-3569`: `AppsConfig` documents only `work`; `BUILTIN_TABS` is `[("work")]`. `effective_tab_order` drops every name other than `work`, then appends `work`; `normalized_default_tab` falls back to the first surviving name. Therefore `default_tab = "observe"` cannot survive normalization and `observe` cannot be placed by the requested order.
2. `crates/thegn-host/src/apps/registry.rs:30-45`: host registry separately registers `observe`, gated by `cfg.observe.enabled`. This registry is not available to core config resolution.
3. `crates/thegn-host/src/apps/mod.rs:129-174`: `AppHost::from_config` consumes the already-filtered core order, makes slots only for enabled builders, then appends any omitted enabled slots. That append makes Observe reachable but cannot honor its requested position or default selection.
4. `crates/thegn-host/src/run.rs:6411-6412`: the loop creates an `UnboundedChannel<usize>` for app change events and constructs `AppHost` once from the startup config.
5. `crates/thegn-host/src/run.rs:11534-11628`: successful config reload rebuilds the keymap, publishes `current_config`, and updates multiple live services, but never reconciles `app_host`. Config errors leave the existing app state in place. `need_relayout = true` is set after the reload updates, so an app-host reconciliation can be incorporated as a full chrome relayout.
6. `crates/thegn-host/src/run.rs:15924-15953`: switching and input dispatch use `ActiveApp::Tile(index)` and index into `slots`. `app_change_hook` in `apps/mod.rs` captures a slot index. Reordering slots while retaining existing callbacks can route an old callback to a different tile.

## Catalog and layering decision

Do not project app tabs from `thegn_core::capability::CATALOG`. That catalog is
the authoritative list of externally callable control capabilities, with
stable capability IDs, scopes, and surface membership (`capability.rs` docs and
catalog rows); UI tiles have builders, opt-in predicates, labels, and tile
lifecycle instead. Registering `observe` as a capability would falsely expose
it as an API/MCP/plugin operation or add unrelated capability metadata. Nor
should the app registry be moved into core: `docs/ARCHITECTURE.md` makes core
substrate-free and the primary brief explicitly forbids moving the app catalog
across this seam.

The least-coupled candidate is a host-owned app registry as the authoritative
runtime catalog, with its known IDs projected into core's pure order/default
resolution through explicit caller-supplied IDs (rather than a core-to-host
dependency). However, strict `config validate` and admitted config validation
currently live in core, and schema describes these fields as plain strings.
The three-file scope does not specify how that host registry projection reaches
those validation surfaces or what actionable diagnostics they should emit.
This must be settled before implementation if acceptance requires diagnostics
from those surfaces, rather than only runtime normalization.

## Smallest complete implementation plan (for primary review)

1. **Set catalog/validation contract.** Keep `APP_BUILDERS` host-owned and validate uniqueness, reserved `work` collision, and IDs there. Expose a pure known-ID projection to config-order resolution via explicit arguments. Decide whether core validation receives the projection from the host-facing `config validate` command/admission caller, or whether unknown names remain runtime warnings; document the same outcome for schema/help. Do not encode host IDs in a second core list or repurpose the capability catalog.
2. **Resolve order/default against known, enabled entries.** In the registry/config resolution path, preserve configured known IDs once in requested order, include `work`, and append enabled registered apps omitted by the user in deterministic registry order. Produce diagnostics that distinguish unknown ID, known-but-disabled ID/default, duplicate ID, and unavailable ID. Never select a disabled or unavailable default; fall back to Work. Define deterministic behavior when current default is removed or disabled.
3. **Reconcile `AppHost` by stable ID on successful reload.** Build the desired slot set/order from the new config. Preserve each still-enabled slot's loaded state by ID; call `AppTile::shutdown` for removed/replaced running tiles; choose active tile by the new default when the user-facing policy says default changes selection, otherwise preserve the previous active ID if it remains enabled. If the old active app disappears, fall back to Work. Do not carry `ActiveApp::Tile(index)` across a slot reorder; resolve the active ID to its new index.
4. **Fence callback events.** Current callbacks capture vector indices. Before preserving tiles across reorder, change callback messages to carry stable app ID plus a per-slot generation/instance token and reject stale events after removal/recreation (or prove an equivalent strategy in tests). This prevents an old tile's late callback from pumping a different tile now at its former index.
5. **Wire reload and rendering in `run.rs`.** Reconcile only after config admission succeeds, keep the old app host on reload error, ensure the newly selected app is loaded through the existing lazy-load path, update app tab model state, and request the existing full relayout/repaint. Reconciliation must not add blocking I/O; tile build/lifecycle behavior must retain current event-loop constraints.
